* Intent

Make the Herdr TUI plugins and the herdr-app mods depend on one shared install of the herdr-orch and org-tasks skills at `~/.agents/skills`, and make a missing or mismatched install easy to diagnose from each surface. Neither surface installs the skills or the other surface. The skill under `skills/herdr-orch` stays the canonical implementation, and the live dotagents development flow (out-of-store symlinks, `herdr plugin link`) continues unchanged.

* Summary

*Level:* MVP · *Tests:* smoke · *Docs:* README

The TUI and desktop surfaces run side by side on the same machines, and both must resolve the same `oh` and `ot`.

** Scope

*** In scope

- Skill-first resolution in the TUI plugins: `~/.agents/skills/...` first, then the checkout-relative path, for `oh` (herdr-orch plugin) and `ot` (org-tasks plugin).
- A read-only `doctor` popup pane and mirror action in the herdr-orch plugin, beside the existing `quota` pane, `quota-stanza` and `tree-toggle` actions, startup hook and event hooks.
- A not-installed state, with the missing path, in the herdr-app quota and org-tasks mods.
- `skills/herdr-orch/references/install-surfaces.md`: a redirect to the existing install instructions of each surface.
- Traits-binary fallback resolution in `pi/extensions/traits/index.ts` (delivered).
- Preflight version gate in the `oh` CLI (delivered by task [[task:cf561004-25e4-46ee-aa4a-5e09b8eecff6][Simplify herdr-orch skill based on upstream changes]]; later raised to 0.9.1 by [[file:2026-09-17-herdr-orch-improvements-260917.org][herdr-orch improvements 260917]]).

*** Out of scope

- Any plugin, mod or skill code that installs, links or repairs the skills, the plugins or the mods. Home Manager owns this on the owner's machines; other users follow the READMEs.
- Any `[[build]]` manifest entry.
- The Pi orchestration proxy extension `pi/extensions/herdr-orch`.
- Claude Code and Codex `UserPromptSubmit` trait adapters (see Follow-ups).
- Windows support.
- Moving orchestration logic out of `skills/herdr-orch`.
- Marketplace listing (see Open questions).
- Babashka bootstrapping (see Follow-ups).

** Decisions

- Chose diagnostics over a shared, externally owned install :: the TUI plugins and the herdr-app mods run side by side, and the mods already run `oh` and `ot` from `~/.agents/skills` by absolute path. If neither surface writes that path, no ownership rule between them is necessary. Rejected:
  - Consented `setup` action in the TUI plugin (the accepted plan until [2026-11-09 Mon]): `plugin update` and reinstall make a new install directory and keep the old one, so a link into the managed checkout silently points at old files after each update; `plugin uninstall` has no hook, so the link outlives the plugin (Herdr 0.9.5 `plugins.mdx`).
  - Self-install from a herdr-app mod: herdr-app 0.1.10 has no package, install hook or update channel; a shared mod is a folder that a person or agent copies into `mods/`, so the skill cannot come with it, and a mod that clones the repository is a second installer for the same path.
  - Installer scripts in the herdr-orch skill: `herdr plugin link` needs a full dotagents checkout, because the plugin is outside `skills/`; the desktop layout also needs the `orch-spaces`, `org-tasks` and `system` mods, which herdr-orch does not own; a script would duplicate the occupant rules of `checkHerdrAppLeaves` in the parent `agents.nix`; no user installs without Home Manager today.
- Skill-first resolution in the TUI plugins :: both surfaces run the same `oh` and `ot` when the home skill exists; the checkout-relative fallback keeps a GitHub-only install working. Same order as `resolveTraitsBinary`, without an environment override until one is needed.
- Install instructions stay in the surface READMEs :: the skill reference is a redirect, so the procedures have one home each. Herdr-app's own `AGENTS.md` already tells an agent how to add a mod folder from GitHub.
- Minimum Herdr version :: the plugin manifest requires 0.9.5 for the sidebar tree hooks; the bundled `oh` preflight keeps its own 0.9.1 floor in `contract.md`. Doctor checks the manifest floor.
- No `[[build]]` entries :: nothing needs building, and build commands get no plugin runtime context. Babashka is a documented prerequisite that doctor checks.
- Traits fallback keeps the live path's priority :: env override, then the canonical home path, then extension-file-relative, per the parent task constraint.

** Risks

- The checkout-relative fallback of a GitHub-installed plugin depends on Herdr keeping the whole-repository clone for a subdir install. The Herdr 0.9.5 docs do not state this; it was measured once, on Herdr 0.8.0. Accepted: the error names each path tried, and doctor reports the resolved `oh`.
- A home skill and a plugin checkout at different revisions run different code in the two surfaces. Accepted: doctor reports it as a version-skew warning.

* Implementation

- Traits :: isolated launcher fixtures cover precedence and missing paths; real and symlink launcher expansion and installed-Pi RPC cases pass with a clean home.
- Plugins :: `plugin_oh` in `herdr/plugins/herdr-orch/lib.sh` and `resolve-ot` in `herdr/plugins/org-tasks/src/org_tasks_host.clj` try the home skill, then the checkout. The org-tasks host resolves `ot` only for `serve` and `select-pane`, so `toggle` and `ensure` still work without `ot`.
- Doctor :: `herdr/plugins/herdr-orch/doctor.sh` (Bash and awk, no `sort -V`), opened by the `doctor` action through `open-pane.sh`. A missing home skill or Pi traits extension is a `WARN`, because the plugin itself still works.
- Mods :: when `exec` cannot start the executable, the mod reads the file with `readTextFile`; only a `null` result (absent file) gives the not-installed state. A present but non-executable file, or a failed read, keeps the generic failure message. This is narrower than the plan task's "not executable" wording: a present file that cannot run is reported as a failure, not as an absent install.
