- Paid API-key fallback without explicit consent, automatic model upgrades, or changes to global Pi startup defaults.

** Decisions
- Chose a focused repository-owned integration in the existing Pi Herdr extension, reusing native Pi authentication/provider APIs and the Babashka routing policy.
  - Rejected adapting ~pi-multi-account~ wholesale: its quality-band heuristics differ from configured weight aliases; its wider recovery/proxy surface is outside this change.
  - Rejected extending ~pi-multi-claude~ as the account foundation: its shared ~anthropic~ credential replacement cannot provide independent concurrent selections.
- Each account has a stable non-secret identity, separate from its base provider and quota adapter. Preserve the existing base-provider credential as the default account. Register additional accounts as distinct Pi providers so the selected model identifies the credential without global credential swapping.
- The owner selected ~<provider>-<N>~ for alternate account keys and display names, with positive integers without leading zeros: ~anthropic-1~, ~anthropic-2~. The base ~anthropic~ key remains the default. Bare ~/oh-account add~ registers the lowest unused positive number; an explicit number is also supported. Only adapted base providers are recognised; adding another provider requires its authentication/quota adaptation, not a new naming scheme. No separate account database or display-alias layer is required. The authorised one-off credential-key migration preserves the existing OAuth credential without reauthentication.
- Keep canonical models and weight aliases account-independent. Expand candidates to model/account pairs at routing time; retain exact quota scopes, reserve thresholds, harness filters and deterministic order. Preserve the base account first for otherwise equal ties.
- Extend the existing collector with explicit account lookup and account-isolated cache keys. Its output retains ~providers~ rows with unique ~localProvider~ identities, plus explicit base-provider/account identity. Native non-Pi harnesses retain their existing single-account credential contexts.
- One pure Babashka selection policy serves launch routing and primary recovery. Add a bounded machine-readable routing operation usable without Herdr; it accepts the selected tier or direct model, current route, eligible registered model/account inventory and attempted-route exclusions. Validate request shape; return only non-secret routing evidence. This operation grants no terminal control and does not weaken existing launch gates.
- Pi owns account login, refresh and removal through supported credential transactions. Account providers retain native Anthropic OAuth/request shaping and model metadata; subscription aliases must not inherit ambient API-key authentication. The first implementation task proves this with the installed Pi runtime before downstream integration.
- Launches persist and forward the concrete account/model. Fork and measurement loaders must register the same account providers before model resolution. Same-kind inherited concrete selections do not reroute. Native Claude token sharing is not assumed safe.
- Primary tier intent is session metadata, restored on resume and cleared by direct selection. Recovery-generated model changes do not clear it. A child with copied session history must remain in pinned-child mode.
- Recovery first tries same-model accounts, then the selected alias's ranked candidates, including other providers. Direct selections have no cross-model fallback. Filter candidates by registered availability and ability to preserve the requested reasoning level.
- Attribute quota failures to the request's captured account/model. At the final actionable Pi lifecycle boundary, attempt each candidate pair once in a finite chain; use Pi continuation rather than reconstructing tool calls. Cancellation, new input and externally reported model/account changes invalidate automatic continuation. The owner accepts that pending native selection requests and silent same-target selections may not invalidate recovery; the public API reports neither reliably. Explicit abort remains the reliable cancellation action. An already-pending native setter may still commit: retain a visible warning until it settles and report the actual selection after cancellation, per [[file:2026-pi-recovery-selection-limits.org]]. Do not lock controls, roll back selection or add startup auth checks. Report switches and terminal exhaustion. No timer waits for quota reset.

** Risks
- Alias authentication or request shaping may differ from the base provider. Gate dependent work on an installed-runtime fake-upstream OAuth/tool round-trip; return for design review if native reuse cannot satisfy it without a proxy or SDK change.
- Refresh/removal races can lose credentials. Exercise concurrent refresh, cancellation and removal with isolated auth stores; do not copy tokens into a second store.
- Actual refusals can disagree with cached quota. Keep failed routes excluded for the recovery chain; quota collection remains evidence, not a promise that inference will succeed.
- Simultaneous launches can choose the same account. Accepted: no reservation layer; revisit if measured contention justifies it.
- The controller must not replay completed tools, but cannot guarantee a model never independently requests the same action. Preserve the transcript and test controller behaviour, not an impossible model guarantee.
- Herdr quota parsing rejects duplicate ~localProvider~ values. Producer, parser, UI identity and fixtures must change coherently.
