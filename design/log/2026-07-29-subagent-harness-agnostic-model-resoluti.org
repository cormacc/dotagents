* Intent

Make a persona's declared =model:= take effect regardless of the resolved harness kind by translating canonical model IDs through per-harness lookup tables in the subagent CLI, replacing the interim pi-only kindless-model exception from [[plan:2026-07-27-subagent-per-persona-spawn-capability-re.org]]. Unlisted model IDs pass through unchanged so the ID set stays open.

* Summary

*Level:* production · *Tests:* thorough · *Docs:* inline + SKILL.md/contract.md

** Scope

*** In scope
- Canonical model-ID → per-harness-syntax lookup table externalised as EDN, applied to the resolved model at spawn time (frontmatter, `--model` flag, and same-kind parent inheritance all flow through it).
- Default table ships at `skills/herdr-subagents/subagents/roster.edn`; local overrides at `<git-root>/.agents/subagents/roster.edn` then `~/.agents/subagents/roster.edn` (project wins, mirroring persona resolution), merged per model-ID over the default.
- Path resolution is pinned per deployment mode: the default table resolves relative to the installed skill/launcher location (bare-subtree installs included), and the project override resolves under `ledger/assignment-root` (the existing `SUBAGENT_ASSIGNMENT_ROOT` relocation semantics), never a fresh cwd/git probe.
- The EDN table is a first-class skill artifact: SKILL.md § Manual fallback directs an agent without the `subagent` CLI to read the table chain and translate models by hand.
- The harness set is open: roster.edn carries a `:harnesses` section declaring how each kind receives a model (flag spelling), and model rows may carry columns for any kind. An override file can add a new harness + model columns to evaluate a new tool with no skill update, provided herdr itself supports the kind.
- Retire the pi-only exception in `resolve-model`: a frontmatter model is honoured for any resolved kind via translation.
- Retire the paired kind+model drop rule: a definition model survives a kind override instead of being dropped — translation makes it portable, so the drop is legacy noise.
- Extend `model-args` so codex spawns receive a model argument (currently only `pi`/`claude` do); verify the codex CLI flag first.
- Verify the extrapolated claude/codex column values against the actual CLIs before implementation (task body table is UI-extrapolated).
- Update [[proj:skills/herdr-subagents/SKILL.md]] § Roster and routing and [[proj:skills/herdr-subagents/scripts/docs/contract.md]] to document canonical IDs, the table, and the pass-through fallback.
- Migrate the eight roster definitions in [[proj:subagents/]] from pi `provider/model` syntax to canonical IDs.

*** Out of scope
- Cross-kind parent-model inheritance (a child resolving to a different kind than its parent still inherits no model).
- Reverse mapping harness-native model strings back to canonical IDs.
- Any change to spawn gating, depth bounds, ledger, envelope, or label grammar.
- Harness entries beyond pi/claude/codex in the *default* roster.edn (overrides own experimental kinds).
- Teaching herdr new agent kinds — `:harnesses` only tells the subagent CLI how to pass a model to a kind herdr already recognises; kind validation stays herdr's.

** Decisions
- Canonical table is external EDN with a local-override chain :: `skills/herdr-subagents/subagents/roster.edn` (default) ← `~/.agents/subagents/roster.edn` ← `<git-root>/.agents/subagents/roster.edn` (project wins, mirroring persona-definition precedence). Data inside the skill tree keeps the table readable by the manual-fallback path (agent driving the herdr CLI directly, no `subagent` script), and overrides absorb model churn without touching the skill repo. Revised from the initial in-code `def` after review.
  Rejected:
  - `def` in `core.clj`: invisible to the manual-fallback path and forces a skill-repo edit for every model change.
  - Per-persona frontmatter columns (`model-claude:` …): duplicates the table across eight personas and drifts.
- EDN shape is `{:harnesses {:pi {:model-flag "--model"} …} :models {"<canonical-id>" {:pi "…" :claude "…" :codex "…"}}}` :: `:harnesses` makes the kind set open — model-flag knowledge moves from `core.clj` into data, so overrides can onboard new tools; model-row keys are arbitrary kind keywords resolved against it.
  Rejected:
  - Hardcoded kind set in `model-args`: every new harness needs a skill push, defeating the portability goal.
  - Per-harness arg templates (`--model=<m>`, positional forms): YAGNI — a single `:model-flag` producing `[flag model]` covers pi/claude/codex; extend the schema when a real harness needs more.
- Override merge is row-level (per model ID, and per harness ID in `:harnesses`), not deep :: a row you override is a row you own; partial per-kind deep-merge makes effective values hard to predict from any single file.
- Table config is loaded and schema-validated before any ledger or pane mutation :: fail-fast at the `model-args` boundary (`cli.clj:238`) would fire after ledger allocation and pane creation, which is not fail-fast at all. Validation covers parse errors *and* shape/type errors (schema allows sparse model rows and open keyword harness IDs); explicit user config must not silently no-op (same rationale as the `--retro` fail-fast precedent). A missing override file is not an error; a missing shipped default is fatal.
- Default table resolves from the installed skill/launcher location; project override from `ledger/assignment-root` :: two independent roots — a loader rooted at the assignment project cannot find a globally installed skill default, and one rooted at cwd/git ignores a relocated `SUBAGENT_ASSIGNMENT_ROOT`. Mirrors how persona lookup already resolves (`cli.clj:44-49`).
- Paired kind+model drop rule removed :: the drop existed only because a pi-syntax model was meaningless to another harness; canonical IDs + translation void that premise. `resolve-model` simplifies to requested > frontmatter model > same-kind parent inheritance > nil.
- Translation applied to the *resolved* model at the `model-args` boundary :: one choke point covers frontmatter, `--model` flag, and same-kind parent inheritance uniformly; `resolve-model` keeps choosing *which* declaration wins, translation decides *how it is spelled*.
- `gpt-*` → anthropic mappings on pi (and vice versa on codex) are deliberate tier-equivalence remaps, not identity claims :: a persona author picks a capability tier; each harness runs its best equivalent.

** Gotchas
- The claude `haiku` alias is undocumented (docs list `sonnet`/`opus`; local help adds `fable`) — the haiku-tier rows use the full model name `claude-haiku-4-5` instead.
- Bare-subtree installs must ship the whole skill directory, not just `scripts/`: the default table lives at `subagents/roster.edn` in the skill tree, and the launcher resolves it from the installed skill location (the bare-subtree test fixture initially copied only `scripts/`).
- `cli_test.clj`'s default fake-env `.agents/subagents/` is a symlink into the live tracked `subagents/` dir — tests writing roster overrides there must pass an explicit personas map or they mutate the repo.
- Babashka's `(System/getProperty "user.home")` ignores a subprocess `$HOME` override — tests exercising the home-override leg must inject the home path rather than rely on env isolation.
- Subagent result publish is once-only: an envelope rejected by `collect` validation (e.g. relative artifact paths) cannot be repaired by re-prompting the child; the parent must validate identity manually against the ledger and capture the artifacts itself.

** Risks
- The override chain reads user-editable files at spawn time; a stale or experimental override can silently redirect every child's model. Accepted: row-level replace + pre-mutation fail-fast keep effective values predictable, and `--print-prompt` exposes both the canonical and the effective translated model.
