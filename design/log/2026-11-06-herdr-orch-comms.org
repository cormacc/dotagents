* Intent
Decide, with measured evidence, whether herdr-orch's result-file plus advisory-push mechanism is sufficient for inter-agent communication, or whether to augment it with a durable mailbox behind ~oh~. Record a keep/adopt/augment decision. Implementing a chosen augmentation is a follow-on task, not this one.

* Summary
*Level:* prototype · *Tests:* smoke · *Docs:* record only

Decision: augment delivery, keep the pipe. The file pipe (immutable result items plus ~collect --any --wait~ polling at 1000 ms) costs under 1 s per item at 1-6 children and is the smallest term in a real round. The measured delay lives in delivery into the parent model and in model turns: a Pi parent on herdr-app is never pushed (hc cannot observe its session), the terminal push blocks the child's ~publish~ for the parent's whole settle wait, and real-ledger publish-to-capture has median 11 s and p75 39 s. A Pi extension that watches the result directory and steers each item once removes the delivery term on both hosts; the follow-on task [[task:486df916-c1f0-4ab8-ab34-775c1d92d503]] implements it and makes the push non-blocking. No mailbox store, broker, MCP server or catalogue package is adopted.

Measured chain for one round (medians): child decision from last evidence to ~publish~ 9.7 s (153 real sessions); publish to item link under 0.2 s; detection by polling 0.5-0.7 s at 1000 ms, 0.15-0.2 s at 250 ms; presentation into an idle Pi parent 0.4 s by push, under 60 ms by watcher; into a busy parent, the remainder of its current tool call under either mechanism; then the parent's own decision to collect.

** Decisions
- Augment delivery, keep the pipe :: Chosen on the measurements above. Rejected: keep as-is (hc parents never pushed, child blocked up to ~--notify-timeout~); a separate ~oh mail~ store with cursors (the result directory already is the store and the item path is the dedup key); a 250 ms poll (saves about 0.4 s for twice the ~agent list~ traffic); a socket broker (agent-comms shows the cost: port ownership, coordinator election, identity keys, in-memory state that dies with the last peer); MCP (a drain without wake-up; at most an optional read interface); any catalogue package (all Pi-only except agent-comms; pi-messenger imports orchestration; patterns from pi-session-mail are reimplemented, not vendored).
- Delivery augmentation, the shape the follow-on implements :: In ~pi/extensions/herdr-orch/~, active only for an orchestrator session (~HERDR_ENV=1~ or ~HC_TERMINAL_ID~ with a resolvable assignment root): at ~session_start~ load the delivered set from ~<session-file>.herdr-orch-delivered.json~, scan ~<assignment-root>/.tmp/herdr-orch/~, start ~fs.watch~ and a 5 s poll fallback. A new item whose envelope parses is added to the set, persisted, then delivered with ~pi.sendMessage({customType: "herdr-orch-item"}, {deliverAs: "steer", triggerTurn: true})~; the text carries only ~CHILD~, ~TASK~, ~STATUS~, the first ~SUMMARY~ line, the ~oh task collect <task>~ instruction and the advisory line. Items whose ledger entry names another parent session are not delivered. In ~cli.clj~, ~push-decision~ skips the push for a parent of kind ~pi~ (the watcher owns delivery; a duplicate push queued behind the steer turn cost 3 s in the bench); for other kinds the settle wait and prompt run detached from ~publish~, which returns ~{:push "detached"}~ at once, and the outcome is written to ~<item>.push.json~ for ~collect~ to report. ~contract.md~ 'Parent push' changes accordingly; item format, sealing and ~collect~ do not.
- Measure first, prototype on evidence :: The bench and baseline existed before any delivery code; the 250 ms poll variant was the mandatory comparator so an ABAB comparison existed even for a keep decision. Rejected: prototype first (biases toward augment); package first (Pi-only packages leave the CLI path and non-Pi harnesses unserved).
- Child simulation: stub ~pi~ on ~PATH~ :: ~oh task start~ runs unchanged; the ~pi~ it launches is a compiled stub first on the disposable server's ~PATH~, and the parent pane runs the same stub, which forks the bench script so ~oh~ has a recognised caller. A child's publication runs with its ledger identity injected as environment. For the presentation bench the parent is a real Pi (~anthropic-1/claude-haiku-4-5~) with a bench extension that logs events and forces a one-word system prompt.
- Desktop gap folded in :: Task f2365984 became the hc evidence. Classification: session observation by design; ~oh agent get~ on a herdr-app Pi pane returns ~agent_session null~, so ~push-decision~ always yields ~session-mismatch~. The org-execute rule to collect explicitly is the correct response to a mechanism that cannot push; the fix is in delivery, not guidance.

** Gotchas
- The push outcome (~sent~, ~skipped~, ~prompt-failed~) is returned only on the publishing child's stdout and never persisted, so delivery cannot be audited from the ledger. The follow-on adds ~<item>.push.json~.
- ~ot create --parent~ on a task that already carries ~#+IMPORT:~ inserts into ~TASKS.org~, and ~ot move~ cannot cross files. Create and order plan tasks under the parent before ~ot record create~, which migrates them.
- A disposable Herdr server's XDG tree must sit under a short path such as ~/tmp/cb-<token>~: under the repository ~.tmp/~ the socket path exceeds the macOS ~sun_path~ limit.
- ~oh~ calls from a pane fail with ~agent_not_found~ until Herdr classifies the pane (about 0.6 s after ~exec pi~); the second concurrent write-enabled child needs the work root to be a git repository.
- ~collect --any~ without ~--wait~ reports reason ~timeout~, not ~no-candidates~, when nothing is unconsumed (observed, not investigated).
- ~pi -p~ with a steer at startup prints "Agent is already processing"; harmless interactively, noisy in print mode.

** Detection bench (2026-11-06)
macOS, Herdr 0.9.5, stub parent and stub children (no model), ~bb bench/bench-driver.bb bench/detect-parent.clj <N> BENCH_ROUNDS=5~. The collector (~oh task collect --any --wait~) is already polling when each ~WAITING~ item is published; latency is item mtime to collector return. Five ABAB rounds per arm, one sample per child per round, medians per round in [[file:2026-11-06-herdr-orch-comms/detection-results.txt]].

| N | ~ORCH_POLL_INTERVAL_MS~ 1000 median / p90 | 250 median / p90 | ~herdr~ calls per capture (1000 / 250) |
|---+---+---+---|
| 1 | 552 / 625 ms | 149 / 234 ms | 5 / 10 |
| 3 | 481 / 741 ms | 214 / 276 ms | 5 / 11 |
| 6 | 695 / 967 ms | 180 / 308 ms | 5 / 11 |

Every per-round median at 1000 ms lies between 200 and 860 ms; at 250 ms between 37 and 276 ms. Concurrency 1 to 6 has no material effect. Each poll tick is one ~agent list~ subprocess of roughly 100-200 ms, which is the floor at 250 ms. Restart recovery: with items published while no collector ran, a fresh process captured each item exactly once at every N, and the following ~collect --any~ captured nothing (its reason is reported as ~timeout~, not ~no-candidates~; noted, not investigated). The push was skipped on every sample (~session-mismatch~, stub parent), so every sample is the pure poll path and the lost-notification case holds by construction. Conclusion: the file pipe plus polling costs under one second; a perceived lag of seconds or more is not the pipe. Halving the interval saves about 0.4 s for twice the subprocess rate.

** Presentation bench (2026-11-07)
macOS, Herdr 0.9.5, a real Pi parent (~anthropic-1/claude-haiku-4-5~, extension [[file:2026-11-06-herdr-orch-comms/presentation/]] ~present-ext.ts~ in [[file:2026-11-06-herdr-orch-comms/prototype/]]) with stub children; ~bb bench/bench-driver.bb bench/present-parent.clj 0 BENCH_REAL_PI=1 BENCH_ROUNDS=4 BENCH_SLEEP=20~. Latency is item mtime to the ~message_end~ event that puts the item text in the parent's context. "Busy" means a 20 s ~bash sleep~ tool call in flight at publish time. Four ABAB rounds; [[file:2026-11-06-herdr-orch-comms/presentation-results.txt]], raw samples and events under [[file:2026-11-06-herdr-orch-comms/presentation/]].

| arm | mechanism | latency median (min-max) | child's ~publish~ call |
|---+---+---+---|
| push-idle | existing advisory ~agent prompt~ on a terminal item | 409 ms (385-413) | 491 ms |
| watch-idle | extension ~fs.watch~ on the result dir + ~pi.sendMessage(deliverAs: "steer", triggerTurn: true)~ | 7 ms (7-53) | 102 ms |
| push-busy | existing push; publish waits for the parent to settle | 24.0 s (23.7-25.1) | 24.1 s |
| watch-busy | watcher + steer | 21.7 s (21.7-22.0) | 128 ms |

Findings. Into an idle parent both paths are sub-second; the watcher is two orders faster but both are negligible against turn time. Into a busy parent neither path can interrupt a running tool call: steer lands after the tool returns (20 s sleep plus the time already elapsed), and the push lands about 2.3 s later still because it waits for the parent to settle, reply, and then accept typed input. The material difference is on the child: the existing push blocks the child's ~publish~ for the whole settle wait (24 s here, bounded only by ~--notify-timeout~), while the watcher returns in about 120 ms. The push was ~sent~ on every sample because the TUI observes the Pi session; on hc it is skipped by design.

Child-side decision latency, read from 153 real child Pi session files that contain a ~task publish~ tool call ([[file:2026-11-06-herdr-orch-comms/child-decision.txt]], ~bench/child-decision.clj~): gap from the child's last tool result to the assistant message that calls ~publish~ has median 9.7 s, p75 15.9 s. That is one model turn of thinking and composing the envelope, and it precedes every number above.

** Desktop (hc) delivery classification (2026-11-07)
Classification: session observation, by design. Evidence from this live herdr-app session rather than a disposable reproduction: the planner round's ledger entry records ~parent-pane t3~ and a ~parent-session~ path; ~oh agent get t3~ at the same time returns ~agent pi, agent_status done, agent_session null~; ~push-decision~ in ~skills/herdr-orch/scripts/src/herdr_orch/cli.clj~ tests session equality first, so the outcome is ~{"push":"skipped","reason":"session-mismatch"}~, which is what that round's own ~COMPLETE~ publication reported. On hc a Pi parent is therefore never pushed for any child; delivery depends entirely on the parent choosing to collect. The push outcome is not persisted on the ledger entry, so it cannot be audited after the fact; the contract already states the limitation ('Parent push'). No workflow rule is missing: the org-execute guidance to collect explicitly is the correct response to a mechanism that cannot push, and the fix belongs in delivery, not in guidance.

Findings. The prototype delivers into an idle parent in under 60 ms and returns the child's ~publish~ in about 100 ms in every parent state; the busy-arm latency is the remainder of the parent's tool call, as before. Double delivery costs a turn: with both mechanisms active the typed push queued behind the prototype's steer turn, which is why push-idle rose from 0.4 s to about 3 s; a shipped version drops the push for a parent that runs the watcher. Dedup: 16 items, 16 deliveries, no duplicate path. Reload: resuming the same session file with the 16 items present and a 17th control item added delivered only the control (~known: 16~ at start, one ~proto-fire~, set persisted at 17).
