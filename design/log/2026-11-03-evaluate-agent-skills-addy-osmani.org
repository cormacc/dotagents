** Priority recommendations
*** 1. Quality-gate setup workflow
Base this on [[upstream:skills/constraint-driven-development/SKILL.md]]. It turns preferences into a checkable contract: inspect existing tooling, agree on dimensions and thresholds, assign each check to an affordable lifecycle stage, measure a baseline, and track exceptions with an owner and expiry.

Our worker and review instructions already require evidence and protect tests. The useful addition is project-level setup and maintenance of those checks, including detecting weakened thresholds, removed assertions, skipped tests and silenced checkers. This is a workflow skill, not a trait: it needs discovery, user decisions, configuration changes and deliberate violation tests.

Adaptation: use the project's existing contract and check entry points; do not require a new =CONSTRAINTS.md= or duplicate =AGENTS.md=/=CLAUDE.md= instructions. Do not install tools until authorised. Treat coverage percentages and runtime budgets as negotiated values, not universal standards. Distinguish legitimate assertion replacement from a weakened test; our worker already accounts for migrated coverage by test name. Treat the floor guard as a heuristic to evaluate, not an automatic ban on every suppression or =TODO=.

Validation before adoption: exercise each claimed gate on a clean input, a known violation and a scanner failure; test below-threshold findings where relevant. Include staged, unstaged and untracked changes. Demonstrate that a threshold change is detected without rejecting a legitimate test translation. Retain the current checks if a proposed replacement does not improve them.

*** 2. Threat-model-led security workflow
Adapt [[upstream:skills/security-and-hardening/SKILL.md]] and [[upstream:agents/security-auditor.md]]. The strongest procedure is to map assets and trust boundaries, apply STRIDE, derive abuse cases, then verify concrete exploit paths and mitigations. Dependency installation scripts, derived destructive paths, privacy retention, and LLM/tool boundaries are relevant beyond web applications.

Our [[file:../../skills/code-review/SKILL.md]] already checks security defects. The addition is a deliberate threat model and domain-specific evidence checklist, not a second generic review. Begin with =base-analyst= for an explicitly scoped system audit, or =reviewer= for a diff. A thin security persona extending =base-analyst= becomes justified if this workflow gets repeated use; retain read-only scope, local severity rules and explicit unknowns. Do not give it default authority to scan live targets, install dependencies or change controls.

Adaptation: load web/auth/privacy references only when relevant. Verify implementation guidance against the actual stack and current authoritative sources. Do not copy blanket environment-variable storage guidance, numerical defaults or legal-compliance claims as guarantees. A successful dependency audit is evidence about known advisories, not proof that a package is safe.

Validation before adoption: compare against ordinary review on a bounded fixture with an exploitable trust-boundary defect and a safe control. Require a demonstrated input-to-sink path, no invented issue on the control, no writes, and explicit limits on untested surfaces.

*** 3. Measurement-led performance workflow
Adapt [[upstream:skills/performance-optimization/SKILL.md]] and the evidence contract in [[upstream:agents/web-performance-auditor.md]]. Preserve the sequence: baseline, locate the bottleneck, change one mechanism, remeasure, keep or revert, then guard against regression. Retain an attempt ledger, including rejected optimisations, in the existing change-record rather than requiring =PERF.md=.

The persona's useful distinction is source inspection versus measurement: static findings are potential impact; scorecards remain unmeasured without artefacts; lab, field and trace evidence stay separate. This is more specific than our generic evidence bar. It does not justify a global measurement trait, because [[file:../../home/AGENTS.md]] already governs performance comparison.

Adaptation: make the main workflow applicable to CLI, backend and agent tooling as well as web applications. Preserve our alternating ABAB rounds and per-round medians; do not replace them with one before/after pair. Web-only references and an optional web-performance persona can sit below that workflow. Our [[file:../../skills/herdr-orch/subagents/visual-tester.md]] checks appearance and interactions; it should not acquire an implied performance-certification role. Supplied reports are a valid starting point; do not assume our browser tools expose upstream's tracing or Lighthouse tools.

Validation before adoption: use a known bottleneck and a neutral change. Require the workflow to distinguish both, preserve correctness, reject unsupported metric claims, and report unavailable tools honestly. Do not inherit generic bundle, latency or Lighthouse budgets as project requirements.

*** 4. Two small orchestration recipes, not a new SDLC skill
From [[upstream:skills/test-driven-development/SKILL.md]] and =agents/test-engineer.md=, retain independent regression-test authorship when it removes implementation bias: give a worker the bug and contract without the proposed fix; verify the test fails for the intended reason on an immutable baseline; only then assign the fix. Confirm the repaired behaviour and relevant suite. Ordinary fixes remain inline. Our [[file:../../skills/herdr-orch/subagents/worker.md]] already requires pre-fix failure evidence, so another general testing trait adds little.

From [[upstream:skills/doubt-driven-development/SKILL.md]], retain a bounded decision check: provide an independent reviewer with the artefact, contract and necessary evidence, omit the author's persuasive narrative, then classify each finding as a contract misunderstanding, actionable defect, accepted trade-off or noise. Put this in [[file:../../skills/herdr-orch/references/workflow-recipes.md]] if adopted. Do not withhold the proposition when the assignment is explicitly to verify that proposition.

Do not adopt review of every non-trivial decision or mandatory cross-model questions each cycle. Our [[file:../../skills/herdr-orch/SKILL.md]] section 'Executor tier and advisor strategy' records why routine worker consultation was retired; the advisor remains opt-in for stuck or materially ambiguous decisions. There is no local evidence here to reverse that policy.

*** 5. Operational readiness when a deployment workflow needs it
Combine relevant parts of [[upstream:skills/observability-and-instrumentation/SKILL.md]] and [[upstream:skills/shipping-and-launch/SKILL.md]] into a later, explicitly requested release-readiness workflow. Useful elements are operational questions before telemetry, entry-point plus correlation attribution, bounded metric labels, test-fired alerts, staged rollout decisions, and a verified rollback path.

This must produce a readiness assessment before any deployment authority is granted. Select reviewers by actual risk and surface; do not copy a mandatory panel for every launch. Choose monitoring windows and thresholds from the service, not upstream's example percentages. Telemetry is not a universal dependency for local scripts or throwaway work. Defer a separate observability skill until instrumentation itself is a recurring assignment.

** Adoption and evidence limits
- Source: [[https://skills.addy.ie]] links to [[https://github.com/addyosmani/agent-skills]]. The checked-out revision contains 25 skills and four personas. The landing page says 24 skills and a four-person launch panel; [[upstream:.claude/commands/ship.md]] actually uses three reviewers, and the performance persona explicitly excludes itself from that panel. Its plugin evaluations compare enabled and disabled arms and report model/CLI-specific limitations. These are useful evaluation patterns, not evidence that the catalogue will improve our agents. This evaluation did not reproduce those results.
- Adapt trigger tests with positive prompts and adjacent negative-owner prompts; distinguish skill invocation from improved output. Reuse our [[file:../../skills/skill-creator/SKILL.md]] and trait-probing machinery instead of importing another runner. Do not treat lexical routing scores as measured harness triggering.
- [[upstream:README.md]] documents that a per-skill installation omits repository-level =references/=. Any adaptation must move needed references inside its own skill or link to an established local owner, rather than retain broken =../../references/= paths.
- [[upstream:LICENSE]] is MIT. Preserve the copyright and permission notice with copied or substantially adapted material, record the exact source revision and retained parts, and classify it as locally adapted rather than silently vendored.
