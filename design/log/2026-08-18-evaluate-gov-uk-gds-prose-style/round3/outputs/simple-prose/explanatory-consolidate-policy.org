* Intent
Make ~ot~ the sole owner of the policy logic that is duplicated between the pi tasks overlay (TypeScript) and the standalone TUI (Clojure). Both UIs become thin clients that send intent (direction / anchor+relation) and render the result.

* Summary
*Level:* production · *Tests:* thorough · *Docs:* boundary + README + ot-cli

** Scope
*** In scope
- (1) Status cycle order
  - add ~ot status --cycle forward|back~
  - remove the order constant from both UIs
- (2) Create placement
  - add ~ot create --relative-to <id> --as sibling|child~
  - ~ot~ derives parent/after/local/source from the anchor
  - remove the placement maths from both UIs
- (3) Linked-issue URL resolution
  - the overlay consumes ~ot list~'s resolved ~linkedIssues~ (rawToken/label/url)
  - it no longer re-resolves via the TS ~getLinkedIssues~

*** Out of scope
- New keybindings (the key map is unchanged)
- Consolidating editor/Emacs launch (different runtimes, so it stays as-is)
- Browser/URL opening (OS launch, not domain logic)

** Acceptance
- [ ] ISC-1: ~ot status <id> --cycle forward|back~ returns the resolved transition, and the order lives in ~lifecycle/status-cycle~
- [ ] ISC-2: ~ot create --relative-to <id> --as sibling~ inserts after the anchor at its level, ~--as child~ nests under it, and both inherit local/source
- [ ] ISC-3: ~ot create --relative-to~ with no ~--as~ defaults to sibling
- [ ] ISC-4: The TUI and pi overlay no longer encode the status cycle order or the create-placement maths
- [ ] ISC-5: The pi overlay renders and opens linked issues from ~ot list~'s wire data, not the TS resolver
- [ ] ISC-6: The boundary, README, and ot-cli docs reflect the new ownership
- [ ] ISC-A-1: Must not change the selected-task JSON schema or add new keybindings

** Decisions
- Chose to put the cycle order in ~lifecycle/status-cycle~ (not ~commands~) :: it sits beside the rest of the lifecycle semantics, and ~ot status --cycle~ reuses it
- Chose ~--relative-to/--as~ over passing resolved parent/after from the UIs :: anchor + relation is the real intent. ~ot~ already parses the anchor, so it can derive placement (and the local/source routing) in one place
- Chose to pass only ~--after~ for siblings (not ~--parent~ + ~--after~) :: ~insert-task-into-file~ treats a set ~parent-id~ as "make it a child" (level = inc parent level). A sibling must derive its level from the anchor via ~--after~ alone. This also fixes a latent bug in the prior TUI ~create-opts~, which set both for nested siblings
- Chose to delete the overlay's in-process status fallback (~applyStatusTransition~ + ~persistChange~/~save~) :: it duplicated the lifecycle and serialization that ~ot~ owns, and it was dead in the live pi path
