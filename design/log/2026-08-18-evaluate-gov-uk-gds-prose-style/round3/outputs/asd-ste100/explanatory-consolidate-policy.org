* Intent
Remove the policy logic duplicated between the pi tasks overlay (TypeScript)
and the standalone TUI (Clojure). ~ot~ becomes the sole owner. Both UIs
become thin clients that send intent (direction, anchor plus relation) and
render the result.

* Summary
*Level:* production · *Tests:* thorough · *Docs:* boundary + README + ot-cli

** Scope
*** In scope
- (1) Status cycle order: add ~ot status --cycle forward|back~. Remove the
  order constant from both UIs.
- (2) Create placement: add ~ot create --relative-to <id> --as sibling|child~.
  ~ot~ derives parent/after/local/source from the anchor. Remove the
  placement maths from both UIs.
- (3) Linked-issue URL resolution: the overlay consumes ~ot list~'s resolved
  ~linkedIssues~ (rawToken/label/url). It does not re-resolve them via the TS
  ~getLinkedIssues~.

*** Out of scope
- New keybindings. The key map is unchanged.
- Consolidating the editor and Emacs launch (different runtimes. Left
  as-is).
- Opening a browser or URL (OS launch, not domain logic).

** Acceptance
- [ ] ISC-1: ~ot status <id> --cycle forward|back~ returns the resolved
  transition. The order lives in ~lifecycle/status-cycle~.
- [ ] ISC-2: ~ot create --relative-to <id> --as sibling~ inserts after the
  anchor at its level. ~--as child~ nests under it. Both inherit
  local/source.
- [ ] ISC-3: ~ot create --relative-to~ with no ~--as~ defaults to sibling.
- [ ] ISC-4: The TUI and pi overlay no longer encode the status cycle order
  or create-placement maths.
- [ ] ISC-5: The pi overlay renders and opens linked issues from ~ot list~'s
  wire data, not from the TS resolver.
- [ ] ISC-6: Boundary, README, and ot-cli docs reflect the new ownership.
- [ ] ISC-A-1: Must not: change the selected-task JSON schema or add new
  keybindings.

** Decisions
- Chose to put the cycle order in ~lifecycle/status-cycle~ (not ~commands~) ::
  It sits beside the rest of the lifecycle semantics. ~ot status --cycle~
  reuses it.
- Chose ~--relative-to~ and ~--as~ over passing resolved parent/after from
  the UIs :: The anchor plus relation is the real intent. ~ot~ already parses
  the anchor. It can derive the placement (and the local/source routing) in
  one place.
- Chose to pass only ~--after~ for siblings (not ~--parent~ plus ~--after~) ::
  ~insert-task-into-file~ treats a set ~parent-id~ as "make it a child"
  (level = inc parent level). A sibling must derive its level from the anchor
  via ~--after~ alone. This also fixes a latent bug in the prior TUI
  ~create-opts~, which set both flags for nested siblings.
- Chose to delete the overlay's in-process status fallback
  (~applyStatusTransition~ plus ~persistChange~/~save~) :: It duplicated the
  lifecycle and serialization that ~ot~ owns. It was dead in the live pi
  path.
