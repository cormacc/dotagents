* Intent
Answer "what's the selected task, and what's its plan?" with one cheap `ot`
call, instead of several raw file reads. Also stop the agent-facing surface
(both the `ot show` output and the extension's registered tools) from
carrying context the agent never uses.

* Summary
Level: production. Tests: thorough. Docs: README, skill and contract.

** Scope
*** In scope
- Strip `sourceContent` and `effectiveSourceContent` from `ot show` and
  `ot selected` JSON.
- Enrich `ot show` to the documented one-shot resume shape (ancestors and a
  record metadata block).
- Rewrite the `org-tasks` skill resume path to lead with
  `ot show selected --format json`.
- Remove the three agent-facing pi tool registrations (`tasks_insert_task`,
  `org_read_section` and `tasks_scan_summaries`), and keep the JS
  `insertTaskIntoFile` primitive.
- Reconcile the `show` and `selected` schema in `scripts/docs/contract.md`
  with the shipped shape.
*** Out of scope
- Changing `ot list` (already content-deduplicated through
  `result.sources`) or the extension's overlay and widget data path.
- Tracker-specific (`jira`) behaviour, beyond confirming its JS import still
  resolves.
- The tree-sitter org-extension extraction (`f361c429`) itself, except for
  its claim on `org_read_section`.
- Backfilling richer `ot show` data into the `ot status` or `ot create`
  payloads.

** Decisions
- Drop embedded source content from `ot show` entirely, rather than
  deduplicating it into a `sources` map :: `ot show` has no internal
  consumer (the extension uses `otList`, and `jira` imports the JS
  function). Link templates and linked issues are already resolved into
  wire fields, so the raw content adds no value.
  Rejected: mirror `ot list`'s `sources` map. This would add a field that
  no `show` caller needs.
- Gate any raw-content escape hatch behind an opt-in `--include-content`
  flag, off by default :: this keeps a path open for a future consumer,
  without cost to the common case.
- #4: eliminate all three registered tools, and rely on
  `ot <cmd> --format json` through Bash, which the skill already documents
  :: this is the biggest persistent-context win (about 7KB of tool
  schema), for almost no added skill bloat, since the commands are already
  in the quick reference. It makes the CLI the single source of truth.
  Rejected:
  - Consolidate into one `tasks` passthrough tool. This still ships a
    shell-shaped schema, plus an indirection layer that re-parses
    arguments the CLI already parses, which is a net loss compared with
    Bash and `ot`.
  - Keep the tools as they are. This costs about 7KB of persistent tool
    schema, for wrappers the skill already covers.

** Shipped
- `ot show` and `ot selected` now omit raw source strings by default, with
  `--include-content` as the explicit escape hatch.
- `ot show` now returns `ancestors`, plus `record` metadata (`path`,
  top-level sections, `hasContext` and `hasOpenQuestions`) for change-record
  imports that resolve.
- `org-tasks` resume guidance now starts from `ot show selected --format
  json`, and uses `ot section` for the linked record's summary and context.
- The tasks extension no longer registers `tasks_insert_task`,
  `org_read_section` or `tasks_scan_summaries`. The README now points
  agents to `ot create`, `ot section` and `ot scan`.

** Gotchas
- `linkedIssues` still resolves without any raw content in the output,
  because `task->wire` computes it from the internal
  `:effective-source-content`, before the `include-content?` gate applies.
- `insertTaskIntoFile` remains the JS primitive for Jira and direct
  integrations. Only the agent-facing tool registration was removed.
- A selected task in an imported plan may not itself carry a `#+IMPORT:`.
  Record metadata is guaranteed only for tasks with an import-bearing
  ancestor in the loaded graph, so a top-level root with an import is the
  canonical resume path.
