* Intent
Improve Jira requirements and related Confluence exploration through the existing Atlassian MCP connection. Use Teamwork Graph for selective relationship discovery and native pi code mode for bounded orchestration, without replacing deterministic Jira actions with model-written scripts.

* Summary
*Level:* MVP | *Tests:* thorough | *Docs:* full

Jira planning supports conditional, one-hop Teamwork Graph discovery through the existing MCP connection. Portable instructions and tested native pi code-mode recipes keep source reads separate from compact display and deterministic Jira actions. The six ~jira_*~ contracts and configured endpoint are unchanged.

** Scope
*** In scope
- Jira-oriented requirements planning and related Confluence specifications/decisions, owned by [[proj:skills/org-jira/SKILL.md]].
- Detailed portable procedure and optional pi recipes in [[proj:skills/org-jira/references/atlassian-exploration.md]].
- Consistent MCP routing, unchanged site/token semantics and executable recipe tests.
*** Out of scope
- Direct Teamwork Graph API client, Forge application, ~twg~ CLI, new extension/tool, or new slash command.
- MCP endpoint/authentication migration or support for multiple server generations without a demonstrated requirement.
- Changes to existing ~jira_*~ input/output contracts, sandbox guards, task creation, or auto-transition behaviour.
- Graph relationship writes, Confluence writes, production write tests, raw remote-content caches, or organisation-specific data committed to this public repository.
- General-purpose agent research framework or speculative performance optimisation.

*** Anti-criteria

- [X] Must not: persist raw issue/page/graph bodies through ~store()~ or into task records.
- [X] Must not: claim reduced latency or token use without a controlled measurement.

** Decisions
- Use skill instructions plus tested code-mode recipes :: Native orchestration avoids another runtime layer while the existing ~jira_*~ tools retain deterministic validation, sandbox restrictions and task-write semantics.
  Rejected:
  - A combined graph-context tool: no stable missing abstraction demonstrated.
  - Replacing the Jira extension with scripts: returns safety-critical behaviour to model-authored code.
  - A direct graph API/CLI: adds an access surface without a verified capability gap.
- Keep exploration conditional and bounded :: The living reference owns the one-hop call budget and failure policy. Targeted reads remain available when graph/search access is unavailable.
- Keep the configured endpoint :: The implementation uses the tools exposed by the configured connection, not guessed names from a different published server catalogue.

* Validation
- Live read-only trial, 2026-11-02 :: Both selected sources read successfully. The Jira seed returned no relationships; the Confluence seed returned one parent page and a retention-window warning. Hydration and Rovo search succeeded. No relationship between the two seeds was inferred.
- Call accounting :: Four discovery calls (two context, one hydration, one search) plus eight source/resolution/filter reads, including the final two-source recipe run. No remote writes or automatic cursor traversal.
- Native code mode :: The four exact recipe blocks executed with sanitised fixtures in the active pi 1.4.0 VM; the selected-source block also executed against the approved live sources. A known-bad write was rejected. Model-free RPC startup loaded the Jira extension with empty stderr and ~jira~ registered.
- Coverage limit :: The selected issue is disposable test material and the selected page is onboarding guidance, not a product specification. The trial verifies retrieval and honest scope reporting, not completeness or correctness of a product requirements analysis.
- Privacy :: Fixtures contain synthetic IDs/URLs/bodies. A source sweep included tracked and new files, with the synthetic example host as a positive control; the queried live identifiers/hosts did not occur in the changed workflow/test files.
