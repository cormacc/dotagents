* Intent
Give orchestrators one explicit choice of child context: fresh named-persona delegation, fresh persona-less delegation, forked conversation, or isolated measurement. Keep normal delegation safe and inspectable, remove orchestration instructions from measurement subjects, and compose root-owned workflows from the resulting task interface.

* Summary
*Level:* production · *Tests:* thorough · *Docs:* full

The work is complete. ~oh task run|start --context fresh|fork|measurement~ gives an orchestrator one explicit choice of child context. Fresh is the default, and the persona is optional: a persona-less child receives the assignment, explicit traits and launcher guidance, but no role and no authority. "Spawn a subagent" selects fresh context and "fork a subagent" selects forked context. A Pi fork copies the caller's own persistent session and branches before the caller's current turn, so the child inherits only completed turns and its assignment is its only open request. A measurement runs a Pi subject headless under a detached supervisor with only the configured treatment, tools and literal assignment; a request-boundary audit covers four Pi APIs, and any other API fails closed. Root-owned workflows compose these modes with the existing task verbs. The guarded context-modes smoke passed on installed Pi 1.4.0 (see [[*Validation]]).

** Scope
*** In scope
- Unified context selection on ~oh task run/start~, optional persona, existing explicit traits, preview, provenance and lifecycle compatibility.
- Pi fork of the caller's completed turns, before the current turn that delegates; optional persona overlay; recorded named-persona inheritance.
- Pi-only headless measurement, optional Herdr monitor panes, explicit context configuration, execution evidence and supervisor-owned result publication. Measurement request-level audit coverage is exactly four Pi APIs: ~anthropic-messages~, ~openai-completions~, ~openai-responses~ and ~openai-codex-responses~ (user-approved boundary). Within those four APIs the owner permits declared provider model fallbacks, Codex's exact default instruction for an empty treatment, image-bearing tool results and the runtime's exact empty and image-only result placeholders, each only as independently derived (see [[*Measurement]]).
- Root-owned workflow recipe as the final phase, using existing task lifecycle verbs rather than a workflow engine.
- Living contracts listed by ~#+SPEC:~; CLI examples, skill routing and ~/oh~ usage guidance change with the implementation they describe.
*** Out of scope
- Claude/Codex fork or measurement parity; unsupported combinations fail explicitly.
- Measurement on any Pi API outside the four audited ones. Such a request fails closed before it is sent. This narrows measurement only; fresh delegation and forks are not restricted by API.
- Exact cloning of live Pi configuration, extension-forced parent prompts or ephemeral parent sessions.
- Nested workflow ownership, wider spawn permissions, arbitrary persona-file/inline-persona inputs, generic native-argument passthrough and a batch scheduler.
- A new operating-system sandbox, automatic answer-quality scoring, new model weights or changes to packaged persona defaults.

** Decisions
*** Context and routing
- CLI surface: ~--context fresh|fork|measurement~ on ~task run/start~, with an optional positional persona. ~fresh~ is the default; presence of a persona distinguishes normal persona delegation from persona-less delegation. ~fork~ permits an optional persona; ~measurement~ rejects one.
- Chose a unified task interface with separate interactive and headless execution paths. Rejected a separate measurement command because task identity, inspection and result capture should remain consistent. Rejected independent fork/bare/no-wrap flags because their combinations obscure context selection. Headless execution does not prohibit a monitor pane: execution semantics and visibility are separate choices.
- Use the same context resolver once per preview or launch invocation. Stable configuration follows the same rules; invocation-sensitive fork boundaries are recomputed, not frozen by an earlier preview. Preview reports the source session and boundary rule; the start envelope and ledger report the selected entry for that launch. Record mode, effective role/trait provenance, execution type and relevant snapshot/configuration hashes in the ledger and status. Existing records with no context metadata remain fresh interactive delegation.
- Persona-less fresh children receive the assignment, explicit traits and normal launcher guidance, but no synthetic role instructions. Reuse existing kind/model/effort resolution, timeout and retro defaults; spawning capability defaults to leaf. A display label is not a persona or a permission grant.
- Child identity is task-bound, separate from role and display name. Use ~anonymous~ as the display/index token when no role exists; it is not a role identity or permission grant. Distinguish an absent role from a named roster persona even if its name is ~anonymous~; the below-root absent-role refusal runs before name-based allow-list admission. Do not reserve an otherwise valid roster name merely to encode absence. Audit ~HERDR_ORCH_PERSONA~ consumers: ~placement-policy~, ~enforce-spawns!~, ~spawns-policy~, launch identity injection, ~orphans!~ and ~continue!~. Also cover ~child-name~, ~composed-persona-path~, ~ledger/allocate-index!~ and ~core/nested-prefix~. A missing role must never make a delegated process appear root-owned.
- Below root, fresh anonymous and measurement launches remain forbidden. A fork resolves its effective target persona from an explicit overlay or the caller's recorded named role, then applies the existing caller allow-list. No-overlay inheritance grants no authority: an inherited role not in that list is refused before allocation. Below-root children remain leaves regardless of role/frontmatter; packaged allow-lists are unchanged.
- Normal ~continue~ retains the child's existing context and resolved provenance. Context changes require a new child, not a new round in the old child.

*** Pi fork
- Fork reads the caller's own persistent Pi session; it does not select another child's session. Fork means conversation inheritance, not an exact live-process clone. Child resources and executable tools reload in the selected checkout. An unnamed root without an overlay uses normal child-runtime instructions plus inherited conversation; no named role is invented. An authorised named caller without an overlay supplies its recorded role snapshot.
- Snapshot the persistent source before creating the child. Identify the launching assistant/tool batch on the active branch, then the caller's current turn: everything after its last completed assistant response (stop, no tool calls). Branch the child before the first message of any kind after that response (the request, a custom message that opened the run, a continuation's first message, or a message appended between turns such as `!` output or an extension message; that message and any compaction after it are dropped), so the child inherits only completed turns and its assignment is the only open request. The caller's request, steering, failed attempts and tool work in that turn stay outside the child; the caller passes any same-turn findings the child needs in the assignment, and the skill tells it to. A caller with no completed earlier turn refuses with a fresh-context remedy. Parallel sibling tool results must not cause selection of an arbitrary final line. Reject a source whose safe boundary cannot be proved.
  Rejected (owner decision, 2026-10-22, after a controlled single-generation replay reproduced the inherited worker re-running its caller's fork command with the current assignment intact; ~.tmp/child-context-replay-c21f/REPORT.md~):
  - Branch immediately before the launching batch: retains the caller's unanswered request, which the child treats as its own work.
  - Keep the launching call and append a synthetic tool result: preserves same-turn work but adds model-visible history the runtime did not produce, and must also answer or drop sibling calls.
- Use Pi's public session API rather than rewriting its JSONL format: ~SessionManager.forkFrom~ with the selected checkout as ~targetCwd~, ~branch~ at the proved turn boundary, then ~appendCustomEntry~ to persist the selected branch. Refuse a null boundary; do not substitute empty history. The marker is not model context. Launch the independent file through ~--session~; preserve source session identity, target checkout and selected entry in provenance. Installed Pi's explicit-session path takes runtime cwd from the session header, so pane cwd alone does not establish checkout isolation.
- Store immutable named-role content/provenance at delegation launch so later edits to the definition cannot silently change an inherited role. A selected overlay uses its own resolved composition. If a named parent's role snapshot is unavailable, refuse implicit role inheritance with a remedy rather than claiming an exact copy; an explicit overlay remains available.
- Apply new assignment identity and publication guidance after inherited conversation. Historical task/result identifiers are context, never current routing authority. Fork cleanup owns only newly created files and panes, never the parent session.
- The installed Pi is the baseline: the adapters were built on Pi 1.3.0 and re-verified on 1.4.0. Source inspection is not proof that an adapter works. Verify installed capability before allocation; load adapters and their test extensions inside the installed Pi process. The repository test entry point must invoke that runtime, record its version and the API module's resolved runtime identity, and fail on mismatch. Do not import a repository-pinned SDK for these checks, hard-code a Nix-store path or add a separate SDK pin. Ordinary dependency tests do not count as installed-runtime adapter coverage.

*** Measurement
- Input: ~--measurement-config PATH~, required only for ~--context measurement~. Its closed JSON fields are ~systemPromptFile~ (optional; absent means empty text), ~skillFiles~, ~tools~, ~extensions~, ~hardTimeoutMs~ (required positive integer) and ~expectedOutputs~. Resource/output lists default to empty; an empty ~tools~ list enables zero tools, not the harness default. Tool names are exact and case-sensitive, not patterns. Resolve input paths relative to the configuration file; resolve expected outputs relative to the work root. Unknown fields, invalid types, unreadable inputs and unresolved selections fail before launch. Freeze resolved inputs per run rather than rereading editable files during execution.
- Measurement refuses a positional persona, ~--trait~, ~--prompt-extra~, ~--retro~, ~--no-retro~ and ~--spawns~ before allocation; do not silently ignore them or apply persona defaults. ~--measurement-config~ is refused outside measurement mode. Keep model/effort selection, checkout selection, preview, wait budget and explicit monitor placement available.
- The experiment assignment still comes from exactly one of ~--task~, ~--task-file~ or stdin. It is not wrapped. Transport literal text through the adapter rather than reinterpret it as CLI messages: leading ~/~, ~@~, ~-~ and template-like text must not become commands, file attachments, options or expansions. The subject's stdin is closed; only the parent CLI consumes assignment stdin.
- Compile the system file text followed by the literal selected skill-file contents in list order, separated by two newlines, into an inspectable treatment prompt; expose the exact resulting text in preview. Default system text is empty. No discovered context files, skills, templates, tools, MCP servers or extensions may enter the subject. Explicit provider-auth extensions remain supported; do not remove credentials indiscriminately.
- Derive request expectations before execution from configured inputs, provider/auth mode, resolved model compatibility and installed-runtime identity. Record expected adaptations separately from the treatment and retain the final request; never accept an adaptation merely because it appears in the observed payload. Apart from the protocol encoding defined below, only these inspected Pi adaptations are permitted:
  - Anthropic OAuth :: First system block ~You are Claude Code, Anthropic's official CLI for Claude.~; tool definitions and historical ~tool_use~ names follow ~toClaudeCodeName~: case-insensitive lookup in Pi's canonical Claude Code tool-name list, otherwise unchanged. Configured selection stays exact and case-sensitive. Refuse converted-name collisions before launch. Other auth modes expect neither change.
  - Anthropic model fallbacks :: Owner-approved. When the selected model declares ~compat.allowedFallbackModels~, the installed Anthropic consumer sends top-level ~fallbacks~ as that list reduced to ~{model}~, in order, and the ~server-side-fallback-2026-07-01~ beta (protocol encoding). Derive exactly that list from the model; an altered, added, dropped or reordered target fails. Do not exclude fallback-enabled models. A fallback can change which model serves a turn, so record per assistant turn the requested model, the allowed list and the provider-reported served model. Pi surfaces ~responseModel~ only when it differs from the requested id, so an absent value is recorded as unknown, never guessed to equal the requested model; a served model outside the declared list is recorded as undeclared, not guessed. Other APIs read no such setting and expect no ~fallbacks~.
  - Codex default instruction :: Owner-approved. ~openai-codex-responses~ sends ~instructions: "You are a helpful assistant."~ when the configured treatment is empty. Permit and record exactly that text for an empty treatment (adaptation ~codex-default-instructions~); a non-empty treatment is sent as is, and no other default text on any API is implied.
  - Tool-result images, captions, bridge messages and omission text :: Owner-approved across the four APIs. Derive each from the recorded tool-result content, its error state and the selected model's image capability through the installed consumer rules: the model-capability omission text ~(tool image omitted: model does not support images)~ in place of each run of images; the Anthropic image blocks, the placeholder text block ~(see attached image)~ for an image-only result, and for an error result the text ~(image attached after the tool results)~ in the result plus a caption ~Images from the error result of tool call <id> (<name>):~ and the images after all results of the turn; the Chat Completions bridge user message ~Attached image(s) from tool result:~ with its ~image_url~ blocks after the whole group of results; and the inline ~input_image~ parts of ~openai-responses~ and ~openai-codex-responses~. This is not permission to accept observed images or captions: a changed caption, image bytes, MIME type, an added or dropped image or a wrong capability fails. User-message images stay refused because the assignment is literal text.
  - Empty and image-only result placeholders :: Owner-approved, only when independently derived from the recorded result: ~(no tool output)~ for an empty result on the OpenAI APIs and ~(see attached image)~ for an image-only result where the consumer rule produces it. Anthropic sends an empty string for an empty result.
  - Anthropic native tool changes :: When ~supportsMidConvoSystemMessages~ and ~supportsMidConvoToolChanges~ are enabled and initial configured tools are non-empty, expect exactly one trailing ~__pi_deferred_placeholder__~ definition, independently of auth. Match its description ~Reserved placeholder. Never available. Never call this.~, ~input_schema~ ~{type: "object", properties: {}, required: []}~ and ~defer_loading: true~. Record it as a protocol artefact, not an executable tool; do not assume it is model-invisible. Other model/tool combinations expect no placeholder.
- Protocol encoding includes ~betas~, ~thinking~, top-level ~output_config~, ~cache_control~ and ~eager_input_streaming~, plus empty-content ~output_config.effort~ system markers on ~supportsMidConvoEffort~ models when thinking is not disabled. ~openai-responses~ ~configuration_update~ effort items are protocol encoding of the same kind (owner-classified): their positions, content and levels are derived from the selected configuration, resolved level and recorded history, and an alteration, addition or removal fails; this does not permit arbitrary configuration updates. Derive expected marker positions/levels from the selected runtime, resolved effort and recorded history, independently of auth. Record encoding separately from treatment text; validate its runtime/model/effort-derived structure rather than compare it to the compiled treatment. This distinction does not exempt message text, tool definitions or altered/non-empty effort markers from the audit.
- Freeze the executable tool list. Reject unrecorded context, added executable tools, altered protocol artefacts and mid-conversation tool additions/removals. Protocol recording grants no callable tools; a placeholder call is refused and makes the measurement execution fail, with failed evidence retained. Do not add an audit-exception option. Within the four audited APIs do not restrict otherwise supported models (fallback-enabled models are measured under the derived fallback list), and do not substitute a provider-neutral or transcript-only audit for the request-boundary audit. Any other API fails closed: the user explicitly approved this four-API measurement boundary, and it limits measurement only, never fresh delegation or forks.
- The measurement adapter task owns a reusable subject launch/transport helper as well as the explicitly loaded extension; the integration supervisor reuses that helper rather than reconstructing argv, stdin, resource selection or request auditing.
- Use a small explicitly loaded Pi adapter for the full-prompt replacement and request-boundary audit. Native ~--system-prompt~ alone is insufficient because Pi 1.3.0 still adds a cwd section. ~before_agent_start~ can return the full ~systemPrompt~; the adapter and fake-provider tests must verify the actual model-visible request, since the normal transcript records structured prompt sections rather than the forced text.
- Record the selected harness/model/effort, effective input hashes, resource and tool inventory, request-context audit, event stream, stderr and final output. Keep credentials out of reports and launch manifests. Explicit extensions are trusted code; this is reproducibility/context control, not an OS security boundary.
- A headless supervisor owns each run. Before ~start~ acknowledges or ~run~ waits, detach the supervisor from the invoking process group/session, close stdin and redirect stdout/stderr to recorded evidence files. The subject is owned by that supervisor, not the invoking tool call. Record PID plus process-start identity and owned process-group/session evidence; PID alone cannot prove ownership after reuse. Verify detachment on each supported platform; unsupported platform capability fails before launching a subject. Do not assume a Linux-only command provides Darwin support or add a dependency without separate approval.
- ~collect~ and fan-in consume the existing immutable result stream. Single-result and fan-in waiters use execution liveness for headless entries, not Herdr agent presence. No pane is created by default. Repeated invocations supply batching without a scheduler.
- Explicit ~--tab~ or ~--split~ requests a read-only monitor pane for measurement, using existing placement semantics without applying the normal configured placement default. The monitor displays recorded events, tool activity, errors and execution state; it is not the measured process's terminal. Record its identity separately. Opening, closing or typing into it cannot change experiment inputs, stop the supervisor or publish a result. Interactive investigation starts a separate session outside the measured run.
- Successful execution requires process exit zero, valid successful terminal harness evidence, matching context audit and the configured expected outputs. ~expectedOutputs~ names newly created outputs, not modifications to tracked/pre-existing files. Reject such a pre-existing target before launch; existence alone would not prove this run produced it. Outputs remain inside the recorded work root under the existing symlink/path checks. Execution success is not a quality score.
- Bind supervisor publication to its recorded task/execution identity, separate from root pane identity. Preserve publisher validation, locking, artefact containment and checkpoint rules without resolving the supervisor as the root session. Its discharge check is execution-local: open root siblings cannot block its result. Do not fake a Herdr agent. Test two concurrent samples publishing while each other's round remains open.
- The subject receives no publication obligation or root routing. Remove inherited ~HERDR_PANE_ID~ and ~HERDR_ORCH_*~ routing/authority values, inject an explicit task-bound subject marker recognised by the delegated-child predicate, and refuse subject-side orchestration commands before any root/focused-pane fallback. This marker is transport metadata, not model-visible guidance. Keep explicitly required provider credentials. Environment separation prevents accidental authority inheritance; trusted tools/extensions are not an OS security boundary.
- The hard execution limit bounds the owned process tree. ~--timeout~ remains the existing non-destructive wait budget. Crashes, output/audit failure and hard-limit expiry produce failed execution evidence. Never auto-retry a sample. Preserve partial evidence when cleanup or publication fails.
- ~continue~ and ~poke~ refuse measurements. ~close~ requires captured terminal evidence and a stopped owned execution; it closes an optional still-owned monitor and marks the run closed. If the supervisor is lost without terminal evidence, retain the incomplete run for diagnosis; prune may retire it only after recorded process-start and process-group evidence prove its owned subject execution has stopped, without fabricating completion. A missing or replaced monitor never proves that the measured process has stopped and never permits closing another occupant. Status, fan-in, publication identity checks, prune, orphan handling, compact, harvest and worktree teardown must recognise the execution type rather than interpreting a missing pane as proof of death.
- Preserve normal checkout selection/reservation and publication checkpoint rules. Measurement is not implicitly read-only merely because the subject has no persona.

** Gotchas
- An installed Pi upgrade can change request encoding under the adapters. Pi 1.4.0 moved Codex tool declarations into an ~additional_tools~ input item for models that take mid-conversation system messages and additional tools, which broke a test rule derived from 1.3.0. The follow-up below tracks the re-check.
- A fork child that inherits its caller's unanswered request takes it as its own work, even when its assignment forbids that (controlled replay, see [[*Validation]]). This is why the boundary excludes the caller's whole current turn.
- Pi can open a run without a user message (an extension's ~triggerTurn~ custom message, or a continuation), and it appends ~!~ output, tool-loadout system messages and extension messages between turns. A turn rule that looks only for user messages leaks the current request.
- Installed Pi's explicit ~--session~ path takes the runtime working directory from the session header, not from the pane, so checkout isolation for a fork depends on the header.
- A ~collect --wait~ on a round that ~task run~ already consumed reports ~pending~ only when its wait budget ends. The closure review observed the bridge in the passing smoke spend about 26 minutes in such waits.

** Risks
- Fork reliability is unmeasured: one smoke run passed after the boundary change. The leaf, identity and publication guards contain a child that disobeys its assignment, but they do not make it succeed.
- A runtime change can alter what a measurement subject receives. The request-boundary audit and installed-runtime tests fail closed, so the cost is a refused run rather than a silent change.
- Permission drift when the persona is absent: one delegated-child predicate serves every guard consumer, and each consumer has a test.
