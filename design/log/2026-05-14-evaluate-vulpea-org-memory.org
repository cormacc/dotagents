* Summary
Decision: defer/no-adopt for the agent-facing org-memory stack. Vulpea is a solid Emacs-local SQLite/index/query foundation, but this repository's task protocol is intentionally `:CUSTOM_ID:`-centric and currently has zero `:ID:` properties, so a vanilla vulpea index sees no task/change-record notes. A disposable bridge fixture proved that mirroring `CUSTOM_ID` into `ID` makes task headings queryable by ID, property, TODO state, priority, and tags, but org-memory traversal still needs custom work because `#+IMPORT`/`#+PARENT` are keyword-level links and `task:` link abbreviations resolve as file links rather than stable typed task edges. Keep pi's flat-file parser/tools as the agent source of truth; revisit vulpea only as an Emacs-local UI foundation after an explicit protocol decision to add an `ID` mirror or a custom vulpea extractor/export adapter.

** Decisions
- Agent stack :: No adoption. `tasks_scan_summaries`, `org_read_section`, and the task parser remain simpler, Emacs-independent, source-of-truth aligned, and fast enough for the current corpus.
- Protocol compatibility :: `:CUSTOM_ID:` is not enough for vulpea indexing; `vulpea-db-query-by-property` can find `CUSTOM_ID` only after a note already has `:ID:`.
- Bridge shape :: If revisited, prefer an Emacs-local bridge that mirrors `CUSTOM_ID` into `ID` or registers a custom extractor/exporter; do not make agents consume vulpea's SQLite schema directly.
- UI scope :: `vulpea-ui` is only worth a follow-up if we commit to the ID/extractor bridge and want a custom org-memory sidebar; generic outline/backlink/link widgets are insufficient for selected task, imported Summary/Context, plan TODOs, blockers, linked issues, and validation state.

** Gotchas
- Vulpea's scanner intentionally ignores hidden directories, so project-policy temp fixtures under `.agents/tmp` must be updated file-by-file with `vulpea-db-update-file` or moved to a non-hidden disposable path for prototype-only runs.
- `#+LINK: task file:TASKS.org::#%s` makes `[[task:UUID]]` parse as a `file` link in vulpea, not as a queryable `task` edge; an org-memory graph view needs an explicit extractor rather than relying on link type alone.

** Prototype results
- Corpus scan before vulpea :: A local parser found 40 non-hidden org files, 327 `:CUSTOM_ID:` task headings, 0 `:ID:` properties, 29 `#+IMPORT`, 33 `#+PARENT`, 15 blockers, 133 logbooks, and 5 open questions.
- Vanilla vulpea run :: `/home/cormacc/dotfiles/agents/.agents/tmp/prototype-vulpea.el` used a throwaway nix Emacs profile and `vulpea-db-sync-update-directory` against `/home/cormacc/dotfiles/agents`; result was `elapsed_seconds=0.705`, `org_files=67`, `notes_total=0`, `file_notes=0`, `heading_notes=0`, `todo_notes=0`, selected lookup by `CUSTOM_ID` property = 0, selected lookup by ID = 0, `org` tag query = 0.
- Bridge fixture run :: `/home/cormacc/dotfiles/agents/.agents/tmp/prototype-vulpea-bridge.el` indexed a disposable fixture whose `ID` values mirrored `CUSTOM_ID`; result was `elapsed_seconds=0.238`, `notes_total=3`, selected lookup by ID = 1, selected lookup by `CUSTOM_ID` property = 1, `org` tag = 1, `research` tag = 1, TODO notes = 3, links total = 2.
- Bridge fixture details :: The parent task note preserved `TODO`, priority `B`, tag `org`, `CREATED`, `CUSTOM_ID`, and `LINKED_ISSUES`; plan task notes preserved TODO, priority `A`, tags, and `CUSTOM_ID`; body `id:` links were captured, but `task:` abbreviation resolved as a file link and `#+IMPORT` did not provide an import edge.

** Integration comparison
- Emacs-mediated query tool :: Most faithful to vulpea APIs and could drive an Emacs sidebar, but requires Emacs/vulpea running or batch-started, local DB freshness, ID/extractor bridge, and an agent wrapper; failure modes include stale DB, hidden temp paths, multi-checkout local state, API drift, and no benefit on headless/minimal agents.
- Exported cache/read model :: Could let Emacs maintain a JSON/EDN task read model from vulpea/plugin data while pi tools remain non-Emacs, but then cache invalidation and source-of-truth rules duplicate the existing parser work; still needs ID/extractor bridge and explicit writer discipline.
- Human UX only :: Best current path. Keep org files and pi parser as canonical; optionally add vulpea/consult/vulpea-ui to Emacs later if a human-facing side-panel task is selected.
