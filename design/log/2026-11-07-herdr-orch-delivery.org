* Intent
Implement the delivery augmentation decided in [[file:2026-11-06-herdr-orch-comms.org]]: a herdr-orch Pi extension watcher that steers each published result item into the orchestrating session once, on terminal Herdr and herdr-app alike, and an ~oh task publish~ that never blocks the child on the parent's settle wait. The result-item pipe, sealing and explicit ~collect~ stay as they are.

* Summary
*Level:* production · *Tests:* thorough · *Docs:* README

Design and evidence are in the investigation record's Decisions ("Augment delivery, keep the pipe" and "Delivery augmentation, the shape the follow-on implements") and Validation; this record carries only what implementation adds.

** Acceptance
*** Core functionality
- [X] An orchestrator Pi session (~HERDR_ENV=1~ or ~HC_TERMINAL_ID~, resolvable assignment root) receives each new result item once as a ~herdr-orch-item~ steer; a non-orchestrator session starts no watcher.
- [X] Delivery works without Herdr observing the session: a herdr-app Pi parent receives the item although ~oh agent get~ reports ~agent_session null~.
- [X] The delivered text contains only child, task, status, first summary line, the collect instruction and the advisory line.
- [X] ~publish~ returns within 1 s on a busy parent for every parent kind.
- [X] A Pi parent is not pushed (~parent-push: skipped, watcher~); a non-Pi parent's push outcome is persisted in ~<item>.push.json~ and reported by ~collect~.
- [X] ~bash pi/extensions/herdr-orch/test.sh~ and ~bb test-clojure~ pass; the contracts describe the shipped behaviour. (Both suites carry pre-existing, environment-dependent failures on this host, identical at the baseline commit: ~private-browser.test.ts~ and ~recovery-integration.test.ts~ in the extension suite, and ~routing-filters-candidates-by-the-resolved-kind~, ~mechanical-cli-groups-dispatch-to-herdr~ and ~poke-holds-child-lock-through-final-check-prompt-and-update~ in ~cli-test~ when run from a shell under herdr-app. Every other test passes, including the new ones.)
*** Edge cases
- [X] A session reload re-delivers nothing already in the persisted set.
- [X] A partially written item is delivered once, after it parses.
- [X] An item whose ledger entry names another parent session is not delivered to this one.
- [X] A missing or unreadable result directory disables the watcher without an error toast every poll.
- [X] The detached push process survives ~publish~ exiting and writes its outcome even when the parent never settles (timeout recorded).
*** Anti-criteria
- [X] Must not: deliver FINDINGS, NEXT, PROCESS or artifact paths through the steer.
- [X] Must not: run ~oh~, capture, close or continue from the extension.
- [X] Must not: change item sealing, capture, or the result stream layout beyond the sibling ~.push.json~ file.

** Decisions
- Watcher lives in the existing extension :: ~pi/extensions/herdr-orch/~ already carries the caller gate and the ~herdr_*~ tools; a separate package would duplicate gating. Rejected: a standalone extension, a Herdr plugin (cannot reach a herdr-app session).
- Parent kind from the publish-time probe :: ~notify-parent!~ already calls ~agent get~ on the parent pane and receives its ~:agent~ kind, so the Pi skip needs no ledger field. Rejected: recording parent kind at spawn (a ledger migration for one branch).
- Push outcome as a sibling file :: ~<item>.push.json~ beside the immutable item, written only by the detached process, read by ~collect~. Rejected: a ledger field (the detached process would race the unserialised ~ledger/update!~ window the contract already accepts as a residual).
- First start must be quiet :: The result directory holds every past item (219 on this checkout), and the first session with the watcher has an empty delivered set. The ledger entry filters them: another parent's round, or an item already carrying ~captured-at~ for this session, is skipped and not recorded. A later uncaptured item of a captured round is still delivered. Rejected: seeding the set with everything present at first start (would lose an item published while the session was down).
- Dedup key is the item path, persisted beside the session file :: matches the prototype; the set is small (one line per item) and dies with the session file. Rejected: a cursor on mtime (fails on identical timestamps and on replayed directories).

** Risks
- ~fs.watch~ on macOS can miss or coalesce events :: the 5 s poll is the authority; the watcher only shortens latency. Not observed in the bench or the hc check.
- Mixed versions :: a parent with the watcher and a child with an old ~oh~ still gets the push and one duplicate turn until both sides update.
- A non-Pi parent's detached push outlives ~publish~ :: its outcome file is the only trace; ~collect~ reports it, and a lost process leaves the ~publish~-written decision in place.

* Implementation
- ~delivery.ts~ exports pure helpers (~orchestratorSession~, ~assignmentRoot~, ~parseItem~, ~itemText~, ~skipByLedger~, ~itemNumber~) and ~startDelivery~, which takes the env, poll interval and watch factory as options so the test runs without timers or real ~fs.watch~. ~registerDelivery~ wires ~session_start~/~session_shutdown~.
- ~assignmentRoot~ resolves a relative ~ORCH_ASSIGNMENT_ROOT~ against the process cwd, as ~oh~ does; ~test.sh~ exports a relative ~TMPDIR~, which is how that case was found.
- The detached process is the ordinary launcher with ~task notify-detached~, so it inherits the publish process's environment and resolves the same runtime; on Linux it runs under ~setsid~. Its stdout goes to ~<spec>.log~, removed with the spec on completion.
- The parent's kind comes from the publish-time ~agent get~ probe; no ledger field was added.
