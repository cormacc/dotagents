* Intent
Spread work across all authenticated subscription accounts so that weekly credit is not lost unused. Today an account that no session uses keeps an expired token, drops out of the routing inventory, and is never chosen. Routing must refresh such an account, prefer the account whose weekly credit is most at risk of expiring unused, and let a delegated child move to another account when it reaches a quota limit.

* Summary
*Level:* production · *Tests:* thorough · *Docs:* README

All three plan tasks are implemented and tested; not yet committed. Measured cause (2026-11-19): `cli.clj` `authenticated-inventory` keeps only accounts whose credential is `"ready"`, and `quota_credentials.clj` `ready` returns `expired-credentials` when the access token has expired. In 271 ledger entries, 2 routes chose `anthropic-1`; the route of 2026-11-17 had `anthropic` as its only Anthropic candidate. When both tokens were valid, the current rule chose `anthropic-1` correctly.

** Scope
*** In scope
- Refresh of an expired Pi account (base or `anthropic-<N>`) that has a refresh token, during the routing inventory step.
- Pace-based order of model/account pairs inside one rank, for launch routing and primary recovery (one shared policy).
- Quota failover in delegated Pi children.
- The contract, extension README and skill README sections for routing, the owned credential boundary and primary recovery.
*** Out of scope
- Pace across ranks: rank stays the first sort key.
- Native Claude and Codex harnesses: they keep single-account behaviour.
- Refresh by the quota collector: it stays read-only.
- A hard 5-hour gate.
- Separate reserves for each window: the existing `:reserve` on the effective minimum already excludes a pair when any bounding window is at or below it.
- Account reservations, quota polling and timers that wait for a reset.

** Decisions
- Rank first, pace inside a rank :: rank expresses model preference between providers; pace only chooses between pairs of equal preference.
  Rejected:
  - Pace across all ranks of a tier: a lightly used account of a less preferred model would take work from the preferred model.
- Weekly spare rate (remaining / time to reset) :: it uses credit that will expire soonest. Example: 50% left with 1 day to reset beats 80% left with 6 days to reset.
  Rejected:
  - Effective remaining fraction (current rule): ignores reset time.
  - Used% minus elapsed%: does not compare windows of different lengths, for example the Codex 30-day window against a 7-day window.
- 5-hour headroom is a tiebreaker, not a gate :: child failover recovers a child that reaches the session limit.
  Rejected:
  - Hard 5-hour gate for delegated launches: skips an account with spare weekly credit even for a short task.
- Refresh in the headless Pi inventory loader (`skills/herdr-orch/scripts/pi/account-loader.ts`) :: Pi already loads the account extension there, and Pi's own auth storage does the refresh, so Pi stays the owner of refresh.
  Rejected:
  - Refresh in the Babashka collector: races running Pi sessions if refresh tokens rotate, and breaks the owned credential boundary.
  - `pi auth check`: Pi 1.5.2 does not load extensions for `pi auth`, so it returns `provider_not_found` for `anthropic-<N>` (measured 2026-11-13).
  - A one-request Pi session on the account: uses quota and adds latency to each launch.
- Child failover follows its launch request :: same model on another account first; an alias launch can then use the alias's ranks; a direct launch never changes model. This is the rule that primary recovery and launch routing already use.
  This reverses two earlier decisions: the out-of-scope item "Automatic in-flight child failover" in [[file:2026-multiple-subscriptions.org]], and the anti-criterion "Must not: activate primary-session automatic recovery in delegated children" in [[file:2026-pi-recovery-selection-limits.org]]. `/oh tier` stays unavailable in children.

** Risks
- A fan-out of several children reads the same cached evidence (Claude TTL 5 minutes, `usage.clj` `ttl-ms`) and chooses the same account, so they share its 5-hour limit. Accepted: child failover recovers each child that reaches the limit; see Open questions.
- After a child fails over, the ledger `:model-canonical` and `:model-route` still show the launch account. Accepted: the ledger records the launch.

** Shipped
- `skills/herdr-orch/scripts/pi/account-loader.ts`: the `model-inventory` operation asks Pi for the auth of each OAuth provider (15 s bound each) before it writes the inventory; Pi refreshes an expired token through its locked auth storage. `--offline` does not stop the refresh (it disables only model catalogue network).
- `cli.clj` `route-model`: the inventory loader runs before usage collection, so a refreshed account has fresh evidence.
- `core.clj` `route`: weekly spare rate inside a rank; each candidate carries `:spare-rate`, also in the ledger `:model-route`; the reason names the rate.
- `cli.clj` launch env: `HERDR_ORCH_MODEL_ALIAS` for a Pi child launched with a vector alias.
- `pi/extensions/herdr-orch/recovery.ts`: delegated children recover within their launch request.

** Gotchas
- Pi installs its own global `fetch` at startup, after any `NODE_OPTIONS=--require` preload. A test that redirects an HTTPS endpoint must wrap `fetch` from an extension factory, not a preload (`account-launch.test.ts`).
- `usage-body` fixtures in `cli_test.clj` give Codex a reset in 2030, so its spare rate is near zero; a test that needs Codex chosen must exclude the other candidate instead.

* Implementation
- Spare rate is remaining fraction per day: `core.clj` `spare-rate`. A due or past reset counts as one minute away. The window is the longest bounding window of known length (least remaining on a tie); session headroom is the shortest one. `:session-remaining` is internal to the sort and not exported.

* Open questions
** DECIDED Should launch routing spread a fan-out across accounts?
:PROPERTIES:
:DECIDED: [2026-11-19 Thu 08:56]
:END:
Decision: no. Keep routing deterministic and rely on child failover, which is quick. Revisit if failover reports show that fan-outs regularly reach the 5-hour limit; the preferred change is then round-robin between pairs whose spare rates are within a margin, with a machine-wide launch count (the ledger is per assignment root).
Rejected:
- Subtract an estimated cost for each recent launch: the estimate is a guess, and a bad one moves work away from the account that pace prefers.
- Bypass the usage cache at launch: new spend appears only after children have run, so fresh evidence does not separate a burst.
