* Intent
Build a standalone Babashka TUI for org-tasks so operators can browse, mutate, and select tasks outside the pi overlay. Bare ~ot~ becomes the interactive entry point on TTY while preserving existing help and machine-output contracts for harness interop.

* Summary
*Level:* production · *Tests:* thorough · *Docs:* README

** Scope
*** In scope
- Add a charm.clj-based TUI launched by bare ~ot~ on TTY.
- Verify charm.clj and nexus dependency coordinates under Babashka before relying on them.
- Use nexus for TUI state, actions, effects, and testable dataflow if the smoke-load confirms it is viable.
- Render a task tree and task-detail view with functional parity to the pi expanded tasks UI documented in ~pi/extensions/tasks/README.md~.
- Preserve clean machine interop by reserving stdout for the final selected-task envelope and rendering interactive control sequences through a terminal device/stream that harnesses do not capture as JSON.
- Persist selection through the existing selected-task mechanism; exiting without pressing ~s~ returns the previously persisted selection, not the cursor row.
- Emit the existing ~ot selected --format json~ shape when the TUI exits successfully.
- Make bare non-TTY ~ot~ and bare ~ot --format json~ emit selected-task JSON without interactive control sequences.
- Preserve ~ot --help~, ~ot -h~, ~ot help~, and every existing subcommand invocation.
- Support the overlay key map in v1: ~↑↓/jk~ navigation, ~←→/hl~ status cycle, ~Ctrl-d/u~ detail scroll, ~Enter/Space/Tab~ collapse, ~s~ select, ~e~ edit, ~p~ plan, ~n/N~ create sibling/child, ~A~ archive, ~P~ publish, ~U~ unpublish, ~J~ open linked issues, and ~Esc/Alt-t~ close.
- Update CLI/reference/boundary/test docs that describe invocation, machine output, UI ownership, and test coverage.

*** Out of scope
- Modify the pi tasks extension in v1 beyond documentation references needed to keep contracts consistent.
- Change the ~org-tasks/v1~ selected-task JSON schema.
- Require JVM Clojure for normal ~ot~ use.
- Reproduce the overlay pixel-for-pixel.
- Replace pi's overlay or compact widget with the TUI in v1.

** Decisions
- Chose in-process charm.clj TUI over existing org-tasks Clojure functions :: Keeps one durable mutation source of truth and preserves Babashka deployment.
  Rejected:
  - Shelling out to ~ot~ subcommands from the TUI: slower, recursive-risky after bare ~ot~ changes, and harder to handle errors cleanly.
  - Extracting a shared TypeScript/Clojure UI model before implementation: better long-term consolidation, but it touches the pi extension and expands v1 scope.
- Chose dependency smoke-load before finalizing charm.clj/nexus architecture :: Coordinates were pinned only after verifying Babashka compatibility; the smoke-load confirmed both libraries load, so the planned nexus architecture was adopted rather than the thinner-dispatcher fallback.
- Chose nexus (single explicit ~nexus.core~ map, not the global registry) for v1 state/action/effect dispatch :: Pure action handlers receive a state snapshot and return effect data; effects perform side-effects against a per-event store atom bridged into charm's update loop. Avoiding the registry keeps dispatch free of global mutable state and unit-testable in isolation.
  Rejected:
  - ~nexus.registry~ convenience API: introduces process-global registration that complicates testing and load order for a single in-process TUI.
  - Requiring ~[nexus.core]~ purely as a dead smoke-load while hand-rolling dispatch: carries the dependency cost with none of the testability benefit and contradicts the stated decision.
- Chose functional overlay parity in v1 :: The standalone TUI should implement the documented expanded overlay key map; parity means same user-visible operations and constraints, not identical rendering internals.
- Chose persisted selection as the exit contract :: The TUI emits the same envelope as ~ot selected --format json~; cursor position is not an interop signal unless the user first persists it with ~s~.
- Chose stdout-reserved JSON for harness interop :: Interactive rendering must target a controlling terminal or another non-stdout stream so captured stdout contains only the final envelope.
- Chose non-interactive selected JSON for bare non-TTY and bare ~--format json~ :: Harnesses can shell out to bare ~ot~ without interactive blocking or ANSI output.
- Chose responsive stacked layout for narrow terminals :: Details render below the task tree when the terminal is too narrow for side-by-side panes.
- Keep pi overlay unchanged in v1 :: Consolidation is evaluated after the standalone TUI establishes behavior and contracts.

- Surfaced human-readable command failures in the TUI: ~error-message~ extracts ~[:error :message]~ from the forced-JSON error envelope instead of rendering raw JSON to the status line.
- Refactored bare ~ot~ dispatch: help remains explicit; bare non-TTY and bare ~--format json~ emit selected-task JSON; bare TTY launches the TUI.
- Updated the declared spec-impact docs for CLI invocation, machine output, boundary ownership, and test coverage.

** Gotchas
- charm.clj's ~program/run~ creates a system terminal; the TUI temporarily routes ~System/out~ to ~System/err~ while Charm owns the screen so raw-mode rendering stays interactive without polluting stdout. Keep non-interactive JSON checks in place when changing this boundary.

* Implementation
- Added dependencies in ~bb.edn~, ~deps.edn~, and the standalone ~scripts/ot~ fallback shim.
- Added ~skills/org-tasks/scripts/src/org_tasks/tui.clj~ for TUI state, rendering, nexus-based dispatch (actions/effects + ~msg->actions~ + ~update-fn~ charm bridge), command-effect reuse, and final selected JSON emission.
