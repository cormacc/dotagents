* Summary
Normalize Jira project configuration so shared defaults live with the rest of the task-memory preamble in =TASKS.setup.org=. =#+JIRA_CLOUDID= and =#+JIRA_PROJECT= move out of =TASKS.org=; =#+JIRA_BASE_URL= becomes derived from the org-native =#+LINK: jira https://.../browse/%s= template and is no longer required as a stored keyword. =TASKS.local.org= remains the checkout-local override layer.

** Decisions
- =#+LINK: jira= is the canonical URL source :: It already drives badge/open URL resolution. Derive =baseUrl= by stripping the browse suffix from the Jira link template instead of maintaining a duplicate =#+JIRA_BASE_URL= keyword.
- =TASKS.setup.org= carries shared Jira defaults :: =#+JIRA_CLOUDID= and =#+JIRA_PROJECT= are project-level config alongside =#+LINK:= declarations, TODO keywords, and startup settings. Keeping them in setup reduces root =TASKS.org= noise.
- =TASKS.local.org= remains highest precedence :: Local checkout overrides should still win over both =TASKS.org= and =TASKS.setup.org= for cloudId/project/baseUrl.
- Use a =#+SETUPFILE: TASKS.local.org= chain (declared before =TASKS.setup.org=) so org-mode resolves overrides natively :: Empirical check (2026-05-14) showed org-mode merges keywords from multiple =#+SETUPFILE:= entries with first-declared-wins semantics, so a local-first chain gives the same override behaviour the pi config loader applies in code. The pi extension still reads files directly today; aligning the pi side onto a multi-=#+SETUPFILE:= walk is tracked as a follow-up.
- No =#+JIRA_BASE_URL= compatibility read :: =baseUrl= is derived only from =#+LINK: jira .../browse/%s=. Existing =#+JIRA_BASE_URL= keywords are removed during migration rather than treated as overrides.

** Shipped
- Jira config loader now reads =TASKS.setup.org= through =#+SETUPFILE:= and applies precedence =TASKS.local.org= > =TASKS.org= > =TASKS.setup.org=.
- =baseUrl= is derived solely from =#+LINK: jira .../browse/%s=; =#+JIRA_BASE_URL= is no longer read.
- Fresh setup scaffolding emits =#+JIRA_CLOUDID:= and =#+JIRA_PROJECT:= in =TASKS.setup.org=.
- =TASKS.org= / =TASKS.archive.org= scaffolding now declares =#+SETUPFILE: ./TASKS.local.org= before =#+SETUPFILE: ./TASKS.setup.org=, and bootstrap touches an empty =TASKS.local.org= so org-mode never warns about a missing local setupfile.
- Doctor gained =missing-local-setupfile= / =misordered-setupfile= checks.
- =org-tasks= skill documents the local-first =#+SETUPFILE:= chain in its quick-reference and bootstrap sections.
- Migrated Jira keywords in =~/dotfiles/agents=, =~/dotfiles=, and =~/nmd/products/connect/portal=, and added the =TASKS.local.org= setupfile line to each repo's =TASKS.org= / =TASKS.archive.org=.
- Updated =org-jira= skill and Jira extension README.

** Gotchas
- The Jira extension currently reads only =TASKS.org= and =TASKS.local.org= in =loadJiraConfig=. It must learn the same one-level =#+SETUPFILE:= inclusion used by the tasks extension before content moves.
- =#+LINK: jira= templates may be either =https://host/browse/%s= or a project-specific shape. Derivation accepts only the known =/browse/%s= suffix; if the template is absent or non-matching, =baseUrl= remains unset.
- =#+JIRA_PROJECT:= may intentionally be blank. Empty values should not override a non-empty setup default unless we deliberately introduce a clear/disable syntax. Preserve current non-empty override semantics.
- =#+SETUPFILE: ./TASKS.local.org= must precede the shared one; reversing the order makes shared defaults win and silently breaks the override channel. The doctor =misordered-setupfile= check catches this.

** Follow-ups
- Remove stale references to =#+JIRA_BASE_URL= from docs/tests during implementation.
