** Priority recommendations
*** 1. Adapt test design, not another testing mandate
[[upstream:skills/engineering/tdd/SKILL.md]], [[upstream:skills/engineering/tdd/tests.md]] and [[upstream:skills/engineering/tdd/mocking.md]] add a useful combination: choose the observable interface, derive expected values independently, avoid implementation-coupled assertions, and build one vertical test/implementation slice at a time.

Our [[file:../../skills/herdr-orch/subagents/worker.md]] already requires a regression test to fail without the fix, and [[file:../../skills/herdr-orch/references/workflow-recipes.md]] already provides independent regression-test authorship. Repeating those rules in a new trait would add little. The useful addition is guidance on /which tests to write/ and /which interface to observe/, especially the distinction between behavioural and tautological assertions.

Destination: a small optional testing workflow skill, read by =worker= for an explicit test-first assignment and usable inline. Keep examples and mock guidance in references; retain the existing independent-author recipe for complex bugs. No =test-engineer= persona is needed.

Adaptation: use the accepted contract and existing test conventions to select the interface. Ask the user only when that choice changes scope or assurance, not before every test. Do not ban internal tests, call-order assertions or mocks categorically: ordering and interactions can themselves be the contract. Do not require all refactoring to wait for a separate review. Keep baseline, failure-path and assertion-preservation rules already owned locally.

Probe before adoption: compare the existing worker with and without the new workflow on a small feature and a bug whose obvious test merely duplicates the implementation. Check that the test fails for the intended defect, exercises the real call pattern, and survives a behaviour-preserving restructuring. Include a case where call ordering is required, so the adaptation does not remove valid coverage.

*** 2. Absorb the executable reproduction gate
[[upstream:skills/engineering/diagnosing-bugs/SKILL.md]] makes the feedback loop an explicit deliverable: one executed command that detects the reported symptom, minimise while preserving that failure, test falsifiable predictions, and rerun the original scenario after the fix. Its emphasis on distinguishing the user's bug from a nearby failure is valuable.

Our [[file:../../skills/herdr-orch/traits/investigate/prompt.md]] already separates symptom from inferred cause and ranks hypotheses. [[file:../../dirge/prompts/debug.md]] already asks for reproduction and a failing regression test. The addition is a more concrete completion gate, not a new debugging stance.

Destination: an on-demand debugging recipe reached from =investigate= and relevant worker assignments. Keep the trait short and diagnosis-only: an instruction to diagnose must not silently authorise a fix. Use =worker= for authorised fixes, =advisor= for a stuck consult and =base-analyst= for a read-only assessment; retain the existing performance workflow for performance comparisons.

Adaptation: require a passing control as well as the observed failure, protect captured secrets, and state which evidence is unavailable. Do not copy mandatory 3--5 hypotheses, unlimited persistence, or a blanket ban on reasoning before an automated reproduction exists. Some failures require source inspection to construct the probe. Stress loops, production instrumentation and live service calls still need bounded execution and appropriate authority.

Probe: provide a symptom with a tempting unrelated failing test. Require the correct reproduction and a safe control, then confirm diagnosis-only mode makes no project changes. For fix mode, require the original scenario to pass, not just the minimised test.

*** 3. Absorb active terminology checks; adapt bounded discovery
[[upstream:skills/engineering/domain-modeling/SKILL.md]] goes beyond consistent wording: challenge overloaded terms, check claims against code, and test relationships with concrete edge-case scenarios. Its three-part ADR test -- hard to reverse, surprising without context, real alternatives -- is a useful filter for durable rationale.

Our [[file:../../skills/doc-writing/SKILL.md]] already owns terminology and one home for each fact. [[file:../../skills/herdr-orch/subagents/planner.md]] and =org-plan= already clarify intent, explore alternatives, ask factual specialists and record decisions. Absorb the active checks into their existing ambiguity/design stages; put decisions in the change-record or existing living contract. Use a glossary only when the project needs one, and do not create =GLOSSARY.md=, =GLOSSARY-MAP.md= and =docs/adr/= as a compulsory second memory tree.

[[upstream:skills/engineering/wayfinder/SKILL.md]] contributes a distinct technique for work too uncertain to plan fully: resolve /decision questions/ before scheduling implementation, keep a coarse list of in-scope questions that cannot yet be stated precisely, and expand the plan only as answers make it actionable. This is more specific than ordinary task decomposition.

Destination: an optional discovery recipe under =org-plan=, using existing tasks, =:BLOCKED-BY:= and =Open questions=. Keep =planner= interactive; route facts to =scout=/=researcher=, experiments to a scoped worker or permitted scratch work, and preferences to the user. No =wayfinder= persona, tracker-label family or new scheduler is needed. Avoid a rigid one-ticket-per-session rule and model-independent context-size assumptions.

Probe: use a multi-session design with one overloaded term and an unresolved decision that changes later work. Check that the plan exposes the conflict, does not invent downstream acceptance criteria, and resumes from the existing record without creating a competing memory surface.

*** 4. Absorb requirement-conformance review, not the upstream reviewer
[[upstream:skills/engineering/code-review/SKILL.md]] separates standards from spec conformance in fresh reviews. The useful question set is explicit: what is missing or partial, what was added without approval, and what looks implemented but is wrong?

Our =reviewer= already loads the task/change-record; =code-review= already establishes intent, traces changed behaviour and ranks evidence-backed defects. Make requirement-to-implementation evidence more explicit when a spec exists. For a substantial change, the root can assign one fresh reviewer to conformance and another to correctness. This is opt-in decomposition of an existing role, not mandatory fan-out or a replacement for the separate =simplifier=.

Keep local scope and verdict rules: include relevant staged, unstaged and untracked files for working-tree requests; accept a clean range; investigate concrete security/correctness paths; reconcile findings by impact. Do not import the compulsory Fowler-smell baseline, an empty-diff error, a universal 400-word cap, or a prohibition on reranking across axes. The object-oriented smell remedies are not universal replacements for the surrounding language's conventions.

Probe: review a change that passes existing tests but omits one accepted requirement, plus a clean control. Require a precise contract citation and reachable consequence, without inventing standards findings or broadening the range.

*** 5. Absorb instruction-authoring diagnostics selectively
[[upstream:skills/productivity/writing-for-agents/SKILL.md]] offers useful review questions: does each pointer state when its target is needed; is branch-specific reference material disclosed only on that branch; does each step have an observable completion condition; is a directive a no-op against the current model baseline?

Our [[file:../../skills/skill-creator/SKILL.md]], =doc-writing= and trait probes already own progressive disclosure, single ownership and behavioural evaluation. Add only missing diagnostic questions to those owners when a real failure warrants it; do not install another authoring skill or rename all our concepts to upstream's vocabulary.

Treat claims about leading words, negation and context pressure as upstream hypotheses, not measured facts about our models. In particular, retain explicit negative safety boundaries and anti-criteria. Validate any shorter replacement against a tempting violation and the existing deployment instructions; attractive prose alone does not establish an improvement.
