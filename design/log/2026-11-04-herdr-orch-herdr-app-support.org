* Intent
Let a root agent that runs in a herdr-app terminal delegate through `oh`, and stop `oh` and the pi Herdr extensions from acting on the wrong Herdr session when Herdr TUI environment variables leak into a herdr-app terminal. Choose between a second `oh` backend over `hc` and a thin layer over hc-native delegation from measured hc behaviour, not from its documentation.

* Summary
*Level:* production · *Tests:* thorough · *Docs:* full

`oh` calls only the `herdr` TUI CLI (`herdr-orch.herdr/invoke`). herdr-app (0.1.10) runs every terminal in herdr-core (`hc` 0.1.15) and identifies the caller by `HC_TERMINAL_ID`, not by `HERDR_PANE_ID`. In a herdr-app started from a Herdr TUI pane, the TUI variables leak: on 2026-11-04 `HERDR_PANE_ID=w3:pG` named the TUI pane that hosts herdr-app, `oh task start --print-prompt` failed closed with `agent_not_found`, and `oh pane current` returned `w3:pG`, which is the wrong target.

** Scope
*** In scope
- Caller-backend detection by process ancestry: the nearest ancestor that is a Herdr pane shell (`pane process-info` `shell_pid`) or an hc terminal (`hc get` `pid`) selects the backend.
- Refusal of every `oh` verb, and of the pi `herdr-orch` extension and its `herdr_*` tools, when the detected backend does not match the variables in use.
- An hc capability spike that measures the facts in `** Risks` before the approach decision.
- The chosen approach (see `* Open questions`), with its contract, skill and README changes.
*** Out of scope
- Changes to herdr-app, herdr-core or Herdr TUI upstream. File upstream issues instead.
- Remote machines (`hc run --on`). The first delivery is local only.
- Measurement context (`--context measurement`) on the hc backend.
- The Herdr plugin wrapper ([[plan:2026-08-16-herdr-plugin-wrapper-for-herdr-orch.org]]). It stays TUI-only.
- Herdr-app layout mods that display the ledger.

** Acceptance
*** Core functionality
- [ ] In a herdr-app terminal with leaked TUI variables, `oh pane current` refuses with a backend-mismatch error.
- [ ] In a Herdr TUI pane with no hc ancestor, existing `oh` behaviour is unchanged.
- [ ] In a Herdr TUI pane inside a herdr-app terminal (reverse nesting), the TUI backend is selected.
- [ ] The spike records whether `herdr-agent-state.ts` (Herdr-owned, not edited here) reports pi state to a leaked `HERDR_PANE_ID`. If it does, an upstream issue exists.
- [ ] Under the chosen approach, `oh task run scout --task ...` from a pi root in herdr-app returns a validated `COMPLETE` envelope.
- [ ] Under the chosen approach, `oh task collect --any --wait` returns the first of two published hc children.
- [ ] Under the chosen approach, `oh task close <uuid>` ends the child terminal.
- [ ] Under the chosen approach, the child appears in the parent's herdr-app space with the configured placement.
*** Edge cases
- [ ] In both runtimes, a child whose parent terminal ends stays live until `close` or `orphans --close`.
- [ ] A blocked hc child is never sent prompt text (hc exit 9 is surfaced, not forced).
- [ ] `--context fork` from a pi root in herdr-app resolves the source session without `agent_session`.
*** Anti-criteria
- [ ] Must not: call `herdr` when the detected backend is hc.
- [ ] Must not: call `hc send --force`.
- [ ] Must not: run `hc server stop`, `hc server restart` or `hc update`.
- [ ] Must not: give a verb, flag or envelope field a behaviour that differs between the two runtimes, except where `contract.md` names the runtime fact that forces it.

** Decisions
- Backend detection by process ancestry :: Both variable sets can leak in either nesting direction, so variable presence cannot choose a backend. The nearest ancestor is the innermost host.
  Rejected:
  - Prefer `HC_TERMINAL_ID` when set: wrong for a Herdr TUI that runs inside a herdr-app terminal.
  - Prefer `HERDR_PANE_ID` when set: wrong for the measured case.
- Chose Option A, a second `oh` runtime over `hc` :: Keeps the ledger, validated envelope, worktrees, `continue`, `poke`, retro and trait composition, which Option B loses. The spike shows that `--outlive-parent`, `--no-notify` and an `env K=V` wrapper remove the hc conflicts.
  Rejected:
  - Option B, thin layer over hc templates, `hc send` and `hc wait --children`: no validated completion, and the TUI runtime would need a second, different design.
- Runtime parity over runtime fidelity :: One contract, one behaviour. Where hc and Herdr TUI differ, `oh` picks one behaviour and implements it in both, preferring the simpler one. The contract can be rewritten for this, provided its functionality stays equivalent.
- One `oh`-owned parent push in both runtimes :: hc children launch with `--no-notify`. The push fires only on a validated terminal result, with the same text in both runtimes. Blocked and exited children show through `collect --wait` `child-status`.
  Rejected:
  - hc-style notes in Herdr TUI: needs a watcher process for each child, because Herdr does not push child events to a parent.
  - hc notes plus the `oh` push in herdr-app: duplicate messages in two formats.
- Children outlive their parents in both runtimes :: hc children launch with `--outlive-parent`, and `orphans` stays the cleanup path. Herdr TUI already behaves this way, and hc kills on parent-terminal exit, not on parent-agent exit, so hc's default would not give "ends with the parent" anyway.
  Rejected:
  - End children with their parent: needs a new Herdr TUI mechanism that a crash skips, and loses in-flight work that a resumed parent could collect.

** Risks
Spike results are in `* Validation`.
- Environment :: a child gets the core's environment, not the caller's, so `HERDR_ORCH_*` must be injected as `env K=V ... <cmd>`.
- Lifetime :: a child dies (SIGHUP) when its parent terminal's program ends, not when the launching subprocess ends. `oh` children need `--outlive-parent` to keep the TUI semantics, where closing the parent leaves children for `orphans`.
- Notes :: hc types `<hc>` notes into an agent parent when a child exits. `--no-notify` suppresses them; `oh` keeps its own parent push.
- Status :: pi 1.5.0, codex 0.166.0 and claude-code 2.1.317 all report OSC 7501. A pre-report dialog (claude's folder-trust prompt) leaves `status` null, which `hc wait --children all` counts as working, so a launch needs a timeout and a screen read.
- Session :: hc has no session field. For a pi parent, `PI_SESSION_FILE` has the same path form as Herdr's `agent_session.value`. Claude and codex have no measured equivalent.
- First message :: only template runs report `first_message`; hc sends the template body plus the task once the agent is ready. A plain run must pass the task as the agent's own argv prompt.

* Implementation

* Validation
hc capability spike, 2026-11-04, hc 0.1.15, in an isolated core: wrapper `hcx` = `env -u HC_TERMINAL_SOCKET -u HC_TERMINAL_ID -u HC_SCOPE HOME=<scratch> XDG_{CONFIG,STATE,CACHE,RUNTIME}_*=<scratch> HC_SESSION=spike hc`. Control: `hcx server status` gave a new core id and pid; the user core (`ffeb71f0...`, pid 98243, 2 live) was unchanged before and after. The spike core was stopped at the end.
- Environment :: `SPIKE_MARK=caller hcx run 'echo MARK=$SPIKE_MARK'` printed `MARK=` both from outside and from inside a parent terminal that exported it. Control in the same run: `HOME` and `HC_SESSION` printed the core's values. `hcx run env SPIKE_MARK=wrapped sh -c 'echo $SPIKE_MARK'` printed `wrapped`.
- Lifetime :: a parent that started `kida` (default) and `kidb` (`--outlive-parent`), then exited: `kida` finished with reason `killed`, signal 1; `kidb` stayed `live`. A child started by a subshell that exited stayed live until the parent terminal's own program ended, then was killed.
- Notes :: a fake OSC 7501 agent parent (`printf '\033]7501;state=idle:app=fakeagent\033\\'`, then logs stdin) started `kidf` (default) and `kidg` (`--no-notify`). Its stdin got only `<hc>t15 kidf exited (exit 0). Read: hc read t15</hc>`. A plain non-agent parent got no notes.
- Blocked :: `hc send` to a fake agent reporting `blocked` exited 9 with `kind: blocked`. Control: `hc send --if idle` to an idle fake agent exited 0 and the line arrived.
- Status :: with the real `HOME` (`env HOME=... <agent>` in the isolated core), `hc get` showed `reported: true` for `pi` (`app: pi`), `codex --no-daemon` (`app: codex`) and `claude` (`app: claude-code`, cwd `~/dotfiles`, a trusted folder). In the untrusted `~/dotfiles/agents`, claude stopped at the trust dialog with `status: null`. With a scratch `HOME`, claude and codex stopped at onboarding with `status: null`.
- Session :: `hc get` has no session field (`hc schema` `Terminal`). `PI_SESSION_FILE` in this pi was an existing `.jsonl` path of the form that Herdr reports.
- First message :: a template `fake.md` (frontmatter `command:` the fake agent after `sleep 2`, body `PERSONA-BODY`) run as `hcx run --bg fake TASK-TEXT` returned `first_message: {sent: true, started: true}`, and the agent received `PERSONA-BODY`, a blank line, then `TASK-TEXT`. A plain run returned no `first_message` field (schema: "Template runs" only).
- `herdr-agent-state.ts` leak :: while this pi in herdr-app terminal t3 was `working` (`hc get t3`), `herdr pane get w3:pG` (the leaked `HERDR_PANE_ID`) showed `agent: null`, `agent_status: unknown`. No visible effect, so no upstream issue. Whether Herdr rejects the report or never receives it is not measured.
- Side effects :: claude, codex and pi each started once with the real `HOME` and no prompt. They can have updated their own state files.

* Open questions
** DECIDED Child lifetime: should a child end with its parent?
:PROPERTIES:
:DECIDED: [2026-11-04 Wed 22:35]
:END:
Decision: no. See `** Decisions`.
Recommendation: no. Pass `--outlive-parent` on hc and keep `orphans` in both runtimes.
- hc's rule is not "ends with the parent agent". It is "ends when the parent terminal's program ends" (measured: a child outlived the subshell that launched it). In herdr-app that program is the login shell (`hc get t3` argv `/bin/zsh -l`), so the kill comes on pane close, not when pi exits.
- Herdr TUI has no equivalent. Parity would need a new `oh` mechanism there, such as a pi shutdown hook, which a crash skips.
- A child that survives keeps in-flight work, and a resumed parent session can still collect it, because the ledger is keyed by session.
** DECIDED Notes: should `oh` send hc-style notes in Herdr TUI?
:PROPERTIES:
:DECIDED: [2026-11-04 Wed 22:36]
:END:
Decision: no. See `** Decisions`.
Recommendation: no. Pass `--no-notify` on hc and keep one `oh`-owned parent push, with the same text in both runtimes.
- hc notes fire on child exit, turn end, block and error. To send them in Herdr TUI, `oh` would need a watcher process for each child, because Herdr does not push child events to a parent.
- The `oh` push fires on a validated terminal result, which is the only completion signal. Blocked or exited children already show in `collect --wait` as `child-status`.
- Two push mechanisms in herdr-app (hc notes and the `oh` push) would deliver duplicate, differently formatted messages.
** DECIDED Full hc backend for `oh`, or a thin layer over hc-native delegation?
:PROPERTIES:
:DECIDED: [2026-11-04 Wed 22:29]
:END:
Decision: Option A. See `** Decisions`.
- Option A, second `oh` backend :: Extract a backend protocol from `herdr.clj` and add an hc implementation. Keeps the ledger, v1 envelope, worktrees, `continue`, `poke`, retro and trait composition. Cost: re-implement identity, placement (`hc run --label herdr.space/herdr.tab`, `herdr-app do terminal.keep --place`), session recording, close and the parent push; a fake-hc fixture.
- Option B, thin layer over hc :: Generate hc templates (`~/.config/herdr-core/templates/<name>.md`) from personas and traits; children report with `hc send $HC_TERMINAL_ID`; the parent fans in with `hc wait --children any`. `oh` keeps only envelope validation. Cost: loses ledger-backed `continue`, `poke`, ownership guards, worktree isolation and validated completion, which `SKILL.md` names as the only completion signal.
- Recommendation: A. The spike shows that `--outlive-parent` and `--no-notify` disable the conflicting hc semantics, and `env K=V` covers injection. Open costs for A: session identity for claude and codex, and first-message delivery (argv prompt per kind, or a generated template).
