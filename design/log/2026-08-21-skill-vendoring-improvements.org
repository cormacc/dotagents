* Intent
Make the maintenance boundary between first-party, adapted, and vendored skills explicit and checkable: per-class editing rules and classification in =skills/README.org=, and tool-written provenance on every vendored copy, so each one names its upstream, carries a content-hash drift signal, and stays updatable by the tool that installed it.

* Summary
*Level:* production · *Tests:* smoke · *Docs:* README

** Scope
*** In scope
- Classifying every top-level skill as first-party, adapted, or vendored in =skills/README.org=. dirge is first-party; skill-creator and clojure are adapted.
- Vendoring herdr as a pure upstream copy installed by =gh skill=.
- Rewriting find-skills around =gh skill=, which makes it adapted rather than vendored.
- Adopting =gh skill ... --dir skills/= as the manager for the vendored set.
*** Out of scope
- Publish-side control of what =npx skills add cormacc/dotagents= offers consumers.
- Relocating any skill out of =skills/=; any =agents.nix= change in the parent dotfiles repo.
- The gitlab-cli-skills body and its =.vendor.edn= plus =scripts/sync-gitlab-cli-skills.bb= sync path.
- The gitlab-cli-skills schedule-create doc gap (=6d205682=, TASKS.org § Upstream issues).

** Decisions
- =gh skill= manages the vendored set :: =gh skill install|list|update --dir skills/= operates directly on the committed tree, and provenance is tool-written frontmatter that =update= reads back, so no lockfile is needed. =gh= is flake-pinned, and installs resolve to the latest tagged release. Rejected: =npx skills= plus a committed =skills-lock.json=, which cannot target the committed =skills/= tree, is unpinned, and offers no release pinning. The two are not blendable per skill -- =metadata.github-*= reads as local modification to =npx skills=.
- Content hash, not upstream SHA, is the drift signal :: =github-tree-sha= hashes the installed skill directory, so it answers "did this skill change" and catches an unchanged tag whose contents moved, where a repo SHA churns on every unrelated upstream commit.
- The managed set stays unpinned :: =gh skill update= skips a pinned skill, which would suppress that signal. Updates are applied deliberately after a =--dry-run= review.
- Byte-identity is measured modulo tool metadata :: an install re-serialises the YAML frontmatter and injects =metadata.github-*=, so "vendored" means the prose is upstream's and the only delta is the tool's own block.
- Classification follows byte-identity :: a deliberately condensed or rewritten body is adapted, takes local conventions, and stays published; only an unmodified copy is vendored.
- dirge is first-party :: locally authored and owned here, with no upstream to resync from and no injected metadata.
- find-skills is adapted, not vendored :: its subject is the skill toolchain itself, so an upstream body documenting =npx skills= would teach agents the tool this repository does not use. It keeps the upstream workflow shape, documents =gh skill=, takes local conventions, and leaves the =gh skill=-managed set.
- gitlab-cli-skills keeps its exception :: upstream ships 48 root-level skills, so =gh skill= would install 48 siblings and flood discovery. =scripts/sync-gitlab-cli-skills.bb= keeps them nested under the router.
- Republishing is acceptable :: consumers who want a skill install it individually; the goal is internal maintenance separation, not publish control.

** Gotchas
- =gh skill update --dir skills/= warns once per unmanaged skill ("has no GitHub metadata"), so 15 of our 16 top-level skills produce noise around the single real result. It still exits 0. Filter by =sourceURL= from =gh skill list --json= rather than reading the update output directly.
- The vendored classification is duplicated in =scripts/validate-skills.bb=, which downgrades a vendored skill's frontmatter failure to a warning. A skill leaving the vendored class must leave that set too, or its frontmatter silently stops gating -- reclassifying dirge and find-skills opened exactly that hole, and a broken frontmatter in either still exited 0 until the set was corrected.
- =gh skill update= without =--all= stops an interactive terminal at =? Repository for <skill> (owner/repo):= for the first unmanaged skill. Piped or redirected it skips them instead, so a scripted check looks clean while the same command hangs for a human.
- =gh skill install --pin= takes the ref as an argument (=--pin <tag-or-sha>=); bare =--pin= fails with =flag needs an argument=.
- =gh skill list --dir= reports every skill in the directory, not only managed ones; a managed skill is identified by a non-empty =sourceURL= / =version=. Nested children under the gitlab-cli-skills router are not listed, so the router counts once.
- A =gh skill= install needs GitHub API auth. Unauthenticated, a handful of probes exhausts the rate limit and the failure surfaces as =HTTP 403= from the version resolver, not as an auth error.

** Risks
- =gh skill= is explicitly "in preview and subject to change without notice". Accepted: the frontmatter it writes is plain YAML that survives the tool, and =gh= itself is flake-pinned.

* Implementation
=gh skill= behaviour, measured 2026-08-21 against gh 2.97.0 (preview), evidence under =.tmp/gh-skill-probe/=:
- =install --dir=, =list --dir --json= and =update --dir --dry-run= all operate on an arbitrary directory, installing to =<dir>/<skill-name>/SKILL.md=.
- =install= injects =metadata.github-repo=, =github-path=, =github-ref= and =github-tree-sha= (plus =github-pinned= when pinned); =update= compares the local tree SHA against the remote.
- Installs resolve to the latest tagged release before default-branch HEAD; =@VERSION= and =--pin= override it.
- Against the raw upstream file at the same tag, an installed body differs by three hunks: frontmatter re-serialised alphabetically, the metadata block added, one blank line dropped. The prose is untouched.
- herdr needs no exception because upstream repackaged it: at =v0.8.2= the skill sits at =skills/herdr/SKILL.md= and the repository-root =SKILL.md= is a 404, which is exactly the retirement condition the old exception named. The exact-path form (=... herdr SKILL.md=) is rejected with =skill "SKILL.md" not found=; install by skill name.
- Discovery on vince-winkintel/gitlab-cli-skills returns 48 root-level skills, so that exception is unchanged by the tool switch.

Repository facts behind the classifications:
- =skills/dirge/SKILL.md= has one commit here (=fee2327=) and no recorded upstream.
- =metadata.internal: true= hides a skill from =npx skills add --list= (scratch two-skill probe, "Found 1 skill", visible skill as positive control) if publish-side control is ever wanted.
- =~/.agents/skills= and =~/.claude/skills= are whole-directory links to this repo's =skills/= (dotfiles =agents.nix=), which is why no relocation is on the table.
