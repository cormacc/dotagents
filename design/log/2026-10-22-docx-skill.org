* Intent
Move the generic Word (.docx) tooling that the Neuromod `nmd-dcr` skill grew -- inspection, tracked-change extraction, version comparison and XML-safe editing -- into a reusable `docx` skill, and move the generic SharePoint version recipes into `ms365`. `nmd-dcr` keeps only the organisation-specific DCR workflow and FR0001 fill, so that each fact lives in the lowest layer where it is correct.

* Summary
*Level:* production · *Tests:* thorough · *Docs:* full

Extracted from the `nmd-dcr` skill in the nmd-dev repository (`~/nmd/process/nmd-dev/.agents/skills/nmd-dcr/`), which keeps the FR0001 fill and loads `docx.core`.

** Scope
*** In scope
- New `skills/docx`: `docx.core` library namespace, CLI (`inspect`, `changes`, `compare`), LibreOffice compare helper, synthetic fixtures, tests, `SKILL.md`.

- `skills/ms365`: SharePoint version state and version download recipes, and the draft-visibility check.

- Changes to the vendored `convert-documents-to-markdown` skill.

** Decisions
- Skill name `docx` :: it holds inspection, comparison and editing helpers, not only tracked changes.
  Rejected:
  - `docx-tracked-changes`: too narrow once `docx.core` editing helpers are included.
  - Extend `convert-documents-to-markdown`: vendored, so local edits are lost on re-sync; and its purpose is conversion, not review or editing.
- Babashka with `clojure.data.xml` :: keeps namespace prefixes on emit, so `mc:Ignorable` stays valid and Word opens the result.
  Rejected:
  - `python-docx`: Python against the repository preference, and `cell.text` drops text inside `w:ins`.
  - docjure / Apache POI: Java libraries that bb cannot load.
- `nmd-dcr` loads `docx.core` from the installed skill through the bb classpath :: one copy of the helpers.
  Rejected:
  - Copy the helpers into `nmd-dcr`: two copies drift.
  - Keep all helpers in `nmd-dcr`: generic code in an organisation layer.
- Build fixtures at test time from hand-written WordprocessingML (decided 2026-10-22, reversing a committed-fixture plan) :: no binaries in Git, no pandoc or LibreOffice for generation, exact control of each XML feature under test. Only the compare test needs LibreOffice.
  Rejected:
  - Commit fixtures made with pandoc and LibreOffice: binary diffs, and neither tool gives direct control of a byte-order mark, checkbox controls or namespace prefixes.
- SharePoint version recipes go to `ms365`, not `docx` :: they are about Graph, not about the file format.

** Gotchas
- In hand-written WordprocessingML fixtures, escape `<`, `>` and `&` in text: a placeholder such as `<DD-Mmm-YYYY>` otherwise parses as an element.
- In a bb script, `dir` is already referred from `clojure.repl`; a top-level `(def dir ...)` fails at analysis.

** Risks
- `nmd-dcr` depends on a skill outside its repository. A colleague without dotagents cannot run `fill`. Accepted: `ms365` is already an external dependency; `fill` fails with the expected path.
- A later `clojure.data.xml` in bb could change prefix handling. Mitigated by the round-trip test.
- LibreOffice compare output differs between versions. Tests assert presence of changes, not counts.
