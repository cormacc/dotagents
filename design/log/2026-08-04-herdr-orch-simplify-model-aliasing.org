* Intent

Split the flat subagent model table into two levels -- `:models` keyed by pi-style provider-qualified canonical IDs, plus an `:aliases` map from weight/short name to canonical ID -- so an override can retarget one alias in one line instead of restating every harness spelling. Effective translations are preserved except one deliberate cell.

* Summary

*Level:* production · *Tests:* thorough · *Docs:* inline + contract.md

** Scope

*** In scope
- Two-level resolution: alias -> canonical ID (single hop) -> per-kind row, with the *canonical* ID passing through on a miss.
- Shipped [[proj:skills/herdr-orch/subagents/config.edn]]: 7 canonical `:models` rows + 18 `:aliases`.
- Validation of `:aliases` shape per file, and of alias/model key overlap and alias chains post-merge.
- `--print-prompt` reports the post-alias canonical model.
- contract.md § Model resolution, `config.edn` header, AGENTS.md subagents bullet.

*** Out of scope
- Multi-hop alias chains or per-alias row exceptions.
- Derivation rules generating per-harness IDs from structured entries.
- Any change to kind resolution, spawn policy, ledger, envelope, `:harnesses` semantics, or `merge-config` itself (`merge-with merge` already composes `:aliases` per key).
- New harness entries or model rows beyond the migrated set.

** Decisions
- Canonical ID is the pi-style `provider/model` string :: the `:pi` column becomes redundant (pass-through delivers the canonical spelling), rows shrink to genuine cross-provider remaps, and the same model via another provider is just a second row; aliases carry the human ergonomics so canonical verbosity costs nothing.
  Rejected:
  - Bare model names: keeps a redundant `:pi` column on every row and forces invented IDs for a second provider.
  - Map entries `{:provider … :model …}` with derivation rules: schema and rule machinery nothing currently needs.
- Alias/model key overlap fails loudly post-merge :: no silent shadowing in either direction; a legacy override carrying a full weight row fails at spawn naming the key rather than silently changing meaning.
  Rejected:
  - `:models` exact row wins (back-compat): a stale row silently shadows the alias override the user just wrote.
  - `:aliases` wins silently: a legacy row override silently stops taking effect.
- Aliases are single-hop and chains are validation errors :: multi-hop makes effective values non-local across override files.
- The canonical haiku row uses the documented full name `claude-haiku-4-5` :: a two-level table cannot keep feather's undocumented `haiku` shorthand without per-alias exceptions, which would reintroduce the duplication this change removes. One effective cell changes; same model. This knowingly supersedes the earlier deliberate choice of the shorthand.
- `:aliases` composition needs no merge code :: `merge-config` is `merge-with merge`, so a top-level `:aliases` map already merges per key across packaged < home < project; pinned by tests rather than new code.

** Shipped
- `--model feather` on kind claude passes `--model claude-haiku-4-5`, not `--model haiku`. Same model; the only effective translation change.
- Retargeting a weight is `{:aliases {"heavy" "<canonical-id>"}}` -- one line, no harness spellings restated.
- An override carrying a weight row in `:models` now fails at spawn naming the key.
- MODIFIED contract docs :: [[proj:skills/herdr-orch/scripts/docs/contract.md]] § Model resolution and [[proj:skills/herdr-orch/SKILL.md]] describe the two-level shape; [[proj:AGENTS.md]] no longer claims pi receives a `:pi` column.

** Gotchas
- A config example outside contract.md has no test guarding it, so it can become executable-wrong rather than merely stale :: README.org's worked override (`{:models {"heavy" …}}`) hard-fails with `config key is present in both :aliases and :models {:key "heavy"}`. Validate doc examples by parsing them out of the doc and running them through `validate-merged-config!`.
- Migrating a shared table's keyspace breaks fixtures nothing names :: four loader-precedence tests embedded `"heavy"`/`"middle"`/`"claude-opus-5"` as literal `:models` override keys. Grep the whole suite for literal old-key strings before declaring such a migration green.
- An argv-preservation claim is only as good as its expectation source :: hardcode the pre-migration matrix from the old table (or `git show HEAD:`), never derive it from the new one, or a green suite proves nothing.
- `bb test` runs from the repository root only :: there is no `bb.edn` under `skills/herdr-orch/scripts/`, and running it there fails with `test (Is a directory)`.

** Risks
- Claude renaming or dropping a native spelling is unchanged exposure, but now localised: one canonical row fixes every alias of that model.
