* Summary
Reduced =/jira clone= token cost on the emission side by introducing a shared =tasks.insertTask= JS helper plus its =tasks_insert_task= LLM-tool wrapper, and a =jira_clone_apply= tool that delegates the deterministic org-rendering to that helper. The model no longer re-emits the rendered =:PROPERTIES:= drawer / UUID / =:CREATED:= timestamp / heading boilerplate; only the body and structured fields cross the wire. =buildClonePrompt= reworked into a two-step dispatch (call =atlassian_getJiraIssue=, then call =jira_clone_apply=). Idempotency is enforced at the helper: scanning the target file plus =alsoScan= siblings (and recursive =#+IMPORT:= imports) for matching =:LINKED_ISSUES:= tokens; duplicate clones refuse without model involvement. Fetch-side optimisation deferred: pi-mcp-adapter does not expose a JS-callable MCP client to extensions today, so any MCP fetch must remain LLM-brokered.

** Decisions
- Re-scope to emission-side win :: drop =jira_clone_fetch= and any cache; revisit if the ExtensionAPI gains a JS-callable MCP primitive.
- =tasks.insertTask= owns deterministic org assembly :: priority mapping (Highest..Lowest → #A..#D), UUID, =:CREATED:=, drawer assembly, section-existence checks, idempotency on =:LINKED_ISSUES:= match. Tracker-agnostic.
- =jira_clone_apply= is the only Jira-side runtime addition :: parses Jira fields, performs Jira-specific transforms (priority-name → cookie, label list → org tags), delegates the write to =tasks.insertTask=. No org-mode strings inside the jira extension.
- Two-step dispatch in =/jira clone= :: prompt instructs the agent to fetch then apply; user-facing slash command unchanged.
- Body normalisation stays out of scope :: the model still owns ADF→markdown cleanup; helper writes body verbatim.
- =/jira get= reduced to a prompt-builder slash command :: no underlying tool today; renders compact human-readable summary.

** Shipped
- =pi/extensions/tasks/insert.ts= :: =buildTaskBlock= (org rendering, no I/O) + =insertTaskIntoFile= (file splice + idempotency). Importable JS, no =pi-tui= / =pi-coding-agent= dependency.
- =tasks_insert_task= (=tasks/index.ts=) and =jira_clone_apply= (=jira/index.ts=) as thin TypeBox-schema adapters; =jira_clone_apply= calls =insertTaskIntoFile= directly via JS import.
- =buildClonePrompt= rewritten as the two-step dispatch describing structured =jira_clone_apply= args and =inserted= / =duplicate= / =section_not_found= / =error= return shapes.
- Idempotency contract: scan target + =alsoScan= + recursive =#+IMPORT:= for matching =:LINKED_ISSUES:=; first match wins; refuse with =status: "duplicate"= and =existingId= / =existingFile= / =conflictingToken=. =jira_clone_apply= passes =alsoScan: [TASKS.local.org]= when target is =TASKS.org= and vice-versa.
- =/jira get= prompt-builder via =buildGetPrompt=; reuses =resolveKey= + cloudId resolution + same field filter; supports multi-key plural wording + footer link composition from =#+JIRA_BASE_URL=.

** Gotchas
- A registered pi tool's executor *cannot* invoke MCP from JavaScript today. =pi-mcp-adapter='s MCP client is internal to the adapter; the pi =ExtensionAPI= exposes no =callTool= / =mcp.call= / cross-extension RPC primitive. Any MCP fetch must remain LLM-brokered.
- =parentId= placement semantics: =buildTaskBlock= promotes to =***= when set, but =insertTaskIntoFile= still appends at the *end of the named section* rather than under a specific parent task subtree. Jira clones are always top-level under a category section, so no consumer needs the parent-anchored case yet — gap documented in the type but not exercised.

** Follow-ups
- Empirical token measurement against a body-heavy SAND issue (open question on file).
- Fetch-side optimisation (=jira_clone_fetch= + cache) revisits if pi-mcp-adapter exposes a JS-callable MCP client to extensions.

- Body cleanup heuristics could move into =buildTaskBlock= as a pre-emit normaliser if the MCP server gains deterministic markdown rendering.

* Implementation

** Architecture
- /Pure helper at the bottom./ =tasks/insert.ts= exposes =buildTaskBlock= (rendering, no I/O) and =insertTaskIntoFile= (splice + idempotency). Both importable JS — no =pi-tui= / =pi-coding-agent= dependency — so cross-extension consumers can use them without round-tripping through the LLM tool registry.
- /LLM-tool wrappers on top./ =tasks_insert_task= and =jira_clone_apply= are thin TypeBox-schema adapters. =jira_clone_apply= calls =insertTaskIntoFile= directly via JS import. The schema duplication is intentional: the contract the model sees needs Jira-specific descriptions (priority-name buckets) out of scope for the generic helper.
- /Two-step dispatch in the prompt./ =buildClonePrompt= describes structured =jira_clone_apply= args + =inserted=/=duplicate=/=section_not_found=/=error= return shapes. The rendered org body never appears in any =edit= tool call.

** Token-reduction reasoning

| Step                                   | Pre-2f0f354    | Post-2f0f354 (today)        | Post-this-change          |
|----------------------------------------+----------------+-----------------------------+---------------------------|
| Issue ingest (=atlassian_getJiraIssue=)| ~17 KB JSON    | ~1.5 KB JSON (field filter) | ~1.5 KB JSON (unchanged)  |
| Org body emission                      | edit tool: drawer + heading + UUID + timestamp + body (~300–800 tok) | edit tool: same as pre | tool args: key + summary + priorityName + body + labels — org boilerplate gone |
| Idempotency on re-clone                | none           | none                        | structured refusal at the helper, no model rendering |

Single largest residual cost is the body itself (intrinsic). Savings come from removing org-mode boilerplate around it plus refusing duplicates without invoking the model for rendering. Empirical measurement against a body-heavy SAND issue tracked as an open question.
