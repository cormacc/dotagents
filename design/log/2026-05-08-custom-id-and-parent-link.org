* Context

Today the org-tasks/org-plan protocol stores task identity as =:ID: <uuid>= and back-links plans to their parent task with =#+PARENT_ID: <uuid>= — a bare keyword. Plan→task navigation requires a UUID grep; for a project-local task graph that is the only direction in the system that is not a clickable org link.

Adopting =[[id:UUID]]= would lean on Emacs' =org-id-locations= cache (system-local, agenda-files-dependent), which is fragile for a self-contained per-project graph. The file-link form =[[file:<rel>/TASKS.org::#<uuid>]]= is fully self-contained but requires the target heading to expose a =:CUSTOM_ID:= — org's =::#anchor= syntax resolves only against =:CUSTOM_ID:=, not =:ID:=.

Decision: drop =:ID:= outright, store UUIDs as =:CUSTOM_ID:=, and replace =#+PARENT_ID:= with a navigable =#+PARENT:= link. Migration is a one-shot rewrite across three repos checked out on this machine: =~/dotfiles/agents-src=, =~/dotfiles=, and =~/nmd/products/connect/portal=.

** Design decisions
- =:CUSTOM_ID:= replaces =:ID:= outright :: No dual-slot, no drift surface. The task graph maintains its own UUID index; we do not depend on =org-id= machinery, so losing =:ID:= semantics costs nothing internal. From the protocol's perspective the property is still the canonical task ID — the rename is an Emacs-side implementation detail driven by org's anchor-resolution rules.
- =#+PARENT:= carries an org-link :: Form =#+PARENT: [[file:<rel>/TASKS.org::#<uuid>][<parent summary>]]=. The relative prefix is computed from =#+DEFAULT_PLAN_DIR= at scaffold time. Default =design/log/= → =../../TASKS.org=. Link descriptions are escaped/sanitised, or omitted when unsafe, so heading text cannot break org link syntax.
- No legacy tolerance window :: Three projects, one machine, one sweep; tooling and content migrate atomically. (Tolerant reader stays cheap to add later if a fourth project surfaces with stale data.)
- Subtasks (level-3) also use =:CUSTOM_ID:= :: =#+PARENT:= is a plan-file keyword only — subtasks under a parent task do not need it (the org tree already encodes the relationship).
- Plan files do not grow =:CUSTOM_ID:= entries beyond their existing task headings :: Only =TASKS.org= / =TASKS.local.org= / =TASKS.archive.org= headings carry top-level identity. Plan-task headings continue to carry their own =:CUSTOM_ID:= (these are the same UUIDs that get migrated out of =TASKS.org= when a proactive plan is created).
- Scope of migration includes =TASKS.archive.org= :: Archived tasks keep their UUIDs intact under the new property name so historical references continue to resolve.
