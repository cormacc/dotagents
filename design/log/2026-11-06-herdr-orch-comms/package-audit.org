* Reading

- Closest design match :: pi-session-mail. Its Maildir ~tmp/new/cur~ claim-by-rename, watcher-plus-poll wake-up, ~deliverAs~ split (steer for requests, followUp for replies), neutral labelled injection with an end-of-mail line, pid-plus-start-token liveness, and explicit "any process running as you can write" caveat match the mailbox hypothesis almost clause for clause. It is Pi-only and keyed by Pi session id, so it serves no ~oh~ CLI path, no non-Pi child, and no herdr-orch round identity.
- pi-mail :: same shape at a higher level (project scope, threads, UI, reminders). Deliberately not orchestration. GPL-3.0-only, which matters if any code is copied rather than merely consulted.
- pi-agent-comm :: the only one that separates mechanical context (no model turn) from cognitive asks. Its Unix-socket answer path is the small socket broker the parent task says to avoid unless measured; its system-prompt injection on every turn is a cost this repository would not accept.
- pi-messenger :: the message layer is a minor part of a Crew/Team orchestration product; adopting it imports a second orchestration authority. Not a candidate.
- agent-comms :: the only cross-harness design, and the only one with delivery states, replay queues and a Claude Code drain. The cost is a TCP/UDP mesh, an elected coordinator, keypair identities, and a default public relay hub. It is the measured-justification case for a socket broker in the parent task; nothing in the current fan-out sizes (1-6 children on one machine) needs mesh formation, and in-memory replication loses everything when the last peer exits, which contradicts "stored messages authoritative".

* Reusable parts for a prototype

- From pi-session-mail: the Maildir ~tmp -> new -> cur~ layout with ~rename~ as the single claim primitive; a ~running/<address>.json~ record carrying pid and process start token; the injected-message label and end line; the rule that a reply never starts a turn. These are patterns to reimplement in Babashka behind ~oh~, not code to vendor, because the store must be addressed by herdr-orch child name and round, not Pi session id, and must be readable without Pi.
- From agent-comms: the delivery-state vocabulary (queued, delivered, read, dropped, expired) and the Claude Code drain-on-hook pattern (atomic rename of a pending file from ~PostToolUse~/~Stop~/~UserPromptSubmit~), which is the known way into a busy Claude child without a socket.
- From pi-agent-comm: the provenance ~customType~ on injected entries, so transcripts and later compaction can tell agent-to-agent text from user text.

* Paper assessment of the deferred options

- Socket broker :: agent-comms shows the full cost: port ownership, coordinator election, reconnection, identity keys, and a relay hub. pi-agent-comm shows the minimal cost: one Unix socket per session for answers only, with durable replay still in the session JSONL. Neither removes the need for durable storage; both add a process-liveness problem the ledger already solves with files. Not justified at current concurrency unless the detection bench shows the file poll itself is the bottleneck.
- MCP :: agent-comms uses MCP only as a drain for harnesses without an extension API (Codex, OpenCode); the Codex/MCP side has no push and must poll ~drainDelivery~. That confirms the parent task's note: MCP resource notifications do not by themselves wake an idle model, so MCP can only be an optional read interface over the same store.
