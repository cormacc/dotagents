* Intent
Keep the Herdr app task widget on a chosen task root while focus moves elsewhere. Pin supported local or remote projects without changing org-tasks or the terminal plugin.

* Summary
*Level:* production · *Tests:* thorough · *Docs:* README

Delivered. One session-only pin per widget overrides focus-following across workspace switches. The pin contains the resolved task root and its machine; the mod owns the action and state.

** Scope
*** In scope
- Widget state, command handling, display, refresh and selection in ~herdr-app/mods/org-tasks/main.js~ and ~herdr-app/mods/org-tasks/state.js~.
- Regression fixtures and assertions in ~herdr-app/tests/org-tasks-state.test.mjs~, ~herdr-app/tests/org-tasks-ui.test.mjs~ and ~herdr-app/tests/layout-wiring.test.mjs~.
- Pin bindings in ~herdr-app/keys.darwin.json~ and ~herdr-app/keys.linux.json~.
- Living user contract: [[proj:herdr-app/README.md]] section 'Task widget'.
*** Out of scope
- Terminal-plugin pinning: deferred by the owner; not a prerequisite for this delivery.
- Workspace-keyed pins, cross-widget synchronisation and restart persistence.
- Changes to org-tasks parsing, task writes, root-resolution semantics or embedded TUI contracts.
- New dependencies, configuration options or Home Manager wiring.

** Decisions
- The owner approved app-mod-only delivery and remote pinning; these replace the parent task's earlier two-adapter and remote-rejection constraints.
- Choose a mod action, shared by the key and clickable indicator, using the existing ~nextCommand~ loop.
  Rejected: a TUI-owned key requires a new return channel and expands scope into org-tasks.
- Choose one pin per widget across workspace switches, stored in memory on the view.
  Rejected: a workspace-keyed map adds lifecycle state without a requested benefit. Persistent pins add recovery state the owner does not want.
- Pin the displayed resolved root, not a transient foreground folder. Preserve its machine as supplied by the app; do not resolve remote paths locally.
- Use separate pin and task-selection click regions rather than relying on an unverified event propagation API.
- Keep a failed pin until explicit unpinning; never fall back silently to another root. Selection must also refuse unavailable or substituted pinned memory.

** Risks
- Requests can finish after a project transition. Invalidate request identity on transitions, including transitions with no replacement request, and test delayed completions across pin/unpin.
- Watches can outlive their project. Keep the existing generation guard and test that obsolete events cannot reload a replacement project.
- A task root can disappear while its ancestor still has memory. Test this explicitly for display and selection; do not relax the anti-criterion to simplify the adapter.
- Builder-spy tests do not prove native click routing, key dispatch or rendering. Require disposable native Linux and macOS checks, including restart; report unavailable platform checks as validation gaps.
- View-local state is intentionally not shared between widget instances. Mark this at the state site with a ~known-limit:~ comment whose revisit trigger is a requirement for cross-widget synchronisation.

* Plan
The implementation task owns the coherent feature change. Native validation depends on that delivery.

* Implementation
- The view holds ~{root, machine}~ in memory; ~org-tasks.pin~ and the pin row click share the ~nextCommand~ loop; the pin row and the selection region are siblings.
- Pinned selection runs a fresh preflight and launches only for the exact pinned root and memory. Review rounds found three ordering defects in this preflight, each fixed with a red-then-green regression test:
  - A stale preflight could erase a newer display model (review 1).
  - The round-2 fix made a background poll (~REMOTE_MS~ 5 s) silently cancel a valid selection (review 2).
  - Two overlapping preflights: an older failure could erase the model after a newer success (closeout correctness review). Fixed with a separate ~selectionRequest~ identity.
