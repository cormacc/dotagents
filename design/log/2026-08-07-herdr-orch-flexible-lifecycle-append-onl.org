* Intent

Replace the one-shot publish with an append-only stream of immutable result items per round: a child publishes as many results as its work produces -- interim reports and monitor observations included -- through the single `publish` verb, and the terminal statuses keep sealing a round mechanically. The child stays lifecycle-agnostic; on receipt of any item the parent decides close, retain, or continue. `progress` is deleted as a redundant second message type.

* Summary

*Level:* production · *Tests:* thorough · *Docs:* full

** Scope

*** In scope
- Envelope STATUS gains the non-terminal value `WAITING`; `COMPLETE`/`FAILED`/`BLOCKED` remain the only terminal statuses.
- Item storage as numbered immutable files (bare `RESULT` path is item 1, `.N` suffixes append), each created one-shot via the existing `Files.createLink` primitive.
- Publish refusal rules replacing the physical one-shot protection: sealed round (a validated terminal item exists among the *published* items, captured or not), closed round (`:closed-at`), superseded round (newer round names the child). Refusal precedence is superseded > sealed > closed, so the `:newer-task` remedy survives.
- Per-item consumption: `collect`/`collect --any`/`run --wait`/`collect --wait` return the oldest unconsumed item; per-item capture state on the ledger entry.
- Guard generalisation through one shared stream-state function (published/captured/sealed) consumed by `close`, `close --settled`, `orphans`, `continue`, `prune`, `compact`, `collect --any` candidacy, and the publish discharge guard.
- Deletion of `oh task progress`: verb, `:progress` ledger field, prompt clause, contract.md § Progress, SKILL.md and persona references; throttle env var renamed and repointed at WAITING publishes.
- Docs: contract.md, SKILL.md, scripts/README.md, CLI usage string, packaged persona guidance.
- Tests: `bb test` matrix over single-item and multi-item rounds; fake-herdr scenarios; smoke update.

*** Out of scope
- One-entry-per-child ledger model and any explicit parent cursor field (rejected -- see Decisions).
- A monitor stop-signal verb: closing a child that never settles stays a manual prompt-then-close (see Risks, Open questions).
- The pi `/fork` sibling exploration.
- Spawn, kind/model resolution, placement, focus, retro gating, and orphans semantics beyond consuming the shared stream-state predicate.
- Ledger migration tooling: pre-change entries are scratch state and must merely remain readable.

** Acceptance

*** Core functionality
- [X] A round accepts multiple published items; each is its own immutable one-shot file via `Files.createLink`, and no verb overwrites or deletes one.
- [X] `STATUS: WAITING` validates as non-terminal; `COMPLETE`/`FAILED`/`BLOCKED` remain the only terminal statuses.
- [X] `publish` refuses a new item once a validated terminal item exists for the round.
- [X] `publish` refuses items on a round carrying `:closed-at`.
- [X] `publish` refuses items on a round superseded by a newer round for the same child.
- [X] `collect` returns the oldest unconsumed item and records per-item capture state on the entry.
- [X] `collect --any` splits capture candidacy ("round with unconsumed items") from wait candidacy (a live round that has published nothing is still polled), so `--any --wait` keeps blocking until a child publishes; the `failed` exclusion is preserved. Amended during implementation -- the original single-noun wording was read as governing both, and shipped a regression that stopped fan-in waiting.
- [X] `run --wait` and `collect --wait` return on the first unconsumed item, terminal or not.
- [X] A capture result states terminality explicitly, so a WAITING capture is unambiguously non-final.
- [X] `close` and `continue` require every published item captured, plus the unchanged ownership/newest-round/liveness/settle guards.
- [X] A round whose only item is terminal behaves as today across `run`/`collect`/`close`/`continue`/`prune`/`compact`.
- [X] `oh task progress` is removed: verb, `:progress` ledger field, composed-prompt clause, contract.md § Progress, SKILL.md references.
- [X] The renamed publish throttle applies to WAITING items only; a terminal item is never throttled.
- [X] A WAITING publish emits the operator toast only -- no advisory parent push; terminal publish side-effects are unchanged.
- [X] Existing personas and the manual-fallback publish need no change: a single terminal envelope with no `WAITING` anywhere remains fully valid.

*** Edge cases
- [X] An item failing validation records `invalid` but does not seal the stream; a subsequent valid item captures normally.
- [X] The publish discharge guard treats an unsealed live child round as open: a delegating parent cannot publish past its own monitor.
- [X] `compact` drops raw envelope text for every item of the round, not only the newest.
- [X] `prune`'s staleness proof generalises to "no items on disk".
- [X] A pre-change ledger entry (single `RESULT`, no item records) reads correctly as a stream of length 1.

*** Anti-criteria
- Must not: allow any verb or status to retract, replace, or reopen a validated terminal item.
- Must not: make terminality a parent judgement -- it stays derivable from the newest validated item's status alone.
- Must not: change the one-entry-per-round ledger identity model (`newest-round`, ownership, `:continues` lineage all survive).
- Must not: retain a `progress` alias or compatibility shim.
- Must not: reintroduce child-side ledger writes.

** Decisions
- Chose stream-per-round generalisation :: rounds, `:continues` lineage, and every identity-keyed guard survive; today's model becomes the special case "stream of length 1", so single-item rounds are regression-testable against current behaviour.
  Rejected:
  - One-entry-per-child plus parent read cursor (the task body's proposal): audited at HEAD, it re-expresses ~9 load-bearing guards that all key on per-round entry identity plus the single RESULT file -- `any-candidates` (boolean `:captured-at`), `newest-round`/`newest-rounds` (shared by close, sweeps, continue, discharge), `capture!` (unmemoised single-file re-read), `prune!` ("no RESULT on disk" staleness proof), `publish!` (one-shot `createLink`, `stale-identity-hint`), `assert-children-discharged!`, `progress!`, `compact!`, and the settle assumption. A migration of machinery phase 1 just stabilised, for no capability the stream model does not deliver.
  - `DONE:` marker orthogonal to STATUS: a status/done cross-product to reason about; STATUS alone carries terminality (user: keep simple).
  - `progress` deprecation alias: preserves the two-message-type confusion this change removes; nothing outside this repo consumes the verb.
- `WAITING` is the sole non-terminal status :: apt for resident/monitor semantics; terminality keys on the status set exactly as today, so mechanical terminality is unchanged in kind.
- `invalid` is no longer terminal for the round :: today's terminality of `invalid` was an artifact of the one-file design (the file could never become valid) and permanently wedged a round over a typo. A malformed item never seals; the child publishes a corrected item next. The invalid item stays recorded for audit.
- Child-side ledger writes are eliminated :: `progress` was the only child-side ledger mutation and carried the one documented lost-update race (progress vs capture). Post-change the child only ever creates immutable item files; every ledger write is parent-side, and the contract.md race note is deleted rather than re-expressed.
- Sealing is stream finality, never pane lifecycle :: a terminal item ends the *round's* stream and nothing else; capture still closes nothing, the child stays resident after publishing `COMPLETE`, and the parent may -- often should -- retain it and `continue` with a follow-up round rather than rebuild the same context in a fresh spawn.
- Close does not require a sealed stream :: it requires all published items captured plus the existing liveness/settle guards, so a monitor idle between WAITING reports is closable without a terminal item. Terminality governs the stream's finality, not closability.
- Ledger head stays stable :: `:status`/`:envelope` keep reflecting the newest captured item (the `record-session!` newest-under-stable-key precedent), with per-item records beside them, so existing readers (`status`, `list`, resume tooling) keep resolving through the same keys.
- Blocking waits return on the first unconsumed item :: one primitive, no policy in the tool; an early WAITING return is the parent's cue that it spawned a streaming child.
- WAITING side-effects are toast-only and throttled :: a chatty monitor must not prompt-spam the parent agent; the parent polls or collects when it cares. Terminal side-effects (toast + advisory push under non-blocking) are unchanged.

** Risks
- A busy monitor is unclosable until it settles: `close` still requires `idle`/`done`, so a child mid-event-loop is `retained`. Accepted -- monitors are a low-priority corner; the remedy is prompt-a-stop then close.
- WAITING capture mistaken for completion by an orchestrating parent. Mitigated: explicit terminality on the capture result plus SKILL.md/persona rewording from "validated result" to "validated terminal result".
- Guard drift while generalising ~9 predicates. Mitigated: single shared stream-state function and a test matrix that pins single-item-round behaviour to today's.
- Unbounded stream bulk from a chatty child. Accepted with bounds: the throttle caps rate, `ORCH_MAX_STREAM_ITEMS` and the envelope byte limit cap a single snapshot, and `compact` retires every item's raw text.
- Publication is not serialised against `close`/`continue`. Accepted, with a follow-up task. The settle-wait rechecks narrow the window but cannot close it: `publish` creates its item file independently of `ledger/update!`, so an item can still be created after the recheck and before `herdr/close!` records `:closed-at`, or before a `continue` successor entry is written. Closing it needs interprocess exclusion shared by publish and the lifecycle verbs, which is larger than this record's scope; the pre-change design carried a comparable publish-versus-close race, so this is not a regression introduced here. Identified by the third closeout review (`.tmp/reviewer-868b1e34-closeout.md`).
