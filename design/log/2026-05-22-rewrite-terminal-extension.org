* Summary

Build a small tmux-focused pi extension that assumes pi is already running inside tmux and exposes one grouped slash command, `/tmux`, for spawning sibling windows and temporarily joining one of those windows below the current pi pane. The extension should not try to replace a terminal multiplexer; it should be a thin, predictable tmux command layer with clear failure messages when `$TMUX` or `tmux` is unavailable.

** Decisions
- Implement as a pi extension under `pi/extensions/tmux/` (directory layout: `index.ts` + `README.md`; no `package.json` unless npm deps later become necessary). Prompt templates/skills cannot reliably perform live tmux side effects or maintain joined-pane state.
- Use canonical slash command `/tmux <subcommand>`. Committed subcommand surface: `spawn`, `watch`, `join`, `break`, `list`, `tail`.
- Command args after the subcommand are joined into a single shell command line and handed to tmux (e.g. via `tmux new-window <shell-cmd>`); no argv parsing beyond the subcommand split. Quoting expectations match `!`-bash usage.
- `/tmux watch <cmd>` runs in a non-interactive shell wrapper. The parent wrapper ignores SIGINT, but the child command runs in a subshell that restores default SIGINT handling: `trap '' INT; (trap - INT; sh -c "$cmd"); status=$?; …; sleep infinity`. First Ctrl-C cancels the user command; second Ctrl-C terminates the wrapper and closes the window.
- Window name for `spawn`/`watch` = the trimmed command truncated to 20 chars, with tmux `automatic-rename` disabled on the new window so child processes do not overwrite it.
- Multi-pane target windows are refused for `/tmux join` initially. Moving only the active pane out of a multi-pane window is surprising; revisit only if a real use case appears.
- Project-local extension only. Not registered in the root `package.json` `pi.extensions` array for `@cormacc/agent-org-memory`, because tmux integration is out of scope for the org-memory package.
- Pane output is in scope. The extension records the `pane_id` (`%N`) and `window_id` of each `spawn`/`watch` window it creates, exposes `tmux_list` so the agent can discover known panes/windows, and exposes `tmux_capture` so the agent can read pane output without visually joining the pane. `tmux_capture` may default to the latest watched pane for the current pi pane when target is omitted.
- Ships a companion skill at `skills/pi-tmux/SKILL.md` registered via the extension's `resources_discover` hook (mirrors how the org-memory extensions ship their skills). The extension provides capability; the skill teaches the agent when to use spawn vs watch vs capture, and the subagent-via-spawn pattern.
- Launching a sibling pi instance is a first-class documented pattern using the generic `/tmux spawn` (e.g. `/tmux spawn pi --model <m>`). No dedicated `/tmux subagent` subcommand initially; revisit if a fixed shape emerges. Cross-references `pi-intercom` for talking to the spawned instance.

** TODO Implement join/break secondary-pane workflow
:PROPERTIES:

Acceptance criteria:
- `/tmux join <window-index-or-id>` joins a single-pane target window as a secondary pane below the current pi pane (`join-pane -s <target> -t <pi-pane>`); refuses if the target is the same window as the pi pane, is not in the same session, or has multiple panes.
- Re-running `/tmux join …` first runs the equivalent of `/tmux break` for any currently-joined secondary pane belonging to this pi pane, then joins the new target.
- `/tmux break` returns the joined pane to its own window via `break-pane`, preserving the running process. Bare `/tmux break` uses in-memory state; `/tmux break <pane-id>` is an escape hatch after restart or state loss.
- `/tmux list` prints the session's windows (index, name, pane count, known spawned/watched pane ids, whether currently joined to this pi pane) using `ctx.ui.notify` or a small renderer.
- The extension tracks per-pi-pane joined-target state in memory keyed by `$TMUX_PANE`. State is not persisted across pi restarts; bare `/tmux break` after a restart is a documented no-op, but `/tmux break <pane-id>` can still operate on an explicit target.

* Implementation

- Added `pi/extensions/tmux/` with `index.ts`, `helpers.ts`, `index.test.ts`, `test.sh`, and `README.md`.
- `/tmux` command registers the committed subcommands (`spawn`, `watch`, `join`, `break`, `list`, `tail`) and dispatches through `pi.events` listeners; event handlers use the current session context captured on `session_start`.
- `spawn` / `watch` create tmux windows with `new-window -P -F` so `pane_id`, `window_id`, and `window_index` are retained in memory per owner pi pane. Window names are derived from the first 20 chars of the command; `automatic-rename off` is best-effort because short-lived commands may exit before the option write.
- Watch wrapper implementation changed from the planned pure-shell trap shape to a Node one-liner after tmux smoke testing showed non-interactive shell traps still allowed the pane to close on first Ctrl-C. The Node wrapper spawns the child command, forwards the first SIGINT to the child, prints status, then exits on the second SIGINT.
- `tmux_list` and `tmux_capture` tools expose window/pane discovery and bounded `capture-pane` output to the agent. `tmux_capture` defaults to the latest watched pane for the current pi pane when available.
- `join` refuses same-window, cross-session, and multi-pane targets; bare `break` uses in-memory state and explicit `break <pane-id>` is available after state loss.
- Added `skills/pi-tmux/SKILL.md` and registered it via `resources_discover`; the skill covers long-running watchers, pane capture, sibling pi spawning, and delegates inter-session communication semantics to `pi-intercom`.

* Open questions

** OPEN Should join/break state persist across pi restarts?
Current decision is no — join state is in-memory keyed by `$TMUX_PANE`; after a pi restart bare `/tmux break` is a no-op. `/tmux break <pane-id>` remains available as an explicit escape hatch. Revisit persistence if this proves annoying in practice; recovery could be done by snapshotting joined target ids via `pi.appendEntry` on `session_shutdown` and rehydrating on `session_start`.
