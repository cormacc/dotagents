* Intent
Make org-task configuration and task-graph mutations consistent across Emacs, pi, and =ot=, while keeping machine envelopes compact and eliminating the remaining need to hand-edit existing task tags. Preserve one canonical writable task node across root, local, archive, and imported plan files, and document/test the machine output produced by this repository.

* Summary
*Level:* production · *Tests:* comprehensive · *Docs:* full

** Scope
*** In scope
- Recursively expand every in-project =#+SETUPFILE:= declaration for pi task/Jira configuration in declaration order, with bounded depth, cycle protection, sandboxed path resolution, and Org first-declared-wins lookup semantics.
- Remove Jira's bespoke =local > shared > setup= merge and consume the same effective Org content/order as the tasks extension.
- Resolve =task:<UUID>= blockers against the complete loaded graph, including open blocker tasks owned by =#+IMPORT:=-linked plan files, and keep blocker list text/JSON views consistent.
- Make JSON/EDN mutator task projections omit whole-file =sourceContent= and =effectiveSourceContent= by default; expose an explicit =--include-content= opt-in and retain source data wherever a command's documented contract genuinely requires it.
- Add idempotent =ot tag add|remove <id> <tag>= mutations for tasks in root/local task files and imported plan files, preserving heading structure, unrelated tags, and source locality.
- Update the living CLI, machine-contract, task-extension, and Jira-extension documentation named by =#+SPEC:=.
- Sequence execution as follows: first perform a serial contract/foundation check covering graph traversal, =task->wire= projection defaults, registry option plumbing, tag grammar, and current dirty-worktree overlap; then assign the four outcome tasks to parallel workers because SETUPFILE/Jira, blocker resolution, envelope projection, and tag mutation have separable primary files; finally run the integration task serially after all four workers land, reconcile shared registry/docs/test fixtures, and execute focused suites before the complete =bb test= and pi extension test scripts.

*** Out of scope
- Changing Org's native keyword precedence, supporting remote/out-of-project setupfiles, or replacing the existing project-root sandbox.
- Redesigning blocker syntax, readiness policy, task import ownership, or archive/publish semantics.
- Removing task bodies/descriptions or other task-level fields from machine output; only duplicated whole-file content is suppressed by default.
- Creating, renaming, filtering, or editing tags through the TUI/pi overlay beyond any minimal parity wiring required by the established mutation-surface contract.
- Bulk-normalising existing headings/tags, changing tag inheritance, or adding tag taxonomy policy.
- Refactoring the parser, loader, or command families beyond the seams required by these outcomes.

*** Edge cases
- [ ] A setupfile diamond or cycle is expanded at most once per canonical resolved path and produces deterministic first-declared-wins lookup results.
- [ ] Duplicate UUID prefixes still fail as ambiguous; blocker resolution uses the blocker's full UUID semantics and does not silently bind to an unrelated prefix.
- [ ] Imported-plan mutations keep optimistic-concurrency checks and atomic writes; a changed-on-disk owner file fails with =conflict= and remains untouched.
- [ ] Removing the final tag emits a heading without a dangling colon suffix; tags containing whitespace, colons, or Org-invalid characters cannot corrupt the heading.
- [ ] =--dry-run= returns the same compact/opt-in envelope shape as a real mutation and performs no write.

*** Anti-criteria
- Must not silently remove task descriptions or make content opt-in unavailable to machine callers.
- Must not read a setupfile outside the resolved project root or weaken =paths.clj= sandboxing.
- Must not resolve blockers from TASKS.org alone when the graph includes imported tasks, and must not duplicate a plan task into a root file to make it resolvable.
- Must not rewrite unrelated org content, reorder tags, or normalise task subtrees beyond the existing serializer guarantees.
- Must not add a new runtime dependency or use JVM-only APIs; =ot= remains Babashka-compatible.

** Decisions
- Maintain backward compatibility for reading and updating existing TASKS.org and imported org files. The skill, =ot= CLI, pi integrations, and their JSON/EDN envelopes are a closed-loop, repository-internal surface that may evolve together when the implementation, documentation, and tests are updated in the same change. Rejected: treating =org-tasks/v1= as an external compatibility promise.
- Use one effective-content model for pi tasks and Jira: recursive setup expansion provides an ordered content stream, and keyword/link lookup takes the first declaration. Rejected: retaining Jira's three-bucket merge, because it duplicates Org precedence and cannot represent arbitrary chains.
- Reuse the existing =resolveProjectPath= boundary and an explicit visited set plus =MAX_SETUPFILE_DEPTH=; canonical resolved paths are the cycle identity. Rejected: raw-target cycle detection, because aliases can name the same file.
- Resolve readiness dependencies through the same complete graph traversal used by ID-accepting commands. Rejected: special-casing DONE imported blockers or loading plan files on demand inside =ready=, because both create state-dependent resolution semantics.
- Change =task->wire= call-site/default policy so mutators explicitly opt into raw content through the registry's existing =include-content= option; retain =ot list='s path-keyed =sources= contract. Rejected: post-serialization key stripping, because nested tasks can still leak duplicates and command contracts become implicit.
- Implement tags as a property-command-style command family mutation backed by a parser-owned task-heading/tag setter and the normal graph save path. Rejected: direct line regex replacement in the command handler, because it bypasses parser invariants and imported-file concurrency handling.
- Preserve the four migrated UUIDs as the outcome work units. Add one blocked integration task rather than forcing ordering among independent implementations.
