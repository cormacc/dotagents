* Intent
Teach org-plan to treat optional in-repo specification documents as a first-class planning input and closure output: discover the living specs a task touches, list impacted specs in the plan, and update them at closure — without duplicating the existing per-record `#+SPEC:` mechanism.

* Summary
*Level:* MVP · *Tests:* smoke · *Docs:* README · *(README here = skill docs: org-plan SKILL.md + change-record-format.md + org-tasks SKILL.md.)*

Add a project-level spec-discovery convention using a single `#+SPEC:` keyword. In TASKS.org it declares where the living specs live (repo-wide discovery roots); in a change-record it lists the specs relevant to that task. The keyword carries its value as a bare `[[proj:PATH]]` org-mode link so paths are directly navigable in Emacs from TASKS.org and from any record. Discovery is *rooted and transitive*: each `#+SPEC:` entry (and the implicit specs) is a root, and sub-specs linked from a root are pulled in automatically. Spec support is entirely optional — projects with no specs are unaffected. Scope stays doc-driven (a skill convention the planning agent performs) plus `ot doctor` guards (dangling `#+SPEC:` path; malformed non-link spec value) and a one-off migration of existing `#+SPEC:` entries to link form.

** Scope
*** In scope
- New `#+SPEC:` keyword in TASKS.org: zero or more entries, each a bare `[[proj:PATH]]` org link to a spec **file or folder**; folders are included recursively. Optional; default root `[[proj:design/SPEC.org]]` is used when present and no `#+SPEC:` is declared.
- `#+SPEC:` values (in both TASKS.org and records) use the **bare `[[proj:PATH]]` link format** (repo-root relative, navigable in Emacs). Strict: the labelled `[[proj:PATH][label]]` form and bare non-link paths are rejected as malformed by `ot doctor`.
- Migration: convert all existing plain-path `#+SPEC:` entries in this repo's records to `[[proj:PATH]]` (strict parser is a flag-day, so no bare-path entries may remain).
- Specs may be org, markdown, or implementation files (in this repo, the skills themselves are specs).
- **Implicit/automatic specs** (always considered, no `#+SPEC:` needed): repository-root `README.*` (any extension, e.g. `README.org`/`README.md`), repository `AGENTS.md`, and skills under `.agents/skills`.
- **Transitive/rooted discovery**: from each root (declared `#+SPEC:`, folder-discovered file, or implicit spec), follow links to sub-specs and include them; sub-specs need no `#+SPEC:` entry of their own. Requires a visited/cycle guard; link resolution is relative to the linking document.
- Planning step: identify impacted specs from the discovered set and record them (this reuses/extends `#+SPEC:`, which is the planning-time impact declaration mirrored in `*** In scope`).
- Closure step: update impacted specs to reflect the change scope; extend org-plan's closure checklist accordingly.
- `ot doctor`: warn when a TASKS.org `#+SPEC:` path does not resolve on disk; warn when any `#+SPEC:` value is not a bare `[[proj:PATH]]` link (malformed). `check-spec` extracts the path from the link before its git changed-set comparison.
- Contract-doc impact: `skills/org-plan/SKILL.md`, `skills/org-plan/references/change-record-format.md`, `skills/org-tasks/SKILL.md`, `skills/org-tasks/references/ot-cli.md`, and `ot doctor` code + tests are expected to change.
*** Out of scope
- Bidirectional spec→record backlinks as a *requirement* (allowed but not mandated; see Decisions Q2).
- Supporting `file:`-relative or bare-path spec values (rejected in favour of `proj:` link-only; see Decisions Q5).
- A dedicated `ot spec list` / spec-crawl command in the CLI (YAGNI; see Decisions Q3).
- Any opt-out keyword for implicit specs (convention only; see Decisions Q4).
- `ot doctor` following/validating spec *links* transitively (MVP validates only the top-level `#+SPEC:` path resolves; see Open questions).
- A separate `#+SPECROOT:` keyword (rejected; see Decisions Q1).
- Auto-editing spec files; closure spec updates remain an agent/human task.

** Decisions
- Q1 — Single `#+SPEC:` for file OR folder, disambiguated by filesystem stat :: One keyword matches the existing single-keyword `#+SPEC:` style; `ot doctor` reconciliation stays file-level via `#+SPEC:`, so folders add no doctor complexity. Discovery aggregates a spec set via three coexisting mechanisms — file path, recursive folder, and transitive link-following from roots.
  Rejected:
  - Separate `#+SPECROOT:` for folders: extra keyword, extra parser branch, no real disambiguation benefit over a stat check.
- Q2 — One-directional record→spec linkage via `#+SPEC:` :: Reverse lookup is cheap (`rg SPEC <path> design/log/` + git log); non-org specs (AGENTS.md, markdown, third-party impl) cannot reliably carry org backlinks. An org pointer back to a record is *allowed* but never required.
  Rejected:
  - Mandatory bidirectional backlinks: high maintenance cost, staleness risk, impossible to enforce uniformly across spec formats.
- Q3 — Doc-driven skill convention + one small `ot doctor` dangling-`#+SPEC:` warning :: Couples to existing contracts, ships fast, adds minimal CLI surface.
  Rejected:
  - Doc-only, zero `ot`: loses the cheap staleness guard.
  - Full `ot spec list` / link-crawler: YAGNI for current needs.
- Q4 — Implicit specs (repository-root `README.*`, `AGENTS.md`, `.agents/skills`) as documented convention, no opt-out keyword :: Adjustable via guidance; nothing hardcoded or enforced in `ot`.
  Rejected:
  - Opt-out keyword: premature configurability with no demand.
- Discovery is rooted/transitive :: A `#+SPEC:` entry names a root; linked sub-specs are included without their own entry. This is an agent-performed convention, not an `ot` crawler.
- Unify `#+SPEC:` across TASKS.org and records :: The intent is identical: a curated list of relevant specification documents. Scope is disambiguated by context — TASKS.org lists repo-wide discovery roots; a change-record lists task-relevant specs. Impact is a closeout determination recorded in `** Shipped`, so the old `_IMPACT` suffix overclaimed. Rejected alternative: keep separate discovery and per-record keywords.
  Rejected:
  - Unify both under `#+SPEC:` everywhere: conflates input/output semantics, forces `ot doctor` to branch on file type to pick dangling-path vs impact-reconciliation checks, and breaks the existing keyword plus every record already using it — for marginal naming economy.
- Q5 — Both keywords carry a bare `[[proj:PATH]]` org link :: Directly navigable in Emacs; `proj` is repo-root relative from both TASKS.org (`#+LINK: proj file:%s`) and records (`file:../../%s` via setupfile), so the text keeps a clean repo-relative path the doctor strips before its git comparison.
  Rejected:
  - `file:`-relative links: force ugly `../../` prefixes in records and make the doctor normalise them.
  - Supporting both `proj:` and `file:`: extra parser branches for no user benefit.
- Q6 — Strict link-only parser + migrate all existing records (flag-day) :: Simplest, most uniform parser; `ot doctor` flags any residual bare-path value as malformed so nothing silently un-migrates. Existing records are bulk-converted in this task to dogfood.
  Rejected:
  - Lenient parser accepting both bare paths and links: indefinite dual-format ambiguity; weaker doctor signal.
- Q7 — Bare `[[proj:PATH]]` only; reject the labelled `[[proj:PATH][label]]` form :: One canonical shape; path is its own label; simplest extraction. `ot doctor` treats the labelled form as malformed.
  Rejected:
  - Allow optional labels: two shapes to parse and lint for cosmetic gain.

** Risks
- Link-syntax ambiguity (from premortem: agent under- or over-discovers sub-specs). Mitigation: docs enumerate the exact recognised link syntaxes and MVP boundary (plan task 2).
- Recursive folder discovery over a large tree is expensive / noisy. Mitigation: convention favours narrow roots (e.g. `design/SPEC.org`) and the repo's skills, not whole-repo roots; note in docs.
- `#+SPEC:` discovery-vs-relevance usage confusion (which context applies). Mitigation: explicit context labelling in change-record-format.md (plan task 3).
- Flag-day strict parser breaks any record not migrated (from premortem). Mitigation: `spec-value-malformed` doctor finding surfaces stragglers; migration task a9742bbf converts all in-repo records and is verified by `ot doctor`.
- Changing `check-spec` behaviour may break its existing tests. Mitigation: task 79d2ad9f updates the tests alongside the parser change.

** Follow-ups
- Possible later: `ot doctor` transitive link validation and/or an `ot spec list` helper if manual discovery proves error-prone (see Open questions).
