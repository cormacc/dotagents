* Intent
Make "what's the selected task / its plan?" answerable in one cheap `ot`
call instead of multiple raw file reads, and stop the agent-facing surface
(both `ot show` output and the extension's registered tools) from carrying
context the agent never uses.

* Summary
*Level:* production · *Tests:* thorough · *Docs:* README + skill + contract

** Scope
*** In scope
- Strip `sourceContent` / `effectiveSourceContent` from `ot show` / `ot selected` JSON.
- Enrich `ot show` to the documented one-shot resume shape (ancestors + record metadata block).
- Rewrite the `org-tasks` skill resume path to lead with `ot show selected --format json`.
- Remove the three agent-facing pi tool registrations (`tasks_insert_task`, `org_read_section`, `tasks_scan_summaries`); keep the JS `insertTaskIntoFile` primitive.
- Reconcile `scripts/docs/contract.md` `show`/`selected` schema with the shipped shape.
*** Out of scope
- Changing `ot list` (already content-deduped via `result.sources`) or the extension's overlay/widget data path.
- Tracker-specific (`jira`) behaviour beyond confirming its JS import still resolves.
- The tree-sitter org-extension extraction (`f361c429`) itself — only its claim on `org_read_section` is touched here.
- Backfilling richer `ot show` data into `ot status` / `ot create` payloads.

** Decisions
- Drop embedded source content from `ot show` entirely rather than dedup into a `sources` map ::
  `ot show` has no internal consumer (extension uses `otList`; `jira` imports the JS fn). Link
  templates / linked issues are already pre-resolved into wire fields, so raw content is dead weight.
  Rejected: mirror `ot list`'s `sources` map — adds a field no `show` caller needs.
- Gate any raw-content escape hatch behind opt-in `--include-content` (default off) ::
  preserves a path for a hypothetical future consumer without taxing the common case.
- #4: eliminate all three registered tools; rely on `ot <cmd> --format json` via Bash, which the
  skill already documents ::
  biggest persistent-context win (~7KB of tool schema) with ~zero added skill bloat (commands
  already in the quick reference). Single source of truth = the CLI.
  Rejected:
  - Consolidate into one `tasks` passthrough tool: still ships a shell-shaped schema and an
    indirection layer that re-parses args the CLI already parses; net negative vs Bash+`ot`.
  - Keep as-is: ~7KB persistent tool schema for wrappers the skill already covers.

** Shipped
- `ot show` / `ot selected` omit raw source strings by default, with `--include-content` as the explicit escape hatch.
- `ot show` now returns `ancestors` plus `record` metadata (`path`, top-level sections, `hasContext`, `hasOpenQuestions`) for resolvable change-record imports.
- `org-tasks` resume guidance now starts from `ot show selected --format json` and uses `ot section` for the linked record summary/context path.
- The tasks extension no longer registers `tasks_insert_task`, `org_read_section`, or `tasks_scan_summaries`; README points agents to `ot create`, `ot section`, and `ot scan`.

** Gotchas
- `linkedIssues` still resolves without emitted raw content because `task->wire` computes it from internal `:effective-source-content` before applying the `include-content?` output gate.
- `insertTaskIntoFile` remains the JS primitive for Jira/direct integrations; only the agent-facing tool registration was removed.
- Existing selected work in an imported plan may not itself carry a `#+IMPORT:`; record metadata is guaranteed for tasks with an import-bearing ancestor in the loaded graph, and top-level roots with imports are the canonical resume path.

** Follow-ups
- None outstanding (f361c429 coordination decided — see `* Open questions`).
