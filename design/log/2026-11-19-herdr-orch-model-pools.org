* Intent
Let a primary Pi session choose a model or a model pool by quota, and start on the account with the most spare credit, while Pi's own default model stays the user preference. Model pools become a config section of their own, so that a set of interchangeable models is not a special form of alias and can be ordered for inference.

* Summary
*Level:* production · *Tests:* thorough · *Docs:* README

All three plan tasks are implemented and tested; not yet committed. Pools replace vector aliases (`:pools`, ranked 1 to 4 in the packaged config), `/oh model` replaces `/oh tier` with a quota-annotated picker, and a new primary session starts on the account (or, with `:pi {:default-model-pool true}`, the pool) that the policy chooses for Pi's default model. Live check (2026-11-19 14:15, RPC `get_state`, no prompt): Pi's default `anthropic/claude-opus-5-5` started on `anthropic-1/claude-opus-5-5`; `settings.json` kept `anthropic/claude-opus-5-5`.

** Scope
*** In scope
- A `:pools` config section: `{"heavy" {:rank 1 :models [{:model "fable" :rank 1 …} …]}}`. Pool `:rank` is optional; candidate `:rank` is unchanged.
- `:aliases` becomes 1-1 (string values only).
- The roster, launch routing, `oh route`, primary recovery and the child environment use pools instead of vector aliases.
- `/oh model <model|pool>` and `/oh model clear`, replacing `/oh tier`, with completion of pool names and canonical model IDs, and a quota-annotated picker for a bare `/oh model`.
- Routing of the session's starting model at `session_start` reasons `startup` and `new`, with a herdr-orch setting `:pi {:default-model-pool <boolean>}`.
- Primary routing refreshes expired accounts in-process before it asks the shared policy, as the launch loader does.
- The contract, skill README, `SKILL.md`, extension README and packaged `config.edn`.
*** Out of scope
- Changes to Pi's `defaultProvider`, `defaultModel` or `settings.json`.
- Routing at `session_start` reasons `resume`, `fork` and `reload`.
- Native Claude and Codex harnesses: they keep single-account behaviour.
- Pool-level metadata other than `:rank`.

** Decisions
- A `:pools` section, with `:aliases` limited to 1-1 strings :: each section has one shape, and pool metadata has a place.
  Rejected:
  - Map-valued entries in `:aliases` (`{"heavy" {:rank 1 :models […]}}`): keeps `:aliases` polymorphic, and a layer that replaces the entry drops its rank.
- Name `:pools`, not `:tiers` or `:roles` :: the section groups interchangeable models by any criterion; "role" already means a persona in herdr-orch (`role-absent`, "adopt that role"), and "tier" implies an order that the rank makes optional.
- `:rank` at both levels, lower first :: one precedence scheme. Candidate rank orders routing inside a pool; pool rank orders which pool claims a model for startup inference. An absent pool rank leaves the pool out of inference.
  Rejected:
  - `:weight` (higher wins) for pools: two opposite schemes in one config.
  - A default rank of 99 for unranked pools: a sentinel that still takes part in inference.
- Pool ranks are unique, candidate ranks are not :: equal candidate ranks are balanced by pace; equal pool ranks would make inference ambiguous.
- Startup setting is a boolean that reinterprets Pi's default model :: Pi's `defaultModel` stays the one user preference.
  Rejected:
  - An explicit pool name in the herdr-orch setting: a second preference beside Pi's default.
- `/oh model` replaces `/oh tier` :: the pool case of `/oh model` is `/oh tier`. The session entry keeps its `herdr-orch-tier` custom type so that existing sessions resume with their pool.
- `HERDR_ORCH_MODEL_ALIAS` becomes `HERDR_ORCH_MODEL_POOL` :: the variable is two commits old and only `oh` sets it.

** Gotchas
- Pool ranks are unique across layers, so a project pool with `:rank` must avoid the packaged ranks 1 to 4; the installed-Pi fixture uses rank 5.
- Pi appends a `model_change` entry for the starting model of every new session, so "has a model change" does not mean "continued session".
- A startup selection reports "Selected …"; a test that waits for the first notify event must skip it (`pi-integration.test.ts`).

** Risks
- If Pi does not await a `session_start` handler before it accepts the first prompt, a fast first prompt goes to Pi's default account. Task 3 establishes this first; if Pi does not wait, the first prompt still works, on the default account.
- Detecting an explicit `--model` from `process.argv` depends on Pi's flag names. Task 3 tests each flag that selects a model.
- The rename touches about 29 doc references and about 100 test fixture lines; a missed vector alias in a test fixture fails validation loudly, not silently.

* Implementation
- Pi awaits `session_start` before it accepts a prompt: interactive mode refuses submission with "Startup is still in progress" until `bindExtensions` resolves (`interactive-mode.js` `handleStartupSubmit`), and print and RPC modes await `bindExtensions` before the prompt. The installed-Pi `startup` scenario confirms it: the default account refuses every request, and the first request goes to the routed account. With the hook disabled, the same scenario fails.
- Startup routing costs one `oh roster` (about 0.4 s) and one `oh route` (about 0.25 s) call, plus any token refresh.
- The picker runs one `oh route` per item, 8 at a time (about 0.25 s each).
- Verification on 2026-11-19: `bb test` (1025 tests, 0 failures), `skills/herdr-orch/scripts/pi/test.sh` (`ok`), `pi/extensions/herdr-orch/test.sh` (exit 0, 51 recovery unit scenarios, startup scenarios `startup`, `startup-pool`, `startup-explicit`).
