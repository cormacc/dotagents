** OpenSpec model (condensed)
- MIT npm tool (=@fission-ai/openspec=). Current workflow =OPSX= (schema-driven); legacy hardcoded-template workflow deprecated.
- Two areas under =openspec/=: =specs/<domain>/spec.md= (durable source-of-truth behaviour contracts) and =changes/<name>/= (self-contained proposal.md + design.md + tasks.md + delta-=specs/=).
- Delta specs are the brownfield-first key concept: ~## ADDED / MODIFIED / REMOVED Requirements~, merged into =specs/= on archive.
- Spec format: ~## Purpose~ → ~### Requirement:~ (RFC-2119 SHALL/MUST) → ~#### Scenario:~ (Given/When/Then).
- A =schema.yaml= declares artefacts + ~requires:~ edges (enablers, not phase gates). Lifecycle is fluid "actions not phases": propose → create artefacts → apply → verify → archive. State (BLOCKED/READY/DONE) is filesystem+DAG-derived.
- CLI: =init/update=, =list/view/show=, =validate [--strict|--json]= (structural lint + archive gate), =archive= (validate → merge deltas → dated archive), workflow =status/instructions --json=, =schema=, =config=, beta multi-repo =workspace/initiative=.
- Agent loop: =openspec init --tools pi …= generates per-tool skill + slash commands; agent queries =status --json= and =instructions <artifact> --json=.

** Similarity map (highlights)
- Strong: change folder ↔ change-record; proposal.md ↔ ~* Intent~ + ~* Summary~; tasks.md ↔ ~* Plan~; =status/instructions --json= ↔ =ot=.
- Partial: design.md ↔ ~* Implementation~/~** Decisions~ (pre-hoc vs post-hoc); requirements/scenarios ↔ ~* Behavior~ + acceptance criteria (org-plan informal but *stricter*); =validate= ↔ =ot doctor= (graph-only, no section lint); archive (merges deltas) ↔ org archive (merges nothing).
- Absent in org-plan: living =specs/= corpus; delta classification.
- Absent in OpenSpec: premortem, approach-exploration/rejected-alternatives, effort line, intent reverse-engineering, anti-criteria, closure-time prune, task-graph semantics (UUID, ~:BLOCKED-BY:~, parent propagation, LOGBOOK), ~* Open questions~, ~** Gotchas~/~** Risks~.

** Net assessment
OpenSpec is broader on tooling surface and uniquely maintains a living behavioural-contract corpus; org-plan is deeper on planning craft and task-dependency semantics. Best-fitting borrowings: the merged spec-coupling feature (R1 lint + R2 delta framing + R4 linkage/verify, with =design/specs/= as a config-driven default), R3 (verify), R5 (scope heuristic). The signature spec-corpus is *not* rebuilt: org-plan couples to whatever contract layer the project already has, nudged at plan/closure time — no merge engine.

* Open questions
** DECIDED design/specs/ contents: contracts-with-no-code-home vs index-to-real-contract?
:PROPERTIES:
:DECIDED: [2026-06-04 Thu]
:END:
Decision: one source of truth per contract — authoritative prose *only* for contracts with no code/skill home; never a per-contract duplicate of one that has a canonical artifact. For code/skill-homed contracts (a skill file, =openapi.yaml=, JSON schema, schema ns, migration set) org-plan couples directly to that artifact. An optional single =design/specs/index.org= lists where each contract lives only when the surface is scattered enough that discovery is a problem. Consequence: a project whose deliverable is already a discoverable contract corpus (dotagents =skills/=) needs no =design/specs/= — hence the folder is a *fallback* default, not mandatory.
Rationale: the only failure mode worth engineering against is drift from duplicate sources of truth; portal proves even a single under-coupled doc rots, so two copies rot faster and disagree. "(a)+(b)+both" collapses under "single source of truth" to: authoritative when prose-only, pointer otherwise. Boundary test — =specs/= = normative, present-tense, current-state (rewritten in place); record ~* Implementation~ = past-tense per-change delta (append-only); =notes.org= = non-normative scratch.
** DECIDED Spec-touched detection: explicit declaration vs path inference? (revised)
:PROPERTIES:
:DECIDED: [2026-06-04 Thu]
:END:
Decision: the spec declaration is authored at *planning* time, NOT derived from ~** Shipped~. A =scout= surveys the existing contract layer to identify the specs a change is expected to impact (a =researcher= instead when the trigger is an external/new capability not yet in the repo); the result is recorded as repeated, machine-readable forward declarations (~#+SPEC_IMPACT: path/to/spec.org~) plus human-readable ~*** In scope~ bullets. Implementation works that checklist. Closure lint warns on any ~#+SPEC_IMPACT:~ path not touched in the record's git scope. Records below the threshold or without a contract layer use ~#+NO_SPEC_IMPACT: true~ as an explicit opt-out. ~** Shipped~ remains the *post-hoc* actual outcome (ADDED/MODIFIED/REMOVED), reconciled at closure, and may include *discovered* impact the planning scout missed.
Supersedes the earlier "declare via ~** Shipped~" decision, which was circular: ~** Shipped~ is LLM-authored after implementation, so a spec the agent forgot to touch is equally absent from Shipped — the check would be blind to the omission case that actually matters (cf. portal's silent =data-model.org= drift). Moving identification to planning (scout-seeded, forward-looking, prescriptive) mirrors OpenSpec's proposal→specs→implement ordering and is the only way the check catches "should have, didn't". This also rehabilitates a dedicated keyword: a pre-hoc, machine-checkable ~#+SPEC_IMPACT:~ is distinct from post-hoc prose Shipped, so the two no longer compete. Fits org-plan's existing Delegation table (scout=codebase, researcher=external) with no new machinery.
Residual: a planning scout reduces but cannot eliminate omission risk (no complete code→spec mapping); accepted — warnings-only + human review raise the floor, not guarantee completeness.
