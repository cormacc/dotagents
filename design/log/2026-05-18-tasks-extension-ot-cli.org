* Summary
Build =ot= as the portable org-tasks protocol engine and reduce the pi =tasks= extension to UI/event glue over that CLI. =ot= owns parsing, lifecycle writes, archive mechanics, selection, doctor checks, section reads, summary scans, and change-record scaffolding. The extension keeps the overlay, compact widget, keybindings, prompts, Emacs/browser integration, and agent follow-up prompts. =ot= ships as a Babashka project installable via =bbin= so third-party harnesses adopt it the same way pi does.

** Decisions
- Boundary :: Durable org-tasks protocol lives in =ot=; harness-specific interaction lives in the pi extension. Other coding harnesses use the same CLI without importing pi or TypeScript code.
- CLI implementation :: Babashka + =babashka.cli/dispatch=. Per-command spec tables give Unix-shaped options, aliases, coercion, validation, and generated help.
- Project layout :: Babashka project root at the dotagents repo root with =deps.edn= + extended =bb.edn=. CLI namespaces under =skills/org-tasks/scripts/src/org_tasks/=, entry namespace =org-tasks.cli=, tests under =skills/org-tasks/scripts/test/=. A =skills/org-tasks/scripts/ot= shell shim invokes =bb -m org-tasks.cli= for in-repo development before any install.
- bbin packaging :: =bb.edn= declares =:bbin/bin {ot {:main-opts ["-m" "org-tasks.cli"]}}=; bbin supplies the argument separator when it generates the wrapper. Third parties install via =bbin install io.github.cormacc/dotagents --as ot --latest-sha=; local development uses =bbin install <repo-root> --local/root <repo-root> --as ot=. bbin is the supported third-party install path; nothing else in the dotagents repo currently claims =:bbin/bin=, so the namespace stays clean.
- Machine contract :: Every command supports =--format json|edn=. Envelope: ={ok, schema, result, warnings}= on success, ={ok:false, schema, error}= on failure. Schema literal is ="org-tasks/v1"=. Additive fields are non-breaking; renames or removals bump to =v2=. =ot list --format json= emits both =tree= (nested) and =rows= (flat with =parentId=) so callers pick the shape they need.
- Migration strategy :: Per-command cutover. The extension switches to =ot <cmd>= only when golden fixtures and =bb test= both pass for that command. No temporary TypeScript fallback in the wrapper — when =ot= is missing, the extension surfaces a single actionable error.
- =ot= discovery :: The pi extension resolves =ot= in order: =$PATH= (covers bbin's =~/.local/bin= and Home Manager entries), then =~/.pi/agent/skills/org-tasks/scripts/ot=, then =~/.agents/skills/org-tasks/scripts/ot=. The same resolution applies in any other harness that vendors the skill.
- Jira clone path :: =insert.ts= survives as a thin shim that shells out to =ot create --linked-issue ...=. =jira_clone_apply= keeps its current JS import surface, so the jira extension does not need a coordinated cutover.
- Emacs companion orthogonal :: =emacs/tasks-org/= continues to edit org files directly. =ot= and Emacs operate on the same files; nothing under =emacs/= changes as part of this refactor.

* Context
The current =tasks= extension mixes three concerns: org-tasks protocol semantics, agent-facing tools, and pi-specific TUI workflow. Prior work already established clean seams for protocol helpers (=insert.ts=, =section.ts=, =scan.ts=) and documented that generic org primitives should outlive the tasks UI. Moving the protocol engine to a Babashka script extends that seam beyond pi: shell users, Emacs helpers, other coding agents, and CI checks can all call the same =ot= binary, and bbin makes that adoption a one-line install for any user with Babashka. The trade-off is process-boundary overhead and an initial dual-implementation period; both are acceptable because the extension batches graph reads and golden fixtures freeze the current TypeScript output as the migration target.
