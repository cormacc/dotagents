* What is this?
A harness-agnostic orchestration framework for agent-assisted development. Subagent personas and their interactions are defined independently of any one coding harness, so you can evaluate or migrate between harnesses without rebuilding your workflow. The bundled =oh= CLI absorbs the mechanical ceremony of orchestration, which keeps token and tool-call overhead down.
- define subagents per-project (in =<project-root>/.agents/subagents=) or per-user (in =~/.agents/subagents=)
- define re-usable prompt snippets (traits) per-project (in =<project-root>/.agents/subagents=) or per-user (in =~/.agents/subagents=)
- traits can be included in subagent definitions or interactive prompts (the latter for pi only, so far) using the syntax ~%my-trait~
- spawn parallel workers in independent git worktrees, with the mechanical aspects of worktree creation and reconciliation handled by skill scripts

My own use is predominantly human-in-the-loop and low-fanout -- subagents for context and token-cost management rather than parallel development by swarms. That is preference, not prescription: the skill is written so other orchestration models can be built on top of it with appropriate persona definitions.

Developed primarily against =pi=, and verified against =claude code= and =codex=. Additional harnesses are configurable (§ Harness configuration).
Scripts written in babashka (clojure).


* Subagent lifecycle
The parent owns both ends of a round: it decides where the child works, and it owns everything the child produces.

- Target :: The parent resolves exactly one checkout before the child exists -- the caller's own checkout, an existing attached checkout in the same repository (=--worktree <path>=), or a managed checkout (=--worktree new=). With no flag, a read-only or first write-enabled child shares the caller's checkout, while an additional concurrent write-enabled child gets a managed one. A managed checkout is created from the source HEAD on branch =orch/<task-prefix>=, before any pane exists.
- Spawn :: =oh task run= blocks for the result; =oh task start= returns immediately. The child's cwd is the resolved checkout, and that cwd is the only child state the target affects: topology is never communicated through the persona, and the child carries no commit permission.
- Publish :: =oh task publish= appends immutable result items to the round's stream -- interim reports and monitor observations included -- and a terminal status (=COMPLETE=, =BLOCKED=, =FAILED=) seals the round. Publication is also the commit gate: from a non-shared checkout it mechanically stages and commits pending nonignored changes and records the resulting tip as =CHECKPOINT=, so recovery never depends on the child having been instructed to commit. From the shared checkout it never touches Git. A read-only child holding dirt is refused, not committed.
- Collect and reconcile :: =oh task collect= captures published items, and =collect --any= takes whichever in-flight child publishes first. For a child with its own checkout, =collect=, =status=, and =oh worktree list= also report base, branch, tip, and checkout state, keeping committed, dirty, and ignored paths as three separate sets, because each calls for a different parent action.
- Close, continue, or tear down :: Capture never closes a pane. =oh task close= closes a settled child's pane, while =oh task continue= assigns the same child another round and carries its checkout identity forward without re-resolving topology. =oh worktree remove= deletes only a managed checkout, and only when it is owned, unreferenced, and clean. The branch always survives.

Integration is the parent's work. =oh= never merges, rebases, pushes, deletes a branch, or commits in the shared checkout. Isolation keeps concurrent writers out of each other's index, but it does not prove their edits compose, so the parent still remeasures the combined tree. Retained =orch/*= branches accumulate until the parent integrates or deletes them.

[[file:scripts/docs/contract.md][contract.md]] owns the mechanics: § Worktree reconciliation and teardown for the reconciliation shape, the removal guards, and recovery when =.tmp/= was cleared before a child published, and § Close for the closure guards.



* How do I use it?

** Requirements

- [[https://babashka.org][babashka]] on =PATH= -- the =oh= CLI is Clojure/babashka.
- The =herdr= binary, and =HERDR_ENV=1= in the environment (i.e. running inside a Herdr pane).
- Optional: the =org-plan= and =org-tasks= skills in this repository complement it but are not required.

Herdr itself is the authority for direct pane and agent operations. The [[https://github.com/ogulcancelik/herdr/blob/master/SKILL.md][upstream Herdr skill]] is vendored here at [[file:../herdr/SKILL.md][skills/herdr/SKILL.md]] for convenience, but the CLI path does not need it, so standalone installs work without it.

** Installation

#+begin_src shell
npx skills add https://github.com/cormacc/dotagents/tree/main/skills/herdr-orch
#+end_src

** Configuration file locations and fallback strategy

Two independent chains, both resolving project > home > packaged:

| What | Locations, highest precedence first |
|---+---|
| Persona definitions (=<name>.md=) | =<git-root>/.agents/subagents/=, =~/.agents/subagents/=, this skill's =subagents/= |
| Model and harness config (=config.edn=) | =<git-root>/.agents/subagents/=, =~/.agents/subagents/=, this skill's =subagents/= |

They differ in how they combine. A persona definition *shadows* atomically by name -- the highest-precedence file wins outright. =config.edn= files are *merged* (§ Model configuration).

=~/.agents/subagents/= is reserved for genuine home overrides. Packaged definitions are never projected into it. A missing override file is ignored. A missing packaged =config.edn= is fatal.

Assignment state (ledger, result files) lives under =<assignment-root>/.tmp/herdr-orch/=, never =.agents/= -- see § Where assignment state lives for why that matters.

** Defining subagents

A persona is a Markdown file with frontmatter. =name= and =description= are advisory. The CLI reads =kind=, =model=, =spawns=, and =retro=. Everything after the frontmatter is the persona's instructions.

#+begin_src markdown
---
name: scout
description: Fast codebase reconnaissance - maps existing code and conventions
model: light        # weight alias or canonical ID; omit to inherit
kind: claude        # omit to inherit the parent's harness
spawns: scout       # whitespace-separated allow-list; omit for a leaf
retro: false        # omit to use the installation default
---

# Scout Agent

<the persona's instructions>
#+end_src

All four keys are optional. Omitting =kind= is usually right: the child then inherits the harness Herdr measured for the parent. =kind= is the *only* place a harness is chosen -- no flag, no env var -- because which CLI a child runs is a deployment property, not a per-assignment dial like =model=. A cross-harness comparison is a definition declaring the other harness.

** Shared directives: traits

Several personas need the same directive -- stay read-only, answer only what was asked, do not manufacture findings. Stating it once per persona means seven near-copies whose wording drifts apart. A *trait* is that directive written once, in one file, and referenced from the personas that need it.

A trait is a Markdown fragment with optional frontmatter:

#+begin_src markdown
---
name: read-only
description: Write boundary
---

Do not create, modify, or delete repository files. Consume the worktree. Never mutate it.

- You may write only to a caller-provided artifact/report path and =.tmp/=. Nothing written there ships.
- Do not run commands that mutate the repository tree.
#+end_src

A persona references it with a =%<name>= token placed where the directive belongs:

#+begin_src markdown
## Constraints

%read-only

- Do not broaden the design or replace the caller's implementation work.
#+end_src

At spawn the CLI substitutes each token in place, writes the composed persona beside the round's result file, and hands the child *that* path. Placement is the point: a directive lands in the section it governs rather than as an appendix the persona's own prose never mentions.

Resolution mirrors personas exactly -- =<git-root>/.agents/traits/= then =~/.agents/traits/= then =<skill>/traits/=, first match wins, accepting =<name>.md= or =<name>/prompt.md=. So a project can override a shipped trait by name, the same way it overrides a persona.

Rules worth knowing before you write one:

- An unknown token of three or more characters *fails the spawn*, naming the searched layers, so a typo cannot silently ship a persona missing a directive. A one or two character candidate is inert unless it resolves, which is what lets =%s= and =%h= pass through untouched in prose.
- A repeated token fails too. Personas are curated files and a repeat silently doubles a child's context.
- Code spans, fenced blocks, indented blocks, and YAML frontmatter are never scanned.
- Substitution is single-pass: text inserted from a fragment is not rescanned, so fragments cannot reference each other.
- A persona with no tokens is untouched -- no composed file, and its own path is passed through.

A trait is not free. Every child carrying one reads it in full, so the bar is a directive genuinely shared by two or more personas, not a stylistic preference. Worth testing that a directive changes behaviour before shipping it: two of the three traits here failed an adversarial check on first writing, and had to be rewritten to address the *cause* of the unwanted behaviour rather than restate the prohibition.

The idea is borrowed from [[https://github.com/xificurC/ai-behaviors][ai-behaviors]] (MIT), which composes hashtag-referenced behaviour fragments into interactive Claude Code and ECA sessions. Its mechanism -- a =UserPromptSubmit= hook injecting sticky per-turn context -- does not transfer to one-shot delegated children, and its taxonomy of modes, qualities and methods is more structure than a three-fragment store needs. What transfers is the shape: small named fragments, layered override directories, and composition at the point of use. The fragment layout here deliberately also accepts =<name>/prompt.md=, so an ai-behaviors library can drop in as a base layer unchanged.

** Model configuration

=config.edn= carries two levels, plus harness invocation and spawn defaults:

- =:aliases= -- short or weight name → canonical model ID.
- =:models= -- canonical ID → the native spelling each harness wants.

Canonical IDs use pi's =<provider>/<model>= form. The packaged defaults cover the models available on Anthropic and OpenAI subscriptions, with =heavy=, =middle=, =light=, and =feather= as the portable weight aliases. Their per-kind values are enumerated once, in [[file:scripts/docs/contract.md][contract.md]] § Model resolution.

*** The merge rule that catches people

=merge-config= is =merge-with merge=, so the merge is exactly two levels deep:

- Top-level keys (=:aliases=, =:models=, =:harnesses=, =:defaults=) merge across files.
- One level down, an entry *replaces* its counterpart wholesale: an override =:models= row for ="anthropic/claude-opus-5"= replaces that whole row rather than merging columns into it, and an override =:harnesses :claude= entry replaces the packaged one -- so it must restate =:model-flag=, or validation rejects the file by name.
- =:aliases= and =:defaults= are the exceptions, because their values are scalars: each key merges independently. Retargeting ="heavy"= therefore costs one line and disturbs no sibling alias and no =:models= row. That is the point of the two-level split.

A weight name is an =:aliases= key, never a =:models= key. The same key in both maps is rejected post-merge, naming the key -- which is the error you will see when migrating an override that carried a full ="heavy"= row.

*** Worked example

A home override pinning the =heavy= tier to a specific Claude release, making claude-kind children usable unattended, and giving every child its own tab:

#+begin_src clojure
  {:aliases  {"heavy" "anthropic/claude-fable-5-20260714"}
   :models   {"anthropic/claude-fable-5-20260714"
              {:claude "claude-fable-5-20260714"             ; pinned, not the floating alias
               :codex "gpt-5.6-sol"}}                        ; cross-provider equivalent
   ;; Override the default permissions for more autonomous operation
   ;; We intentionally don't do this by default - it should be opt in
   :harnesses {:claude {:model-flag "--model"
                        :extra-args ["--permission-mode" "auto"]}
               :codex {:model-flag "--model"
                        :extra-args ["--ask-for-approval" "never"
                                     "--sandbox" "workspace-write"]}}
   :defaults  {:placement :tab}}
#+end_src

The new canonical ID needs a row only because it is new. Pointing ="heavy"= at an already-shipped canonical ID needs the =:aliases= entry alone.

There is no =:pi= column, and adding one would be redundant: an ID with no matching column falls through to the *canonical* ID, which is already the pi-style spelling. So pi receives =--model anthropic/claude-fable-5-20260714=, claude =--model claude-fable-5-20260714=, and codex =--model gpt-5.6-sol=. The =:codex= column is present because it is a genuine cross-provider remap.

** Harness configuration

=:harnesses= says how a resolved kind is invoked. =:model-flag= is required in every entry, including an entry you add only to attach =:extra-args=, because the level replaces wholesale.

=:extra-args= exists so an override can relax a harness's interactive command approval: without it, claude and codex children stall at their first tool call in a pane nobody is watching. Prefer a bounded grant to a blanket bypass -- the live home override at [[file:../../subagents/config.edn][subagents/config.edn]] records the reasoning and the rejected alternatives, and [[file:scripts/docs/contract.md][contract.md]] § Harness =:extra-args= gives the validation rules.

The kind set is open on the config side: adding a =:harnesses= entry for a new kind needs no code change, and a kind with no entry simply receives no model arguments.

*** Upstream support is the real constraint

Herdr, not this skill, decides which kinds exist. The authoritative, version-specific list is the =--kind= enum printed by:

#+begin_src sh
herdr agent start --help   # the --kind option lists its possible values
#+end_src

It is deliberately not duplicated here or in [[file:scripts/docs/contract.md][contract.md]]. Herdr adds kinds on its own release cadence, and a copied list silently goes stale. Herdr also updates a remote agent-detection manifest in the background (=manifest_check= in =herdr --default-config=), so the set can widen without a herdr upgrade.

Upstream support is required at *both* ends of a delegation, which is stricter than it first appears:

- *As a child*, the kind must be startable: =oh= spawns via =herdr agent start --kind=, which not only launches the executable but verifies it was *detected* in the pane. A harness absent from the enum cannot be spawned however it is configured, and shadowing a supported kind's executable on =PATH= does not work -- detection fails rather than mis-registering.
- *As the orchestrator*, the kind must be registered too. Every caller-identity command (=task run=/=start=, =collect --any=, =prune=) runs =agent get= on =$HERDR_PANE_ID=. From a pane hosting an unrecognised process that fails with =agent_not_found=, so an unsupported harness cannot drive delegation at all, only be driven.

What survives without registration is publication and capture: =task publish= degrades open rather than refusing, because an unresolvable caller owns nothing, and =task collect <full-task-uuid>= swallows its own identity probes, downgrading the capture to ="ownership": "foreign-parent-session"= rather than failing it. [[file:scripts/docs/contract.md][contract.md]] § Preconditions enumerates which commands resolve caller identity and how each degrades. So an unsupported harness can be hand-launched into a =pane split --env …= pane and still return a valid, publishable result. Treat that as a manual fallback, not a supported path: such a child is invisible to =agent list=, so it is excluded from =collect --any= and, more dangerously, satisfies =prune='s staleness proof while still working.

** Child placement

=:defaults :placement= decides where a spawned child's pane comes from. Three values:

| Value | At root | Below root (spawner has =HERDR_ORCH_PERSONA=) |
|---+---+---|
| =:split= | split the caller's pane | split the caller's pane |
| =:tab= | new tab in the caller's workspace | new tab in the caller's workspace |
| =:tab-split= | new tab | split the caller's pane |

Resolution order, highest first:

1. An explicit =--tab= or =--split= flag on =task run=/=task start= (supplying both fails).
2. The merged =:defaults :placement= (project > home > packaged, merged per key).
3. The code fallback in =resolve-placement=, which is ="split"=.

=:tab-split= is the shipped default. Spawning is cheap and the intended usage is
promiscuous, so first-level subagents accumulate fast: one tab each stays reviewable and
recoverable, where splitting every one of them produces an ever-narrowing column nobody can
read. A grandchild still splits its parent's pane, which keeps a nested unit visually
together and where the parent can watch it. Depth is discriminated by the spawning CLI's
own injected =HERDR_ORCH_PERSONA=, never by a label or a counter.

The code fallback stays ="split"= deliberately, and is *not* kept in step with the shipped
value. It fires only for a merged config that declares no =:placement= at all, which the
packaged file -- mandatory. A missing packaged =config.edn= is fatal -- always does. For
that degraded case a split is the conservative answer, because it needs no
=HERDR_WORKSPACE_ID=. Changing the product default is therefore a one-line edit to
[[file:subagents/config.edn][subagents/config.edn]], not a code change.

Placement is resolved per spawn and never inherited: it is not persisted per child, carried
in the child's environment, or consulted by that child's own spawns. The ledger entry
records the resolved =:placement= (="split"= or ="tab"=) and =:tab-id= for audit only. See
[[file:scripts/docs/contract.md][contract.md]] § Placement for the mechanical detail.

** Verifying a configuration change

Config is parsed and shape-validated before any ledger allocation or pane mutation, and every failure names the offending file, so a broken override costs nothing billable. =:defaults= is a closed map -- =:placement= only, valued =:split=, =:tab=, or =:tab-split= -- so a typo fails loudly instead of being ignored.

To see what a spawn would do without spawning it:

#+begin_src sh
oh task run scout --task x --model heavy --print-prompt
#+end_src

The preview reports =kind=, the resolved (pre-alias) =model=, its post-alias =model-canonical=, the translated =model-args= the harness will receive, and the resolved =placement=, =retro=/=retro-source=, and =spawns=/=spawns-source=. Read the two model fields together to localise a miss: if =model-canonical= still shows your short name, no =:aliases= entry matched. If it is right but =model-args= repeats it instead of a harness-native ID, the =:models= row has no column for that kind.

* Known gaps

- The CLI implements one child per invocation for =run=/=start=. Multi-child fan-out scheduling (how many in flight, when to replace one) and resident lifecycle remain parent policy in [[file:SKILL.md][SKILL.md]] -- no command spawns or schedules more than one child. Fan-in, however, now has a dedicated primitive: =collect --any= (see [[file:scripts/docs/contract.md][contract.md]] § Fan-in) captures whichever in-flight child of the caller's session publishes first, without scheduling anything itself. Concurrent writers likewise get checkout isolation (§ Subagent lifecycle), but how many run at once remains the parent's decision.
- =task close= settle-waits (bounded by =ORCH_SETTLE_CLOSE_MS=, default 45 s) before its single close attempt, but a child that never settles inside that budget still retains its pane -- closure is one attempt, never retried. Capture never closes anything.
- =close= refuses a foreign or unresolvable parent identity, so an orphaned child whose owning session has ended is not closable through it. =oh task orphans= lists such panes and =oh task orphans --close= sweeps them, under the same live child+pane match =close= uses (see [[file:scripts/docs/contract.md][contract.md]] § Orphans). Both forms are root-only and the operator supplies the judgement that a foreign session is a dead one.
- The advisor-tier convention holds only for a worker that consults through =oh task run advisor=. A worker that hand-rolls a consult with raw =herdr agent start= silently inherits the default model, spends money that never appears in the ledger, and orphans the pane, so ledger consult counts and advisor costs are a floor rather than the truth.
- =HERDR_ORCH_BIN= intentionally carries the deployed absolute path rather than a canonical repository path. Launcher-matrix coverage is its guard.
