# `oh` contract

## Preconditions

All spawn operations require `HERDR_ENV=1` and Herdr >= 0.9.1 on **both** the client and the server. Preflight is those checks and nothing else -- one `herdr status --json` subprocess -- and precedes ledger allocation and pane mutation. `continue` runs it too, since it prompts a pane. `close`, `collect`, `status`, `prune`, and `publish` never run preflight at all.

The versions are read from the `status` envelope's `.client.version` (the invoking binary) and `.server.version` (the running daemon; `null` when none is running). Each endpoint is judged against the floor independently, and a refusal names the deficient endpoint and its version. A client and server that differ but both clear the floor pass: Herdr's own protocol check governs their pairing, and `oh` adds no pairing rule of its own. Missing or unreadable evidence -- a `status` call that fails, an envelope that does not parse, or a `null` server version -- is a refusal, never a pass, because a client that cannot prove its server's version cannot prove the server accepts the commands `oh` will issue. There is no legacy fallback to `herdr --version` and no capability-probe matrix: an old or unknown endpoint is refused outright.

The floor was raised from 0.8.2 to 0.9.1 by an explicit user decision recorded in `design/log/2026-09-17-herdr-orch-improvements-260917.org`, which also made the server an endpoint of the gate: 0.9.1 is the version whose start/prompt outcomes ([#Start and prompt outcomes](#start-and-prompt-outcomes)) and agent-kind set the adapter is written against. The earlier 0.8.2 gate carried readiness fixes `7ae4b05` (agent prompt readiness) and `37644ca` (pane shell readiness), which is why the local start-retry and dispatch-verification workarounds were deleted and are not reintroduced. Raising the gate is an accepted compatibility break: a user still running an older stable Herdr loses support, rather than silently keeping a downlevel binary limping along.

The version gate is the entire capability check: every command and flag the CLI uses (`pane layout/split/rename/get/close`, `tab create`, `agent start/prompt/wait/get/list`, `notification show`) shipped at or before 0.9.1, so per-command `--help` probing could only ever have caught a binary misreporting its own version. `herdr api schema` exposes a socket protocol number, not CLI flag shapes, and is deliberately not used as a substitute.

Every command that resolves caller identity runs `agent get` on `$HERDR_PANE_ID`, via `parent-identity` or its swallowing wrapper `caller-parent-session`. That is `spawn!` (`task run`/`start`), `collect --any`, `prune`, `close` (single and `--settled`), `continue`, `orphans`, `compact`, `harvest`, **and `publish`**, whose children-discharge guard ([#Ledger and completion](#ledger-and-completion)) resolves the caller too and may additionally make one `agent list`. That call requires the calling pane to itself be hosting a recognized agent, not a bare shell. Invoked from a raw, non-agent-occupied pane it fails with herdr code `agent_not_found`.

The *consequence* of an unresolvable identity is deliberately not uniform, and the split is by consequence class. `spawn!` propagates the raw failure. The destructive and cross-session verbs (`prune`, `close` single and `--settled`, `continue`, `orphans` listing and `--close`, `compact`, `harvest`) refuse loudly and mutate nothing. `collect --any` returns the non-final, non-throwing `{"status":"pending","reason":"unknown-caller"}`. `publish` alone degrades **open**: a validated terminal item is the sole completion signal, so a guard that cannot attribute a child must not be able to strand a finished result. Plain `collect <full-task-uuid>` resolves identity only to *report* ownership (`"ownership":"foreign-parent-session"`) and captures either way.

A first-attempt `agent start` failure of any kind runs the existing `:start`-phase cleanup: the ledger entry is marked `failed` with `:failure-phase "start"` and the child pane is closed. `agent start` is never retried. The Herdr outcomes that reach that cleanup, and how each `oh` prompt site handles a prompt refusal, are in [#Start and prompt outcomes](#start-and-prompt-outcomes).

## Start and prompt outcomes

These are Herdr 0.9.1's own outcomes (its `agent start --help`, `agent prompt --help`, and `src/cli/agent.rs` at the reviewed commit, mirrored in the vendored `skills/herdr/SKILL.md`). `oh` passes them through and adds no readiness poll, dispatch verification, or start retry of its own: those workarounds were deleted with the 0.8.2 gate (commit `4741d59`) because Herdr's readiness fixes made them redundant, and they are not reintroduced here.

**`agent start`.** Success returns only after Herdr detects the expected agent kind in the target pane and reports it ready for interactive input (readiness timeout 30 s by default, `--timeout` up to 300 s). The outcomes `oh` callers meet:

- `agent_not_ready` -- the agent started and is registered under its name, but reported `blocked` during startup (a trust, login, or first-run dialog). Herdr returns immediately and **keeps the name usable**: `agent read <name>` and `agent send-keys <name>` address it, and upstream guidance is to wait for `idle` before prompting.
- `agent_start_failed` -- the process exited before becoming interactive. `agent_kind_mismatch` -- a different agent was detected in the pane. `agent_name_not_found` -- the named agent no longer owns the target terminal. `timeout` -- readiness never arrived; Herdr reconciles the pending name so it is reusable at once.

Herdr's retained-name outcome and `oh` delegation's start-failure cleanup are deliberately different things. Raw `oh agent start` passes every outcome through unchanged, so after `agent_not_ready` the caller may inspect the blocked startup with `oh agent read <name>` and answer it with `oh agent send-keys <name>`. Delegation (`task run`/`task start`) does not keep it: any `agent start` failure -- `agent_not_ready` included -- is a failed spawn and runs the `:start`-phase cleanup above (entry `failed`, `:failure-phase "start"`, pane closed, which ends the blocked process and releases the name). A delegated child that cannot take its assignment prompt is not a child, and a retained pane would be a leaked one; an operator who needs to see the startup dialog reproduces it with raw `oh agent start` in a pane they own. The same cleanup covers the assignment `agent prompt` that immediately follows a successful start, because both run in the `:start` phase.

**`agent prompt`.** Herdr writes the text and an encoded Enter as one ordered submission and reports success once both are written; success does not prove the agent began a turn. Before sending any input it refuses with `agent_blocked` when the target is already at an approval or question dialog, so prompt text can never land in that dialog. With `--wait`, a prompt sent from a non-working state must show `working` or `blocked` within five seconds or returns `agent_prompt_stalled`; `timeout` is returned instead if the caller's `--timeout` expires first, and with no `--timeout` the settled-state wait is indefinite once activity is observed. `oh` prompt sites and what a refusal means at each:

- Spawn (`task run`/`start`): the assignment prompt never uses `--wait`; `run`'s wait is the separate `agent wait` loop ([#Timeout resolution](#timeout-resolution)). `agent_blocked` here is a start-phase failure and runs the cleanup above.
- `continue` ([#Continue](#continue)): refuses before prompting unless the observed child is `idle`/`done` at its recorded pane, so `agent_blocked` is not expected; a prompt that fails anyway marks the new round `failed` with `:failure-phase "continue-prompt"`, touches no pane, and leaves the prior round recoverable.
- `poke` ([#Poke](#poke)): the same settled gate; a prompt failure propagates as the command's error, `:pokes` is not incremented, and no round or item is created.
- Parent push ([#Parent push](#parent-push)): a `blocked` parent fails the push gate before any prompt is attempted; a prompt that fails is reported as `result.parent-push {"push":"error","reason":"prompt-failed"}` and never changes the publish outcome. Never `--wait`.
- Raw `oh agent prompt` ([../README.md#Raw passthrough](../README.md#raw-passthrough)): submits without waiting unless `--wait` is given; `--until`/`--timeout` require `--wait` and ride the same call; every Herdr outcome passes through unchanged.

## JSON output

Every non-help command writes exactly one JSON object to stdout:

```json
{"ok":true,"schema":"herdr-orch/v1","result":{}}
```

Failures use `{ "ok": false, "schema": "herdr-orch/v1", "error": {"message": "...", "data": {}} }`. Diagnostics do not carry a completion signal.

`--help` is the one documented exception: it prints human-readable usage text and exits 0. There is no JSON help or discovery variant. Help narrows to the most specific match: `oh --help` and `oh help` print the global command list, `oh <group> --help` prints every signature in that group, and `oh <group> <op> --help` prints just that command's signature, including its positional arity. An unrecognised group falls back to the global list. Help is resolved before option parsing, so `--help` on a command with required options (`oh task run --help`, `oh agent start --help`) prints usage instead of failing on the missing option.

`status` without a task and `list` return a JSON **array** of ledger entries under `result`, and `close --settled`, `orphans`, `compact --closed`, and `harvest` return JSON **arrays** too ([#Close](#close), [#Orphans](#orphans), [#Retention](#retention), [../../SKILL.md#Process retrospectives](../../SKILL.md#process-retrospectives)). Every other command returns an object.

The read verbs -- `collect` (including `--any`), `status`, `list`, and `harvest` -- accept two output knobs, because a delegating parent pays for every byte they emit. `--raw` opts *in* to the raw result envelope: the `text` blob is a byte-for-byte repeat of the parsed fields beside it (top-level `text` on a capture, `:envelope :text` on a ledger entry) and is omitted unless asked for. `--format text` (default `json`; any other value is a loud refusal) renders lines instead of a JSON envelope, and is, with `oh roster --format markdown|org` ([#Roster](#roster)), one of the documented non-JSON outputs besides `--help`: a capture becomes `LABEL: value` lines plus `- ` list sections in envelope order, and a ledger entry becomes one tab-separated line of `task`, `child`, pane, status, `captured`/`uncaptured`, `closed`/`open`. An empty listing renders `none`, never an empty string.

An immutable item that fails validation (identity mismatch, malformed envelope, or missing artifact) is recorded as the non-final status `invalid`, with the reason on that item and in `result.reason`. It is consumed but never seals the stream, so a later valid item can capture normally. Collection re-reads the oldest unconsumed item. A child that wrote malformed content directly may publish a corrected successor.

`run` uses a ten-minute total wait budget unless `--timeout` overrides it. Timeout, no result, and blocked outcomes are non-final and retain the child pane. `collect` polls once unless `--wait` is supplied, which waits with the same ten-minute default that `--timeout` overrides.

When a wait outcome settles (idle/done) without a valid result file, the loop sleeps `min(ORCH_POLL_INTERVAL_MS, remaining-budget)` before polling again instead of re-invoking `agent wait` immediately. Default interval is 1000 ms. This applies identically to `run` and `collect --wait` (both dispatch through the same wait loop) and never overshoots the total timeout by a full interval. `collect --any` uses the same sleep discipline and the same budget default, but polls result files directly instead of blocking in `agent wait` (see [#Fan-in](#fan-in)).

## Checkout target resolution

Every spawn resolves one checkout target before ledger construction and pane placement. `--worktree` is value-taking: `--worktree new` selects a newly managed checkout, while `--worktree <path>` selects an existing checkout. Repeating the singleton option is the only target conflict. Without it, an initial child uses the caller's source cwd. An additional concurrent write-enabled child receives a newly managed checkout. A read-only persona never causes implicit creation. Every child is launched with the resolved target as cwd, including the shared case.

A target canonicalising to the source checkout root (`git rev-parse --show-toplevel`), rather than merely the raw invocation cwd, is shared: no `:worktree` ledger field is written, publication performs no git mutation, and concurrent use remains allowed even when the shared root was explicit. An omitted target preserves the caller's original cwd. An explicit source-root target uses that requested root as the pane cwd. Any other existing target must be an attached checkout root in the same git repository and must not be referenced by a genuinely live round under the same canonical path. Liveness uses the teardown predicate unchanged: an unclosed and unsealed current round refuses reuse, while a sealed terminal, closed, failed, or superseded round does not. Detached HEAD, a path inside rather than at a checkout root, a different repository, a missing path, a live reference, or a read-only target with pre-existing tracked or untracked dirt refuses before task allocation, ledger mutation, or checkout mutation. Ignored paths alone remain legal. Its branch, current HEAD, and canonical common-git-directory identity are recorded as `:worktree {:path ... :branch ... :base ... :repository ...}`, where `:base` is the target HEAD at assignment time. A managed target uses the same identity shape, writes it recoverably before `git worktree add -b`, and creates the checkout before pane mutation. Existing ledger fields outside this shape remain readable.

Existing targets may be outside the managed root because use is path-addressed. Destruction is not: `worktree remove` continues to resolve and enforce the one central managed-root containment predicate, so an externally supplied checkout is legal to use but cannot be removed by `oh`. A non-shared existing target is refused while any newest, unclosed and unsealed round still references its canonical path. A sealed prior round may hand the checkout to a successor, while an explicit source-root target remains the parent's shared-tree override. `oh` never merges, rebases, pushes, deletes a branch, or removes an external checkout.

Target decision and ledger reservation are one assignment-root-scoped OS-file-lock transaction. Assignment input, parent-pane inspection, launcher resolution, and other potentially blocking external reads finish before the lock. The critical section spans canonical target decision and the liveness/in-flight check through bounded local UUID/path, persona-file/index, and entry construction plus the ledger write. It serialises independent CLI processes without coupling unrelated assignment roots, releases before checkout or pane mutation, and is automatically released if a process exits. The `:worktree` map is lineage-owned identity, not a per-round decision. `continue` copies it, together with `:read-only`, onto each new immutable round, so publication and reconciliation keep the same path, branch, base, and repository witness without resolving or creating another target. Shared-root lineages carry neither field.

## Persona discovery

Persona definitions are `<name>.md` files resolved in descending precedence: project `<git-root>/.agents/subagents/` > home `~/.agents/subagents/` > packaged `<skill-dir>/subagents/`, where `<skill-dir>` is derived from the installed launcher. This atomic name shadowing is distinct from the roster-table replacement in [#Model resolution](#model-resolution). The packaged directory is a skill default, not a Home Manager projection into the home override path.

Persona transport is per kind: pi uses `--append-system-prompt <path>`, claude uses `--append-system-prompt-file <path>`, and other kinds use prompt-level adoption only.

### Persona composition (`extends`)

A persona declares one base with `extends: <name>` in frontmatter, resolved through the same project > home > packaged roster lookup as the top-level persona. A missing base, and a base that itself declares `extends`, both fail before task allocation, ledger/index creation, or pane mutation -- the second check also rejects a persona extending itself, since resolving its own frontmatter as the base finds the same `extends` key. This is deliberately one level only: no graph traversal, no cycle detector, and no arbitrary inheritance depth.

The composed body is the base's body concatenated before the derived persona's own body, verbatim (no inserted separator; each source file's own leading blank line after its frontmatter block supplies the visual break in the common case). The composed file, when materialized, carries only the *derived* persona's frontmatter block, byte-preserved -- the base's frontmatter is never written to the composed file.

Scalar runtime settings (`kind:`, `model:`, `retro:`, `timeout:`, `spawns:`) inherit from the base, with the derived persona's own declaration winning when present: the effective frontmatter every resolver below reads is the base's frontmatter merged under the derived persona's, so an omitted derived declaration falls through to the base's and a present one (including an explicit blank `spawns:`) overrides it. `name:` and `description:` are never inherited -- they stay local to the persona actually being resolved, even when the derived persona omits them. A persona without `extends:` is unaffected: its frontmatter, body, and materialization behave exactly as before this composition layer existed.

### Trait composition

A persona declares a trait inline by placing `%<name>` in its Markdown body where the fragment belongs, or as a metadata selection via one-line frontmatter `traits: [name, ...]` -- base first, then derived, each parsed the same way. A spawn adds explicit selections with a repeatable `--trait NAME` on `run`/`start` and their `--print-prompt` preview, appended after both metadata lists. `herdr-orch.traits/interpolate` is the shared in-process implementation: callers inject the text, ordered resolution directories, existence predicate, and text reader, and receive transformed `:text`, ordered resolved `{trait, source, path}` maps, incompatibility declarations by trait in `:incompatibilities`, unresolved candidate names in `:unknowns`, and repeated resolving names in `:repeats`. Failure policy belongs to the caller. The standalone adapter below exposes the same result without changing that policy.

Metadata and explicit trait names (`traits:` and `--trait`) are combined base-first, derived-second, explicit-last, deduplicated by name -- an overlap between any of the three emits exactly one copy -- and validated against the resolution layers regardless of name length, unlike an incidental inline candidate. A selected name is also validated against the token grammar `[a-z][a-z0-9-]*` before resolution: a name outside it, such as `2fa` or `Read-Only`, fails before any ledger or pane mutation even when a file of that name exists, because substitution only ever matches a `%<name>` token -- accepting it would drop the directive, leave a literal `%2fa` in the composed persona, and omit the name from `:traits` and `:trait-sources` at exit 0. A name already used inline in the composed body keeps that one occurrence; composition does not append a second copy for it. The full set (inline plus metadata plus explicit) is what `%read-only` and every other trait-gated policy reads, so a trait inherited only through a base's `traits:` or body still governs the derived persona's checkout/publication policy. Names not already inline are appended, each as its own `%name` token separated by a blank line, after the complete base-plus-derived body; the whole result -- composed body plus appended tokens -- is then substituted by one `interpolate` call, so composition never re-scans already-substituted text.

The ledger records launch provenance alongside `:persona-path`: `:persona` (the selected persona name), `:base-persona` (the resolved base's name, when `extends:` resolved one), `:traits`, and `:trait-sources`, the last two omitted entirely (not empty vectors) when the effective set is empty. `continue` inherits all four with the rest of the round's metadata, exactly as it inherits `:persona-path`.

`--print-prompt` reports the same `:persona`, `:base-persona`, `:traits`, and `:trait-sources`, plus `:persona-text`: the exact effective persona text -- base-plus-derived body and every appended metadata fragment, substituted -- identical to what a real spawn would materialize to its composed file. Preview never creates a pane, a ledger entry, or a composed file; `:persona-text` is computed in memory only.

Scanning is body-only. Persona YAML frontmatter, including its delimiters and line endings, is preserved byte-for-byte and never scanned. A candidate is `%` preceded by start-of-line or whitespace, followed by the full lexical name `[a-z][a-z0-9-]*` through the first character outside that grammar: `%focused,` finds `focus`, while `page%focused`, `%20`, `%PATH%`, and `%%` do not match. Backtick code spans, fenced code blocks, and lines indented by 4+ spaces or a tab are excluded. Substitution is single-pass: text inserted from a fragment is never scanned again.

Candidate length affects unknown policy, not grammar. Every candidate, including a 1-2 character name, is resolved. An unresolved 1-2 character candidate remains literal, so `%s` and `%h` are inert unless a layer actually provides those names. A resolving short candidate such as `%ct` expands. An unresolved name of 3+ characters fails before task allocation, ledger/index creation, or pane mutation. A resolving name repeated in one body fails at the same boundary. Both failures name the trait and report `searched-layers` plus all six candidate paths. The message tells the author to write a literal example as code or fix the name.

Each candidate resolves through project `<git-root>/.agents/traits/` > home `~/.agents/traits/` > packaged `<skill-dir>/traits/`. Within each layer `<name>.md` wins over `<name>/prompt.md`. A match in a higher layer wins regardless of shape. The packaged directory is a real directory shipped inside the skill. Fragment YAML frontmatter is optional. When present, it is stripped before substitution and its `name:` must match the resolved file or directory name (`description:` and unknown keys are metadata only). When absent, the whole file is substituted verbatim.

A fragment adapted from an external source carries two optional metadata keys: `adapted-from:`, the source URL, and `adapted-from-sha256:`, the SHA-256 of the source file as it read when the fragment was written. The hash pins the source rather than our copy, so it answers "has upstream moved since we adapted this?" -- an adapted fragment is expected to differ from its source immediately and is not a vendored body, so [../../../README.org#Vendored](../../../README.org#vendored) does not apply and local editing is intended. A file hash rather than an upstream commit for the reason given there: a source revision churns on every unrelated commit while saying nothing about whether the fragment itself moved. Both keys must be single-line scalars. Nested YAML is not parsed: `parse-yaml` matches `key: value` per line, so a nested mapping silently flattens its children to sibling top-level keys instead of failing.

When at least one token resolves, or `extends:` resolved a base (whose body changes the composed text even with zero trait tokens), spawn writes `<assignment-root>/.tmp/herdr-orch/composed/<task>-<persona>.md` with each fragment substituted in place. The ledger records this composed file as `:persona-path`. Both the prompt's `Read <path>` line and pi/claude persona transport receive that path. `oh` never deletes composed files, matching its result-file policy. `continue` inherits `:persona-path` but `continuation-prompt` has no `Read` line, so a continued round retains context and does not re-read or re-send the file.

A token-free, `extends`-free persona, and a persona containing only unresolved short candidates, passes through exactly: no composed directory or file is created, and the source persona path remains `:persona-path` for the prompt and persona transport.

`--print-prompt` scans, resolves, and validates composition but never materializes a file. Its `preview` substitutes the literal `<composed-persona-path>` in the `Read` line when composition changed the text (a token resolved, or `extends:` resolved a base). `persona-path` still reports the source persona for inspection. It reports `traits` in body-occurrence order and `trait-sources` as ordered `{trait, source, path}` objects, where `source` is `project`, `home`, or `packaged`. A pass-through preview reports empty vectors and the unchanged source path in its `Read` line.

### Standalone trait interpolator CLI

`skills/herdr-orch/scripts/traits` is the thin launcher for `herdr-orch.traits-cli`. The repository-root `bb.edn` also exposes the same entry point as the `traits` task. The launcher resolves final-component and directory symlinks, finds the repository root from its own installed path, and preserves the caller's cwd. This lets the pi extension invoke the co-installed launcher through `~/.agents/skills/herdr-orch/scripts/traits` from an unrelated project without making the project cwd a source-path assumption.

The CLI reads text from stdin by default or from one `--file PATH`. Each repeated `--layer SOURCE=DIR` adds one resolution layer in command-line order. The CLI does not inject project, home, or packaged defaults. `--plain` writes only transformed text. Without `--plain`, success writes one `herdr-orch/v1` JSON envelope whose `result` is the complete `interpolate` map: `text`, ordered `resolved` `{trait, source, path}` objects, `incompatibilities`, `unknowns`, and `repeats`. Unknowns and repeats are reported but do not fail or suppress substitution, because failure policy remains with each caller. This keeps the entry point usable by interactive input today and direct gate-arm prompts later. Argument, file, fragment-metadata, and I/O failures write an `ok: false` envelope to stderr and exit non-zero.

### Harness `:extra-args`

A `:harnesses` entry may carry `:extra-args`, a vector of non-blank strings appended to that kind's native `agent start` argv, between the model args and the persona transport. The shipped config declares none for any kind, so the flag set is empty unless an override file asks for it, and it is granted per kind: naming `:claude` never affects `:pi`. Its purpose is to relax interactive command approval for unattended delegation, since both claude and codex otherwise block on it. The recommended grant for an unattended child is claude `--permission-mode auto` and codex `--ask-for-approval never --sandbox workspace-write`: prompts suppressed for routine work, dangerous actions still escalating. Whether any install actually declares it is a property of that machine's override files, not of this contract. Note that claude `bypassPermissions` does not achieve this -- it gates on its own startup confirmation, so an unattended child stalls there instead.

`merge-config` is `merge-with merge`, so a `:harnesses` entry is replaced wholesale at level two exactly as a `:models` row is. An override adding `:extra-args` must therefore restate `:model-flag`, and `:effort-flag` if that kind should keep receiving an effort level. `parse-config` rejects, with the offending file path, a non-sequential `:extra-args`, a non-string or blank member, and any member containing `\n`, `\t`, or `\r` -- the last because Herdr rejects control characters in agent argv with `invalid_agent_argument` before pane lookup, so the failure belongs at config-parse time rather than at spawn.

## Model resolution

`resolve-kind` has exactly two tiers: frontmatter `kind:`, else the inherited parent kind, failing when neither resolves. Nothing per-assignment selects a harness -- no flag (`task run`/`start` rejects `--kind` rather than ignoring it), no env var, and nothing in the model layer below. Raw `oh agent start --kind` is an unrelated Herdr passthrough and keeps its flag.

`resolve-model` precedence is requested > frontmatter model > same-kind parent inheritance > nil. Inheritance is exactly one level at every depth, by one mechanism: a spawn reads its immediate parent's model and injects its own as `HERDR_ORCH_MODEL` for the next. A child reads back what its parent injected. A root, which nothing injected into, falls back to its harness's own environment -- `PI_MODEL`/`PI_PROVIDER`, and only when the root really is pi, since claude and codex expose no verified equivalent and a stray `PI_MODEL` must not be read as a claude root's model. Only a persona declaring no `model:` reaches this tier at all. Every packaged persona declares one. The resolved value is translated at the `model-args` boundary, the single choke point for frontmatter models, explicit `--model` flags, and same-kind parent inheritance alike.

`resolve-effort` precedence is `--effort` > frontmatter `effort:` > same-kind parent inheritance > `medium`. The mechanism mirrors `resolve-model` exactly: a spawn reads its immediate parent's effort level and injects its own as `HERDR_ORCH_EFFORT` for the next -- always, unlike `HERDR_ORCH_MODEL`, because `resolve-effort` always resolves to a level rather than to nil. Inheritance is same-kind only, exactly like `resolve-model`'s guard, so a pi-only level such as `off` never reaches a claude or codex child. A root, which nothing injected into, falls back to `PI_REASONING_LEVEL` (set by pi 0.87.1's bash tool), and only when the root really is pi, for the same reason `PI_MODEL` is read only from a pi root. `:effort-flag` is optional: a `:harnesses` entry without one receives no effort args. When present, it is a non-blank string template with an optional `{}` placeholder. A template containing `{}` splits on whitespace and substitutes the resolved level into each token (codex's `-c model_reasoning_effort={}` becomes `["-c" "model_reasoning_effort=high"]`); a template without `{}` appends the level as the next arg (claude's `--effort` becomes `["--effort" "high"]`). The level vocabulary is pass-through, never validated against a per-kind allow-list. The pi `provider/id:<thinking>` model suffix is unsupported -- no packaged persona, alias, or `:models` column produces one, and `oh` neither generates nor rejects it.

The model table is in external EDN, in two levels, alongside optional spawn defaults: `{:defaults {:placement :tab-split} :harnesses {:<kind> {:model-flag "…" :effort-flag "…"} …} :aliases {"<short-name>" "<canonical-id>" …} :models {"<canonical-id>" {:<kind> "…" …} …}}`. `:aliases` maps a short or weight name to a canonical, pi-style `provider/model` ID. `:models` maps that canonical ID to a sparse row of per-kind native spellings. Resolution is: an alias hop through `:aliases` (or pass-through if the value is not an alias key), then a `:models` row/column lookup by that canonical ID, consulted only after kind resolution. `:harnesses` keeps the kind set open -- a resolved kind absent from it yields no model args, and herdr alone validates which kinds exist.

The alias hop is single-hop by contract: `canonical-model` looks a value up in `:aliases` at most once and never re-resolves the result through `:aliases` again. An `:aliases` value that is itself an `:aliases` key is a validation error (below), not a chain resolved at runtime, so the effective canonical ID for any alias never depends on following a value into a second alias entry.

Both the ID and kind sets stay open, and a miss anywhere in the chain is pass-through, never a warning or failure: an alias whose canonical target has no `:models` row yields the *canonical* ID -- not the requested alias -- for the resolved kind, and an ID present in neither `:aliases` nor `:models` passes through unchanged. Rows are sparse, and a configured column may deliberately remap across providers. In the shipped table, tier-equivalent cross-provider mappings are confined to `:claude` and `:codex` (for example, the `claude-sonnet` family → codex `gpt-terra` family). There is no `:pi` column: pass-through already delivers the canonical, pi-style spelling for pi. `:defaults`, when present, is a closed map: its only key is `:placement`, whose values are `:split`, `:tab`, or `:tab-split`. Each file is validated before merge, and an invalid value names that file.

File chain, project wins: skill default `skills/herdr-orch/subagents/config.edn` (resolved as `subagents/config.edn` under the launcher's skill directory) ← `~/.agents/subagents/config.edn` ← `<git-root>/.agents/subagents/config.edn`. `merge-config` is `merge-with merge`, so the two levels compose differently: a `:models` row is replaced wholesale by canonical ID (an override never deep-merges its harness columns), while `:aliases`, like `:defaults`, merges per key across the chain ([../../README.org#The merge rule that catches people](../../README.org#the-merge-rule-that-catches-people)).

A merged config where the same key is present in both `:aliases` and `:models`, or an `:aliases` value that is itself an `:aliases` key, fails `validate-merged-config!` by name. Both checks run in `cli/config` immediately after `merge-config`, before any ledger allocation or pane mutation, so a stale override (for example, a legacy full weight row now colliding with a shipped alias) fails loudly at spawn instead of silently shadowing or chaining.

This table is the single hand-maintained enumeration of the shipped weight rows. Every other document states the rule and links here. The one exception is generated: [../../README.org](../../README.org) embeds `oh roster --format org --section models` output, which a test keeps current ([#Roster](#roster)). Each cell names a model family: the translated model with its version tokens removed (`anthropic/claude-sonnet-5-5` is the `anthropic/claude-sonnet` family, `gpt-6.1-sol` is `gpt-sol`). `subagents/config.edn` holds the current versions. `cli_test.clj`'s `shipped-config-invariants` parses this table and asserts that each cell has no version tokens and is the family of the translation of `subagents/config.edn`. A version bump therefore needs no edit here, but a weight that moves to another family fails `bb test` until this table changes. The rows translate only after kind resolution:

| Weight | Pi | Claude | Codex |
|---|---|---|---|
| `heavy` | `anthropic/claude-fable` | `fable` | `gpt-astra` |
| `middle` | `anthropic/claude-opus` | `opus` | `gpt-sol` |
| `light` | `anthropic/claude-sonnet` | `sonnet` | `gpt-terra` |
| `feather` | `anthropic/claude-haiku` | `haiku` | `gpt-luna` |

Unversioned canonical IDs (`claude-opus`, `gpt-sol`, …) are floating aliases resolving to the latest version of the tier. Versioned IDs pin a release.

Config is loaded and schema-validated (parse errors and shape/type errors alike) before any ledger allocation or pane mutation. A validation failure carries the offending path. A missing override file is ignored. A missing shipped default is fatal.

`--print-prompt` reports the resolved (pre-alias) model, its post-alias canonical ID under the `:model-canonical` key, and the effective translated native model args. Its prompt preview contains the resolved persona file path and launcher-composed guidance, not the persona body. Inspect the resolved file directly when validating persona-local rules. Spawn capability is enforced before preview generation, so a delegated leaf cannot use `--print-prompt` for a persona outside its `HERDR_ORCH_SPAWNS` allow-list.

## Roster

`oh roster [--format json|markdown|org] [--section all|personas|traits|models] [--detail]` is read-only discovery. It takes no positional argument, never runs preflight, and never calls Herdr, so it works without `HERDR_ENV`.

The default `--format json` is for a tool or agent. It writes the usual envelope, and its `result` is an object:

- `personas` -- every name `available-personas` returns, sorted, each with `name`, `source` (`project`, `home`, or `packaged`), `path`, `description`, `model`, `model-canonical`, `kind`, `spawns`, `traits`, `retro`, `timeout`, and `extends` when a base resolved. The values come from the resolvers a spawn uses ([#Persona composition (`extends`)](#persona-composition-extends), [#Trait composition](#trait-composition), [#Spawn gating](#spawn-gating), [#Retro gating](#retro-gating), [#Timeout resolution](#timeout-resolution)) with no flags applied. `spawns` is the declared allow-list, not the depth-gated policy. A persona whose composition or policy resolution fails carries `error` (the message a spawn would fail with) in place of the resolved fields, and the listing still succeeds.
- `traits` -- every name that some layer offers as `<name>.md` or `<name>/prompt.md` and that matches the token grammar, sorted, each with the winning `name`, `source`, `path`, frontmatter `description`, and `selected-by` (the listed personas whose `traits` contain it).
- `models` -- one row for each canonical ID in the merged `:models` keys or `:aliases` values, sorted, with `canonical`, `aliases` (shortest first), and `kinds` (the sparse per-kind spellings; a kind absent from a row receives the canonical ID).
- `harnesses` -- the sorted kind names in the merged `:harnesses`.
- `defaults` -- the merged `:defaults` map.
- `layers` -- the ordered persona and trait resolution directories, each `{source, directory}`.

An invalid merged config fails the command, as it fails every spawn ([#Model resolution](#model-resolution)).

`--format markdown` and `--format org` are for a person. Each writes the same rendering of that result as plain text, not an envelope. One renderer produces both formats, so the pi `/oh` command (Markdown) and the listings generated into [../../README.org](../../README.org) (org) cannot disagree:

- A persona is one list item: name, then `model` (or `inherits parent model`), `kind`, `extends`, `spawns`, and `traits` when present, then a non-packaged source as `<source> layer`. Its description follows as an indented continuation line. A persona with `error` shows only its name and the error.
- A trait is one list item: name, description, then `selected by <personas>` or `no persona selects it`, then a non-packaged source.
- Models are one table: the two shortest aliases, then one column for each harness. A harness with no entry for a row shows the canonical ID, which is what that harness receives. Cells are padded the way org aligns a table, so org's realignment of a babel result changes nothing.
- `--section all`, the default, writes every section under a heading (`## Title` in Markdown, a bold `*Title*` line in org) and adds the spawn defaults. A single section writes only its list or table, with no heading, so that an org babel result can replace it cleanly.
- `--detail` adds each path (instead of the `<source> layer` note), each persona's timeout and retro policy, every alias, and, under `all`, the resolution layers.

`--section` or `--detail` with `--format json` is refused, as is an unknown format or section. `cli_test.clj`'s `readme-roster-listings-are-current` compares each listing embedded in README.org with a packaged-only rendering, so a packaged persona, trait, or config change fails `bb test` until the README is regenerated ([AGENTS.md#Regenerating README listings](../AGENTS.md#regenerating-readme-listings)).

## Ledger and completion

The CLI stores one JSON ledger entry per task under `<assignment-root>/.tmp/herdr-orch/ledger/`. Index marker files provide lock-free, parent-session/per-persona monotonic allocation. One child may hold several entries over its lifetime, one per round ([#Continue](#continue)). The recorded `:child` belongs to the spawn, not the round UUID: read it and never reconstruct it from a continued round's task id. A spawn entry also records `:model-canonical`, `:model-args`, and `:effort-args`: the translated values the child received, identical to what `--print-prompt` reports for the same arguments ([#Model resolution](#model-resolution)). The `task start` envelope `result` carries them, and a continued round copies them from its predecessor.

A round is an append-only stream of immutable result items. Its bare `:result` path is item 1 and later items use `.2`, `.3`, and so on. Each `publish` writes the next free item through `Files.createLink`. No command overwrites or deletes an item. `STATUS: WAITING` is a valid non-terminal item. `COMPLETE`, `BLOCKED`, and `FAILED` are terminal statuses. A round is sealed only when a validated terminal item exists, and it seals the moment that item is *published*: the immutable files on disk are the authority, so an uncollected terminal item already refuses further publication. Capture is how the parent consumes items, never what seals the round. An uncaptured terminal seals when its envelope and ledger identity validate. Artifact existence is mutable and is validated only at capture, where a missing artifact records `invalid`. A malformed envelope never seals, so a corrected successor can still publish and capture. An unreadable or over-limit item is indeterminate and refuses publication rather than being treated as unsealed. A pre-stream entry with one captured bare `RESULT` remains readable as a stream of length one.

`publish` resolves `--task <full-task-uuid>` first, then `HERDR_ORCH_TASK`. A continued child uses `--task` because its injected environment still names its original round. The named entry must carry the injected `HERDR_ORCH_CHILD`. A ledger-backed publish refuses before writing when the round is sealed, carries `:closed-at`, or has been superseded by a newer round for that child. It also refuses a `WAITING` item inside `ORCH_WAITING_INTERVAL_MIN_MS` of the prior item. Terminal items are never throttled. Every ledger-backed publish additionally runs the children-discharge guard: a caller that still owns an open child round -- uncaptured, or captured but unclosed while its pane is live or shell-pid-reclaimable -- is refused with the collect/close/prune remedy, while a captured, fully consumed round whose vanished child no verb can reclaim is discharged and reported under `released-children`. A failed or refused publish raises a best-effort `Subagent publish failed` operator toast, which never changes the outcome. A hand-driven publish with no ledger entry still writes its one bare item and stays silent on success.

`publish`, `close`, `continue`, and the post-settle phase of `poke` mutate one child's round only while they hold that child's exclusive OS file lock at `<assignment-root>/.tmp/herdr-orch/ledger/locks/<child>.lock`. The lock is keyed by child rather than by round, so a publication against an old round contends with the `continue` that writes its successor. `publish` re-reads its ledger entry inside the lock, then holds the lock across every refusal check, the worktree checkpoint, and the item link. That hold has no timeout either: the discharge guard's `agent list`, `pane get`, and `pane shell_pid` calls and the worktree checkpoint's `git` subprocesses are each an untimed `herdr/invoke` or subprocess call, so a hung listing call or a stuck `git` call during publish blocks that child's own `close`, `continue`, and `poke` for the life of the call, the same way an unreturning `herdr pane close` blocks `close`'s hold below. It releases the lock before it notifies, so a parent push cannot block this child's lifecycle verbs. `close` takes the lock after its settle wait and holds it across the re-validation, the `pane close` call, and the `:closed-at` write. That hold has no timeout: `with-file-lock` waits on a blocking `FileChannel.lock`, and `herdr/invoke` derefs the `herdr pane close` subprocess with no timeout, so a `herdr pane close` that never returns holds this child's lock for the life of the closing process and blocks that child's own `publish`. `continue` takes the lock after its settle wait and holds it around the assignment-root reservation lock of [#Checkout target resolution](#checkout-target-resolution). That order is the only order in which two locks are ever held, so the pair cannot deadlock. `poke` also takes the child lock after its settle wait. It re-reads the entry and applies the final guards inside the lock, then holds the lock through the `agent prompt` call and the `:pokes` update. A concurrent `publish` therefore becomes visible before the prompt or waits until the prompt and update finish. The prompt call has no timeout, so a stuck call blocks that child's publication for the life of the poke process. `prune` and `compact` run only from the owning parent session, so those writes are race-free by ownership; a spawn allocates a child name that no other verb can address yet, so that allocation needs no such gate either. Capture and its `record-session!` backfill are not owner-restricted: a foreign caller's `collect` still writes the item capture through the unserialised `ledger/update!` read-modify-write, and the backfill inside a waited capture's retry loop writes unconditionally regardless of ownership. That is an accepted residual lost-update window, not a race-free site: two concurrent collects on the same round can lose one item's capture record, and a locked `close` writing `:closed-at` can be overwritten by an unlocked backfill that read the entry before the close and writes it back after. `orphans --prune` is a further exception among the ownership-checked verbs, because its candidate filter selects entries whose `:parent-session` is *not* the caller's, so its caller is by definition not the owner. It takes no child lock. Its guards are the root-only bar, the operator's judgement that the owning session is dead ([#Orphans](#orphans)), the liveness refusal for a child still present in `agent list`, and a re-check inside `ledger/update!` that refuses an entry captured or published during the listing. That re-check leaves the same narrow time-of-check/time-of-use window the child lock closes elsewhere, because `publish` links its item outside `ledger/update!`. Both this window and the capture/session-backfill window above are pre-existing and accepted. The kernel releases each lock when its process exits. There is therefore no stale-lock recovery, and no lock file is ever deleted.

`:work-root` is the absolute checkout the parent selected as the child's pane cwd. The parent records it on the ledger entry before the pane exists, injects the same value as `HERDR_ORCH_WORK_ROOT`, and copies it onto every continued round, so one child lineage resolves artifacts against one base for its whole life. `publish` reads it from the ledger entry and serializes it as `WORK-ROOT:`. It is publisher-owned: there is no `--work-root` option, and a child that rewrites its own injected variable still publishes the ledger's value. A hand-driven publish with no ledger entry reads the injected variable and refuses when it is unset, exactly as it does for `HERDR_ORCH_RESULT`. `WORK-ROOT` joins `CHILD`, `TASK`, and `RESULT` as validated identity, so an envelope naming another root is captured `invalid`. There is no compatibility branch for the pre-`WORK-ROOT` absolute-artifact envelope, and stale `.tmp/herdr-orch/` state from before the change is not a supported input.

`collect`, `run --wait`, and `collect --wait` consume the oldest unconsumed item and record capture per item under `:items`. Their result names `:item` and `:terminal?`, so a captured `WAITING` item is explicitly non-final. The stable entry head (`:status`, `:envelope`, and related fields) follows the newest capture for existing readers. **Capture closes nothing.** `stream-state` is the shared predicate for published items, captured items, and sealing. Lifecycle guards use it rather than inferring state from one result file.

The exact immutable item files are the only completion evidence. A validated terminal result item, not terminal output, is a completed round result. Transcript output, `agent read`, terminal history, notifications, and a `WAITING` capture are never completion signals. `BLOCKED` means a genuine blocking dependency. `FAILED` means unrecoverable failure after reasonable retries. Both retain the pane for the parent decision.

```text
--- HERDR RESULT v1 ---
CHILD: <live agent name>
TASK: <parent task UUID>
RESULT: <absolute parent-chosen result path>
WORK-ROOT: <absolute publisher-chosen child work root>
STATUS: WAITING | COMPLETE | BLOCKED | FAILED
SUMMARY: <single line>
[CHECKPOINT: <authoritative git ref; worktree publications only>]
ARTIFACTS:
- <path relative to WORK-ROOT :: purpose, or none>
FINDINGS:
- <at most five one-line items, or none>
NEXT: <one parent/user action, or none>
PROCESS:
- <at most five `signal → category → proposed rule` items>
--- END HERDR RESULT ---
```

`CHECKPOINT:` is optional and absent for shared-root publications. `PROCESS:` is optional retro annotation. Its writer emits it after `NEXT:`. Validation accepts it anywhere between the markers, truncates more than five items for collection, and records `:process-overflow` without demoting an otherwise valid envelope. `:child-session` is the best-effort durable transcript reference. A changed observed session moves the prior value to `:child-session-history` rather than discarding it. `:waiting-policy`, `:continues`, and `:closed-at` are round lifecycle fields. The ledger is shared across parent sessions: reads are global, while ownership governs close, continue, prune, compact, and fan-in candidacy.

For an entry carrying `:worktree`, publication orders every permanent refusal before git mutation: identity and artifact validation, `assert-publishable!`, WAITING throttle, undischarged children, and stream capacity. It then requires the complete final `{:path :branch :base :repository}` identity, proves the checkout's canonical root and repository equality, verifies that the recorded base resolves there, and verifies that HEAD is attached to the recorded branch. Legacy three-key identities remain readable for reconciliation but fail closed at publication. A read-only entry with dirt refuses with that finding and makes no commit. A clean read-only publication reports the current ref. A write-enabled entry stages tracked and untracked nonignored changes with `git add -A`, commits only when the index differs, obtains HEAD, serialises that authoritative ref as `CHECKPOINT:`, appends the item, then notifies. Ignored files remain uncommitted and visible through reconciliation.

The deterministic commit subject is `herdr-orch checkpoint <task> <status>`. These are mechanical protocol checkpoints, not authored commits: they are exempt from `git-commit` conventions and the parent may squash or rewrite them when integrating. `WAITING` is a checkpoint like every terminal status. Commit-before-append makes a retry safe: after an append failure, a clean retry serialises the current tip even though it creates no further commit. A clean worktree publication likewise always carries its current authoritative ref. A staging, commit, checkout, repository, or branch-attachment failure writes no result item and never resets history.

## Worktree reconciliation and teardown

`collect`, `collect --any`, and `status` attach `:reconciliation` only to an entry carrying `:worktree`. `worktree list` reports that same shape for the newest entry of each child lineage owned by the caller. It contains the recorded `:base` and `:branch`, current `:tip`, and `:checkout-state`. For a present checkout, `:committed` names paths changed from base to tip, `:dirty` preserves tracked and untracked `git status --porcelain` lines, and `:ignored` separately preserves `!!` lines. They are deliberately not collapsed: the parent integrates committed branch work, rescues or re-prompts for dirt, and merely decides whether ignored scratch matters. A missing path reports `checkout-state "missing"` with nil change sets. A path that exists but is not the recorded checkout root, belongs to the wrong recorded repository, or has unusable Git metadata reports `checkout-state "invalid"`, nil tip/change sets, and a bounded `:diagnostic`. It never follows Git discovery upward or throws from a reporting verb. Legacy identities without `:repository` remain readable and still undergo checkout-root validation.

`oh worktree remove <full-task-uuid>` is explicit checkout teardown and never branch teardown. It requires the caller and entry to carry the same non-nil parent session, a recorded worktree path resolving inside `<assignment-root>/.tmp/herdr-orch/worktrees/`, no newest unclosed and unsealed round referencing that path, and no tracked or untracked dirt. Symlinks and textual-prefix siblings cannot escape the managed-root check. Ignored paths are returned but do not refuse removal. A missing checkout reports `missing`. Successful removal retains the branch and reports whether its tip is an ancestor of the parent's live HEAD as information only, since squash and cherry-pick integration need not satisfy ancestry. `close`, `prune`, `orphans`, and `collect --close` never remove a checkout.

The ledger is the authority `oh` needs for list, reconciliation, ownership, and removal. If `<assignment-root>/.tmp/` is cleared first, inspect `git worktree list --porcelain`, remove any surviving checkout explicitly with Git, and run `git worktree prune` to discard stale registration for checkout directories that are already gone. Pruning registration does not integrate or delete the retained `orch/*` branch. Inspect the branch and its tip before the parent separately integrates or deletes it. An external checkout was never owned for teardown and remains an operator-managed Git worktree throughout.

## Close

`oh task close <full-task-uuid>` is the only normal path that closes a spawned child's pane. Capture leaves the pane intact. Closure requires the caller to own the newest live round for that child, every currently published item to be captured, no `:closed-at`, and a live settled (`idle` or `done`) occupant that matches the recorded child and pane. It does not require a sealed stream: a settled monitor between `WAITING` reports can be closed. `close` and `continue` each spend one `ORCH_SETTLE_CLOSE_MS` wait before checking liveness. Both then take the child lock that excludes a concurrent `publish` ([#Ledger and completion](#ledger-and-completion)).

A primary close observation matches both child name and pane id. If the name was released after a resumed process, the shell-pid fallback may close only a live, settled pane whose recorded shell pid still matches and whose foreground is not busy. Otherwise the outcome is `closed`, retryable `retained`/`unsettled`, or `gone`. Only `closed` writes `:closed-at`. Ownership, newest-round, uncaptured, pane-mismatch, and unusable-listing guards refuse without mutation.

`oh task close <full-task-uuid> --abandon` retires the ledger round without touching the pane. It has two paths, selected by whether the round is captured, and both report `abandoned` with reason `pane-left-to-operator`, write `:closed-at` plus `:pane-abandoned true`, and issue no `pane close`: disposing of the pane is the operator's decision, and what the flag recovers is the entry. `collect --close` never applies either path, and `close --settled --abandon` is refused rather than ignored -- bulk abandonment is not granted.

For a **captured** round whose pane cannot be confirmed free, it runs every `assert-closable!` guard first -- ownership, capture, newest round, no `:closed-at` -- and skips only the liveness observation, which is the step that cannot conclude when an occupant reports a non-settled status indefinitely. It grants no authority the ordinary path lacks; the entry it recovers otherwise keeps surfacing in `close --settled` and `orphans` after the pane is gone.

For a round with **no publication at all** -- the measured deadlock, where `close` refused an uncaptured newest round, `prune` refused a still-listed name, and `poke` could recover only by resuming the child -- it demands liveness evidence instead of skipping it. The caller must own the entry (both `:parent-session`s non-nil and equal), the round must be the **newest** for its child (recovery addresses the newest round UUID, never an older round's UUID: an older round is refused naming the newest), it must carry a `:pane-id`, no `:closed-at`, and must not be terminal `failed`. Any published item, captured or not, is refused with the `collect` remedy: an existing item is the child's testimony and is collected, never discarded. Evidence is one positively-usable `agent list` with **no settle wait**: a named observation must match the recorded pane and report `idle` or `done`; `blocked` is refused with the remedy that the operator dismiss the dialog or stop the child manually and retry once a permitted state is proved; `working` and `unknown` are refused. A released name alone is not stopped-process evidence, so it falls back to `close`'s own shell-pid witness: the pane is gone (`pane-absent`), or the pane's `shell_pid` still equals the recorded `:shell-pid` **and** its foreground group is that shell (`shell-idle`). Only a `pane_not_found` lookup proves `pane-absent`; a lookup that fails for any other reason proves nothing about the pane and refuses. A mismatched shell, a busy foreground, a nameless occupant that is not settled, an uninspectable pane, an unreadable `process_info`, or an unusable listing is unusable evidence and fails closed. The evidence used is recorded on the entry as `:abandonment-evidence`, beside `:abandoned-unpublished true`.

The write happens under the child lock ([#Ledger and completion](#ledger-and-completion)) and re-reads the entry there: a publication that took the lock first is preserved and the retirement refuses with the `collect` remedy; a retirement that took it first makes any later `publish` refuse on `:closed-at` without creating an item. A retired no-publication round is discharged from its parent's children guard, so the parent's own terminal publication is no longer blocked by it. Abandonment sends no prompt, keys, or signal to the child; closes no pane; removes no checkout; fabricates no `RESULT` or capture; and deletes no `TASK`, ledger, or artifact file. The response names the retained pane as operator-owned (`"pane-owner":"operator"`). Ordinary `close` stays capture-gated throughout, and `prune` remains the verb for a round whose child is provably absent from the listing and never published.

`collect --close` captures first, then requests this same guarded close. It reports the close outcome beside the capture and never turns a valid capture into a failure. It attempts closure only for a validated terminal capture. A `WAITING`, pending, blocked-wait, or invalid capture reports a skipped close. `close --settled` applies the same rules once to each qualifying newest child round and returns a per-child array. Ownership is absolute; [#Orphans](#orphans) is the verb for it when an operator must clean up a foreign or ended owner.

## Poke

`oh task poke <full-task-uuid>` re-issues the publication instruction to a settled child whose round published nothing, or whose `RESULT` holds prose rather than an envelope. It is the recovery verb for the two measured cases where a parent otherwise adopts unvalidated pane text or respawns and pays for finished work twice.

It applies `continue`'s evidence bar with the stream condition inverted. The caller and the entry must carry the same non-nil parent session. The round must be the newest for that child. It must carry no captured **terminal** status, because a round that published a terminal envelope needs no poke. It must carry no published item the parent has not captured, because an uncaptured item may itself be that terminal envelope. It must have no `:closed-at`. A live settled (`idle` or `done`) occupant must match both the recorded child name and pane id. Unlike `continue` it is not root-only: a delegated parent may poke its own child.

Capture is not publication, and the bar is deliberately a captured terminal *status* rather than capture itself. A fully captured `WAITING`-only round and an `invalid` capture both stay pokeable, which is what makes the verb reach the prose-in-`RESULT` case at all: collect the prose as the `invalid` capture it is, then poke the child that wrote it. Reading the captured records rather than the published stream's seal also covers a pre-stream entry, whose head carries `:status` with no `:envelope` beside it.

The parent-session ownership check is immutable for a round, so it runs once, before the settle wait. The terminal-capture, unconsumed-item, closed, and newest-round guards inside `assert-pokeable!` run twice. The first pass runs before the `ORCH_SETTLE_CLOSE_MS` settle wait. After the wait, `poke` takes the child lock, re-reads the entry, and runs the second pass inside that lock. It keeps the lock through prompt submission and the `:pokes` update. The settle wait stays outside the lock. A concurrent `publish` either wins first and becomes visible to the second pass, or waits until `poke` finishes its mutation ([#Ledger and completion](#ledger-and-completion)).

The only external mutation is the prompt. It allocates no task, creates no round, writes no result path, and never touches a pane, so a refused poke leaves the round byte-identical. The prompt is Herdr's ordinary `agent prompt` without `--wait`; its refusal semantics, and what a failed submission means for `:pokes`, are in [#Start and prompt outcomes](#start-and-prompt-outcomes). A delivered prompt also increments the ledger entry's `:pokes` counter, returned as `pokes` beside `{"status": "poked"}`. Repeated poking is permitted and counted rather than capped: the operator sees the count and decides.

## Orphans

`oh task orphans` lists, and `oh task orphans --close` closes, the captured rounds this session does *not* own -- the cleanup path for a child whose owning parent session has ended, which [#Close](#close) deliberately leaves unclosable through `close`. It takes no task argument. Candidates are the newest live round of each child that is captured, has no `:closed-at`, records a `:parent-session` other than the caller's, and either carries a `:pane-id` or is a measurement ([#Measurement launch](#measurement-launch)). A measurement is admitted only with a sealed stream, an execution proved stopped, and a usable `agent list` in which no agent reports the recorded owner as its session value or pane; an unusable listing admits none. That listing is made only when such a measurement exists, so a listing with none still makes no `agent list` call. Absence proves only that the owner is not attached now, which is enough here because closing a stopped measurement stops nothing and writes only `:closed-at`. The listing form is read-only (no settle wait, no `agent list`, no mutation) and returns the task, child, pane, tab, label, status, capture time, and recorded owner of each.

Both forms are **root-only**, refused before the first ledger read exactly as `continue` is refused before preflight, and both also refuse a caller whose own `:parent-session` cannot be resolved. A delegated child, and equally a caller with no resolvable identity, satisfies `(not= caller (:parent-session %))` for every entry that records an owner -- *including its own captured children* -- so the candidate set degrades to "everyone else's live children", which under `--close` would sweep any captured, settled sibling whose child name and pane id still match. The refusal covers the listing too, not merely the mutation, because the contract has the operator take closing authority straight from that list.

`--close` routes every candidate through the identical machinery single-task `close` uses -- the bounded `ORCH_SETTLE_CLOSE_MS` wait, one `agent list`, and the live child-name-**and**-pane-id match in `idle`/`done`, including its shell_pid fallback for a released name ([#Close](#close)) -- so it closes on no weaker evidence than `close` does: name absence with no confirming shell_pid is `gone` and closes nothing, a pane the child no longer occupies is a refusal, an unsettled child is `retained` and retryable, and an unusable listing is a refusal. A measurement candidate goes through `close`'s measurement path with only the ownership check skipped: it still needs the sealed capture and the stopped execution, and closes its monitor only while the pane still holds the recorded idle shell, so a replaced or busy occupant is reported and left alone. This is what the verb replaces: the previous documented remedy was `oh agent list` followed by `oh pane close <pane-id>`, whose second step closes on a recorded pane id alone, which is precisely the evidence the `gone` outcome exists to reject. Like `close --settled` it returns a JSON **array** of per-task outcomes in `:created-at` order, reports a refusal as `{"status":"refused",…}` inside that array rather than aborting the remaining candidates, and exits 0 regardless -- read the array, not the exit code. An empty array means nothing qualified.

What the verb cannot supply is the judgement that a foreign session is a *dead* one. It is not: a concurrently delegating session's captured, unclosed child matches this predicate exactly, and no available signal separates the two ([#Close](#close)). So the operator supplies that authority -- read the list, confirm each pane, then sweep. Unlike `close --settled`, an `invalid` capture is *not* excluded: the sweep's reason for skipping one is that an operator may need that pane, and here the operator is the one acting.

`oh task orphans --prune` retires a foreign session's *stale* round rather than closing a captured one: the mirror candidate set, uncaptured instead of captured. It applies `prune`'s staleness proof unchanged -- not captured, not terminal, no published item, a usable `agent list` that positively omits the child's name, and the same re-validation inside the final ledger write -- minus the ownership bar, which is the one condition the operator explicitly overrides. It marks each entry `failed` with `prune-reason "missing-agent"` and `pruned-by "orphans"`, and touches no pane. `--close` and `--prune` are mutually exclusive.

## Continue

`oh task continue <full-task-uuid> (--task TEXT | --task-file PATH | stdin) [--wait] [--timeout MS]` assigns a settled child a fresh round in the same pane and context. The new immutable round entry inherits identity and metadata -- including the context, execution and role fields of [#Context modes](#context-modes), and the complete `:worktree` map and its `:read-only` publication policy when present -- has `:continues <prior-task>`, and receives its own waiting policy. The target is neither re-resolved nor recreated, and the prior entry is never rewritten. Slow settle and Herdr inspection remain outside the reservation lock. After settling, `continue` takes this child's lock and then the same assignment-root lock as spawn, re-reads the prior entry and ledger, re-checks captured/unconsumed/newest/closed state and every other live reference to the checkout, then writes the successor before releasing both. Thus an explicit existing-target start and a continuation cannot both reserve the same checkout: whichever writes first makes the other refuse.

It is root-only and refuses unless the caller owns the newest live round, every published item in that round has been captured, the latest capture is valid (not `invalid` or a retired `failed` entry), no sibling round for that child is open, and `agent list` shows the recorded child at the recorded pane in `idle` or `done`. A sealed stream is not required: a fully captured `WAITING` round can continue. The prompt names the new task in every publish command, including `WAITING` for non-blocking rounds. `--wait` returns the first unconsumed item, terminal or not. Otherwise the command returns the new entry. The continuation prompt is a plain `agent prompt`; a failed submission marks the new round `failed` with `:failure-phase "continue-prompt"` and touches no pane ([#Start and prompt outcomes](#start-and-prompt-outcomes)). Root-owned recipe guidance uses continuation only for context-dependent follow-up; [../../references/workflow-recipes.md](../../references/workflow-recipes.md) covers the staged and independent-validation cases.

## Fan-in

`oh task collect --any [--wait --timeout MS]` has two same-session candidate sets. Capture candidates are rounds with an unconsumed item and are the only rounds `collect --any` can return. Wait candidates are broader: live, unsealed, non-failed, non-closed rounds, including a child that has published nothing yet. The split keeps `--any --wait` polling until a child publishes instead of treating an empty capture set as finished. `no-candidates` is returned only when both sets are empty. Failed spawn entries remain excluded.

Each snapshot validates each uncaptured item at most once and supplies both candidate sets plus its capture decision. The `agent list` liveness boundary takes one fresh snapshot before an absence outcome, so a child publishing during that subprocess is still captured. A measurement's execution liveness is read at the same boundary, before that snapshot, so a supervisor that publishes and exits after its liveness read is captured on the same call. A valid capture returns the ordinary collect result plus `remaining`, which counts unconsumed-item candidates only. The wait budget bounds the polling loop. No path closes a pane. Known outcomes remain `pending/no-candidates`, `pending/timeout`, `blocked` when every live wait candidate is blocked, and `pending/no-live-children` when every wait candidate vanished. An unusable listing leaves liveness unknown and continues polling.

**Known limitation -- stale uncaptured fan-in entries.** A `run`/`start` killed between ledger allocation and cleanup can retain a same-session uncaptured, non-`failed` round forever. `prune <full-task-uuid>` is its explicit, ownership-checked remedy below.

## Pruning

`oh task prune <full-task-uuid>` is the explicit, single-assignment remedy for the Fan-in "known limitation" above: a `run`/`start` killed between `ledger/write!` and its cleanup leaves a same-session, uncaptured, non-`failed` entry that no `RESULT` will ever complete and whose named child can never reappear in `agent list`, yet it satisfies the `--any` candidate predicate forever. It takes no other form: it never scans the ledger for candidates and never resolves a partial or prefix id -- the argument is looked up as the exact ledger key, precisely as `collect <full-task-uuid>` and `status <full-task-uuid>` already do.

Ownership is checked first, via the same `parent-identity` the rest of the CLI uses: the caller's own `:parent-session` must equal the entry's recorded `:parent-session`, and **both must be non-nil**, or the prune is refused outright, mutating nothing -- so an unresolvable caller can never own a legacy entry that omits `:parent-session` by a `nil` = `nil` coincidence (the guard in `cli.clj` carries the reasoning). An unresolvable caller identity is refused exactly like a genuine foreign session.

Because that guard is absolute, `prune` is not the remedy for a stale entry left by a *different* session, which is the common case once a session ends: the refusal is correct and the entry stays. `oh task orphans --prune` is the verb for it ([#Orphans](#orphans)). Ownership is the single condition the operator overrides there; every other part of this proof, including the final re-validation, applies unchanged.

Once ownership holds, all of the following staleness proof is required together, checked cheapest-first: the entry has no `:captured-at`, its `:status` is not already terminal (`failed`/`invalid`), no published item exists on disk for it, and -- last, since it is the one Herdr call in the path -- its named `:child` is **absent** from a single `agent list` call. Liveness reuses the exact classification `collect --any` already uses (`live-agents`): agents are indexed by `name` only, with no `pane_id` fallback, and a listing that fails or omits its `agents` key returns `nil`, meaning liveness is unknown. Ambiguous liveness must never allow a prune: only a listing that positively excludes the child's name is proof of absence, never an unusable or missing listing. Age is never evidence, and this command never touches `any-candidates` or `collect --any` itself.

That `agent list` call can itself race a child publishing and exiting inside its own subprocess window -- the identical hazard `collect --any` re-polls to avoid ([#Fan-in](#fan-in)). So the final mutation does not blindly write over the pre-listing snapshot: it re-validates the *freshest* ledger state (a fresh read, inside the same `ledger/update!` call that performs the write) for `:captured-at` and an on-disk item, and refuses -- mutating nothing -- if either appeared during the check. The race-won `RESULT` remains ordinarily collectible afterward.

On success the *existing* entry is mutated in place to `:status "failed"`, `:failure-phase "orphaned"`, plus two audit fields: `:pruned-at` (a timestamp, same style as `:reported-at`/`now`) and `:prune-reason "missing-agent"`. Setting `:status "failed"` is what excludes the entry from `any-candidates` afterward, through the pre-existing `failed` exclusion. `prune` never closes the entry's recorded `:pane-id`. It only ever touches the ledger JSON.

Every refusal case -- foreign session, unresolvable caller identity, a live named child, an already-captured entry, an already-terminal entry, a published item, a capture/publish that raced the liveness scan, or an unusable `agent list` -- fails loudly (non-zero exit, no JSON `result`) without any ledger mutation and without closing anything.

## Retention

`oh task compact <full-task-uuid>` and `oh task compact --closed` retire raw envelope bulk, never ledger entries. Compaction removes `:envelope :text` from the stable head and from every captured `:items` record in the round, then records `:compacted-at` and reclaimed bytes. Parsed fields, item identities, transcript references, artifact links, and the immutable item files remain. `collect` never re-returns a consumed item -- a fully-consumed round reports `pending` -- so after compaction the raw text is reachable only by reading the retained item files directly, and those live in gitignored scratch (`.tmp/`) an operator may clear.

Only the owning session may compact a closed round or terminal failed round. An already compacted round refuses loudly. `compact --closed` takes no task argument, refuses an unresolvable caller, and sweeps the caller's qualifying entries in creation order with per-round refusals. Its final ledger mutation revalidates the fresh entry, refusing if another operation compacted it or made it ineligible during the check. There is no automatic deletion, age threshold, or entry-count cap: ledger entries are the audit trail and task-UUID lookup path.

## Parent push

Under a non-blocking waiting policy, every committed item emits an operator toast. A `WAITING` item is toast-only: it never probes or prompts the parent. A terminal item retains the advisory parent push, which names the child, task, and `collect <full-task-uuid>` command. It is advisory only and never replaces a validated terminal result item as completion evidence. Blocking rounds do not notify a parent, and a ledger-less hand-driven publish stays silent.

The advisory push is sent only to an idle or done parent whose observed session equals the entry's recorded `:parent-session`. A working parent receives one bounded `agent wait --until idle --until done`, then both conditions are checked again. Push failure, timeout, or session mismatch is reported under `result.parent-push` after publication and never changes the item's publish outcome. The push itself is an `agent prompt` without `--wait`; a `blocked` parent fails the gate before it is attempted, and a submission that Herdr refuses is reported as `prompt-failed` ([#Start and prompt outcomes](#start-and-prompt-outcomes)). Declared artifact links in a push are advisory. Only collect-time `artifact-links` are existence-validated.

## Artifact links

An `ARTIFACTS` item (`<path relative to WORK-ROOT>[ :: <purpose>]`) is rendered as a portable Markdown link: `[escaped absolute path](encoded file:// URI) :: escaped purpose`. The visible label is the path resolved against `WORK-ROOT`, so the parent always reads a complete absolute path even though the child declared a relative one. One shared renderer (`core/artifact-link`) produces both surfaces below. It splits the item on the same ` :: ` delimiter as `core/artifact-relative-path` and applies the same containment check. A path that contains ` :: ` mis-splits because the delimiter is envelope grammar and is not escapable. The collect-time existence check then usually rejects the truncated prefix.

A declared path is refused when it is blank, absolute, unusable as a path (a NUL byte, which `Paths/get` rejects), normalises to nothing (`.`, `a/..`), or normalises outside the root (`..`, `../x`, `a/../../b`). Normalisation is lexical, and containment is re-checked on the resolved path, so a textual-prefix sibling of the root (`/tmp/wrong` against `/tmp/wr`) is outside it. Every refusal happens at publication, before the item file or its `.tmp` sibling exists, and `--from-file` is refused identically. `core/envelope` owns the check, so the publisher cannot emit an item the parent could not resolve. The advisory renderer keeps its own drop-and-count fallback because publication is already committed when it runs, but no `publish` input can now reach it.

Publication containment is lexical only, so it cannot see a symlink: `link/secret.md` is inside the work root as text while `link` points outside it. Capture closes that gap. After the existence check, `core/artifact-real-path!` resolves both the artifact and the work root with `Path.toRealPath` and refuses an artifact whose real path is outside the real root. The work root is resolved too, because a temporary root is commonly reached through a symlinked prefix (`/var` -> `/private/var` on macOS). A symlink to a file inside the same root still validates. The check needs the file to exist, so it runs at capture and never at publication, and a refusal records the item `invalid` exactly as a missing artifact does.

This is **portable fallback syntax, not a clickability guarantee**. No raw OSC 8 (or any other terminal-control) escape sequence is ever emitted into model- or operator-visible text. A harness that renders Markdown may turn the link into a terminal hyperlink when the terminal advertises support, and every other reader still sees the full absolute path plus a usable URL. Whether a link is clickable therefore depends on the harness and terminal, never on this contract.

The destination is built with `java.nio.file.Path.toUri`, never by hand, so reserved and non-ASCII characters come back correctly percent-encoded and the result carries the canonical empty authority (`file:///…`, not `File.toURI`'s `file:/…`). `(` and `)` are percent-encoded afterwards, because an unbalanced parenthesis would terminate a Markdown link destination early. Markdown-significant characters (`[`, `]`, `\`, `` ` ``, `*`, `_`, `<`, `>`, `&`, `~`) are backslash-escaped in the visible label and in the purpose text, which must stay readable as the exact path.

The renderer is not pure: `Path.toUri` stats the path, so an *existing directory* artifact's destination gains a trailing slash its label does not have, and the advisory (rendered before the artifact need exist) may differ from the collected link for the same declared line.

The two surfaces carry deliberately different weight:

| Surface | Source | Weight |
|---|---|---|
| The advisory parent push ([#Parent push](#parent-push)), under a labelled `Declared artifacts (advisory — pending validation by \`collect\`)` line | the child's *declared* envelope body | **Not evidence.** Publish checks artifact path shape only, never existence, so a declared link may name a file that never appears |
| `result.artifact-links` on a successful `collect` (single-task and `--any` alike) | the captured envelope, after every artifact passed the `fs/exists?` check and the real-path containment check | Existence-validated and containment-validated as of `:captured-at`; also persisted on the ledger entry as `:artifact-links`, which is what keeps the links reachable through `status`/`list` after the pane and the collect output are gone |

Because publication is already committed when the advisory renders, an artifact path that cannot be rendered at all is dropped from the list and counted (`- (N declared artifact path(s) not renderable as a link; see the RESULT envelope)`) rather than failing the push. The `RESULT` envelope remains the authoritative declared list.

An empty artifact list adds *nothing* on either surface: no advisory section, and no `artifact-links` key on the result or the entry. Absent is not the same claim as validated-empty. An artifact that fails the existence check yields a non-terminal `invalid` item and no links for that item. It does not seal the stream, so a corrected later item may capture normally. `--any` gains links through the shared capture path, so its result remains exactly the single-task shape plus `remaining`.

## Retro gating

`run` and `start` decide whether the composed prompt asks the child to apply steps 1--2 of the `retro` skill to its own session. Precedence is `--retro` / `--no-retro` (value-less flags; supplying both fails fast) > persona frontmatter `retro:` > the built-in default, which is **enabled**. Frontmatter values are always strings, so `retro:` is coerced by an explicit `true`/`false` table. Any other value fails fast at spawn, naming the persona and the value.

"Enabled" means the child *evaluates* the `retro` threshold, never that a retro is forced: that skill owns the threshold, including its non-interactive equivalent, and a gated-in child that finds nothing correctly publishes no `PROCESS` section. `--no-retro` and `retro: false` skip the step entirely -- no prompt paragraph and no token cost. `scout` and `researcher` ship with `retro: false`.

The retro skill path resolves `<assignment-root>/.agents/skills/retro/SKILL.md`, then `<assignment-root>/skills/retro/SKILL.md`, then `~/.agents/skills/retro/SKILL.md`. When none exists the frontmatter and default sources degrade silently -- the instruction is omitted and `:retro-source` is `"skill-missing"` -- because the retro step is optional equipment and an installation without that skill is a supported configuration. An explicit `--retro` is an operator request and fails fast at spawn instead of becoming a silent no-op. `--no-retro` is always honoured. The resolved policy is recorded on the ledger entry as `:retro` and `:retro-source` (`flag`, `frontmatter`, `default`, or `skill-missing`), and `--print-prompt` reports both alongside the composed prompt. Gating shapes the prompt only: a `PROCESS` section published by a gated-out child is still accepted.

## Timeout resolution

The wait budget resolves per round as explicit `--timeout` > persona frontmatter `timeout:` (milliseconds) > the shipped default, 600 000 ms -- the same precedence shape as `model:` and `retro:`, and for the same reason: "give review and implementation work an explicit `--timeout`" was a per-persona constant expressed as a standing instruction to every caller, so the persona declares it once instead. Frontmatter values are always strings, so the value is coerced explicitly and an unparseable, zero, or negative one **fails fast at spawn**, naming the persona and the value, rather than degrading to the default. Resolution runs even when `--timeout` is supplied, so a bad declaration stays loud. The flag is validated by the same rule, so `--timeout abc` and `--timeout 0` are clean refusals rather than a raw `NumberFormatException`. This is unlike the `ORCH_*` environment knobs, where a non-positive or unparseable value deliberately falls back to a default.

A wait that reaches its budget without a result returns `{"status": "pending", "reason": "timeout"}` carrying `child-status`, the child's live `agent_status` read once at that moment (`unknown` when the probe fails). A timeout is not a failure and not an absent result: the child may publish minutes later. The field exists so a caller distinguishes a working child from a vanished one without a second `status` call, which is the step whose omission produced respawns that discarded finished work.

The resolved value is recorded on the ledger entry as `:timeout` and `:timeout-source` (`flag`, `frontmatter`, or `default`), reported by `--print-prompt`, and is what `run` waits with. Recording it is load-bearing rather than informational: `collect <task> --wait` and `continue --wait` both read `--timeout` > the entry's `:timeout` > default, so a `start` plus later `collect --wait`, and every continued round (which inherits `:timeout`/`:timeout-source` with the rest of its metadata), get the persona's own budget without the caller restating it. `collect --any` has no single entry to read and keeps flag-or-default. The shipped declarations are `worker: 1800000` and `reviewer: 1200000`.

## Context modes

`run` and `start` take an optional persona and `--context fresh|fork|measurement`. `fresh` is the default. `fork` and `measurement` launch as described below; an unknown value is refused before allocation. Preview (`--print-prompt`) and launch share one resolver, so stable configuration (role composition, kind, model, effort, placement, retro, spawns, timeout) resolves identically; preview reports `:context` and `:execution`.

A launch with a persona is normal named delegation. A launch without one is persona-less fresh delegation: the child receives the assignment, explicit `--trait` selections and the normal launcher guidance, with no synthetic role text. Kind, model, effort, timeout and retro resolve from an empty frontmatter (parent inheritance and shipped defaults), and the child is a leaf unless the root passes `--spawns`. Explicit traits compose into a file at `.tmp/herdr-orch/composed/<task>-anonymous.md`, delivered as the system-prompt append and named in the prompt as instructions rather than a role. With no traits, no persona file exists and no system-prompt append is passed.

The child's `HERDR_ORCH_PERSONA`, agent name (`anonymous-<task prefix>`), index directory and label use the display token `anonymous`. That token is neither a role nor a permission grant, and no roster lookup reads it. `HERDR_ORCH_ANONYMOUS=1` distinguishes an absent role from a roster persona called `anonymous`. The ledger entry records `:persona "anonymous"` with `:role-absent true`; a named launch records `:role-snapshot {:persona :text :sha256}`, the immutable effective role text at launch, so a later fork reapplies what the child actually ran with. Every entry records `:context` and `:execution` (`"interactive"`, or `"headless"` for a measurement); an entry without them reads as `"fresh"` and `"interactive"` in `status`, and `continue` carries all four fields forward unchanged.

`HERDR_ORCH_PERSONA` is the single delegated-child predicate (placement, spawn gating, spawn policy, `continue`, `orphans`), so an absent role never makes a process look root-owned. Below root, launching without a persona is refused before the name-based allow-list is consulted, even when `anonymous` is allow-listed and a same-named roster definition exists.

## Pi fork adapter

`scripts/pi/fork-adapter.ts` is an explicitly loaded Pi extension (`pi -e`), never installed into Pi auto-discovery, and inert unless `HERDR_ORCH_ADAPTER` selects an operation. It is the only code that forks a session; `oh task run|start --context fork` uses it ([#Fork launch](#fork-launch)). It runs inside the installed Pi process and uses only the public `SessionManager` API (`forkFrom` with the selected checkout as `targetCwd`, `branch`, `appendCustomEntry`); it never rewrites the JSONL format.

Operations read a JSON request from `HERDR_ORCH_ADAPTER_REQUEST`, write a JSON result to `HERDR_ORCH_ADAPTER_RESULT` and exit 0 on success or 1 with `{ok: false, error}`. Results travel in files because Pi does not keep stdout for an extension when stdin is not a terminal.

| Operation | Request | Result |
|---|---|---|
| `fork-capability` | none | `{ok, missing, piVersion, runtime}`. Run before allocation. |
| `fork-create` | `sourceSession`, `targetCwd`, optional `sessionDir`, optional `overlay {persona, text}`, optional `callerRole {named, snapshot {persona, text, sha256}}` | `{ok, sessionFile, sessionId, source {path, sessionId, sha256, leafId, entries}, boundary {entryId, batchEntryId, unansweredToolCalls, answeredToolCalls, messages, rule}, marker {entryId, customType}, role, targetCwd, runtime}` |
| `fork-discard` | a `fork-create` result | `{ok, removed}` |

Boundary rule. The caller's own persistent session is read byte-for-byte and parsed strictly (a malformed or partial line, a version other than Pi's current one, an empty file or a missing file refuses). The launching call is in flight, so the active leaf must be the assistant entry that carries its tool batch, or results of that same batch that already finished, with only metadata entries (`usage`, `label`, `session_info`, `custom`, `thinking_level_change`, `model_change`) between. The caller's current turn is everything after its last completed assistant response on the active path (stop reason `stop` and no tool calls; an error, aborted, `length` or `deferred` response does not end a turn, so its turn is dropped with the current one). The child branches at the parent of the first message of any kind after that response: the request (a user message or a custom message that opened the run), the first message of a continuation without a new request, or a message appended between turns, such as `!` command output, a tool-loadout system message or an extension message. That message and everything after it, including a compaction after it, are dropped with the current turn; a compaction appended directly after the completed response stays on the child's path. So the child inherits only completed turns and the active compaction projection at that point. The caller's request, steering messages, failed attempts and tool work of the current turn, the launching batch and any partial parallel results lie outside the child's active context. Its assignment is therefore its only open request: an inherited unanswered request is otherwise taken as the child's own work. A compaction inside the current turn is not on the child's path. The caller passes any same-turn findings the child needs in the assignment. The adapter refuses, before any fork file exists, when the leaf is not inside a batch, results belong to another batch, no call of the batch is unanswered, the batch parent is null, the caller has no completed earlier turn, nothing of the current turn precedes the launching batch, the projection is empty or holds an unmatched tool call, or the source changed between analysis and copy. A missing boundary is never replaced by empty history or a fresh session.

Provenance. The fork file is independent (a new session id, `parentSession` set to the source), its header `cwd` is the selected checkout (installed Pi takes the runtime working directory of an explicit `--session` from that header, not from the pane directory), and a `herdr-orch-fork` custom entry persists the selected branch. The marker is not model context. The source file is never written. The result reports the source path, hash, leaf and the boundary and batch entry ids the launch actually selected.

Role. With an `overlay`, the overlay's persona and text replace any inherited named role. Without one, an unnamed caller inherits no role, and a named caller must supply its launch-time `:role-snapshot` ([#Context modes](#context-modes)); a missing snapshot or one whose `sha256` does not match its text refuses before a fork file exists. The selected role is returned as provenance and never enters the forked conversation. The adapter infers no task or result identity from inherited history.

Discard removes only a session this adapter created: the header must carry the result's session id and the recorded source as its parent, and the source path is refused outright.

Runtime binding. `scripts/pi/test.sh` runs the adapter checks inside the `pi` on `PATH`, records `pi --version`, fails when the API the extensions resolve reports another version or lives under the repository's `node_modules`, and runs a deliberate mismatch control that must fail. It also requires each suite to report a passing test, so an adapter file the entry point never loads cannot pass unnoticed.

## Pi measurement adapter

`src/herdr_orch/measurement.clj` (the subject launch and transport helper) and `scripts/pi/measurement-adapter.ts` (an explicitly loaded Pi extension, inert unless `HERDR_ORCH_MEASUREMENT_MANIFEST` names a manifest) run one isolated measurement subject. `oh task run|start --context measurement` runs a subject through them under a headless supervisor ([#Measurement launch](#measurement-launch)), and measurement request auditing covers four APIs only (see Request audit below). Neither is installed into Pi auto-discovery, and the helper is the only place that builds the subject argv, environment and input transport.

Configuration (`read-config`) is a closed JSON object. Fields: `systemPromptFile` (optional; absent means empty text), `skillFiles`, `tools`, `extensions` (lists default to empty), `hardTimeoutMs` (required positive integer) and `expectedOutputs`. Unknown fields, wrong types, unreadable inputs, wildcard or duplicate tool names and an `expectedOutputs` path that is absolute or leaves the work root fail before launch. Input paths resolve against the configuration file and are read once: the run holds file texts, not paths, so later edits change nothing. `expectedOutputs` stay relative to the work root, and `check-expected-outputs!` refuses a target that already exists.

Treatment. `compile-treatment` joins the system file text and each skill file's literal text, in list order, with two newlines. An empty or absent part contributes nothing, so the default treatment is empty. The adapter forces this as the complete system prompt from `before_agent_start`, because Pi's native flags still add a cwd section. An empty `tools` list launches with `--no-tools` (zero tools, not the harness default); otherwise `--tools a,b`. Tool names are exact and case-sensitive: the adapter checks the active tool set against the configuration in the first session event and fails before any model request on an unknown name, a wrong-case name or a mismatch.

Isolation. The subject is `pi --offline --no-session -ne -e <extensions> -e <adapter> --no-skills --no-prompt-templates --no-context-files --no-mcp <model/effort args> <tools> --mode json -p <sentinel>`. Explicit extensions load before the adapter, so it audits after their changes. Nothing is discovered from home or project. The assignment never appears on argv: it is written to a file and the adapter replaces the neutral sentinel with it from the `input` event, so leading `/`, `@`, `-` and template-like text stay literal. The caller closes stdin. `subject-env` removes every `HERDR_*` and `ORCH_*` value, adds the task-bound `HERDR_ORCH_SUBJECT` marker and keeps provider credentials.

Request audit. Before execution the adapter derives an expectation from the treatment, tools, provider auth and the model's compatibility flags, then audits each actual provider request and ends the process before a failing request is sent. Request-level audit coverage is exactly four Pi APIs, chosen by the user: `anthropic-messages`, `openai-completions`, `openai-responses` and `openai-codex-responses`. Any other API fails closed at its first request, before it is sent, with `no request audit exists for API <api>`. This limits measurement only; fresh delegation and forks are not restricted by API. The audit is of the actual request, never of a provider-neutral transcript. Within the four APIs no otherwise supported model is excluded: a model that declares `compat.allowedFallbackModels` (built-in `claude-fable-5`) is measured under the derived fallback list below, and the built-in OpenRouter Anthropic Chat Completions models (`cacheControlFormat: "anthropic"`) and OpenRouter reasoning models under derived `cache_control` markers and `reasoning_details` replay (Transcript content below). The permitted Pi adaptations for `anthropic-messages` are:

- Anthropic OAuth (an API key containing `sk-ant-oat`): the first system block is `You are Claude Code, Anthropic's official CLI for Claude.`, and tool definitions and historical `tool_use` names follow `toClaudeCodeName`, a case-insensitive lookup in Pi's canonical Claude Code tool list that otherwise leaves a name unchanged. Configured selection stays exact and case-sensitive, and converted-name collisions fail before any request. Other auth modes expect neither change.
- Declared fallbacks (owner-approved): when the model declares `compat.allowedFallbackModels`, the installed consumer sends top-level `fallbacks` as that list reduced to `{model}`, in order, with the `server-side-fallback-2026-07-01` beta (encoding). The audit derives exactly that list (recorded as the `model-fallbacks` adaptation); an altered, added, dropped or reordered target, or an extra field, fails, and a model that declares none expects no `fallbacks`. Only this consumer reads the setting, so the OpenAI APIs expect none. A fallback can change which model serves a turn: `terminal.json` and the event stream record, per assistant turn, `requestedModel`, `allowedFallbacks` and the provider-reported `servedModel`. Pi surfaces `responseModel` only when it differs from the requested id (Anthropic, Chat Completions) and not at all on Responses and Codex, so an absent value is recorded as `servedProvenance: "unknown"` with `servedModel: null`, never guessed; a reported served model outside the declared list is recorded with `servedModelDeclared: false` and is provenance, not a request-audit failure (an alias may be served under its dated id).
- `supportsMidConvoSystemMessages` and `supportsMidConvoToolChanges` with a non-empty tool list: exactly one trailing `__pi_deferred_placeholder__` definition (description `Reserved placeholder. Never available. Never call this.`, an empty-object `input_schema`, `defer_loading: true`). It is a protocol artefact, not an executable tool: a call to it, or to any unconfigured tool, is refused and fails the run.
- `supportsMidConvoEffort` with thinking not disabled (thinking counts as disabled only for a reasoning model whose level is off and which maps `off` to a real setting): empty-content system messages carrying only `output_config.effort`. Positions and levels are derived before comparison from the transcript Pi recorded and the resolved thinking level, never from the payload: one marker directly before each earlier assistant turn whose recorded `providerThinkingLevel` is a valid effort for the same provider and API, then one trailing marker carrying the active effort. The active effort is `high` unless the model forces adaptive thinking, when the resolved level maps through `thinkingLevelMap`, else `minimal`/`low` to `low`, `medium` to `medium` and anything else to `high` (the installed provider's rule). Without a recorded history the audit refuses rather than assumes.

Transcript content. The audit records Pi's own message for every user, assistant and tool-result message (`message_end`) and derives the whole expected message list from it under the API's own conversion, then compares it by value with the request: assistant text, thinking (signed, redacted or replayed as text), tool-call ids, names and arguments, and tool-result ids and text; Anthropic `tool_use.input`/`tool_result`, Chat Completions `tool_calls`/`tool` messages (compat flags `requiresToolResultName`, `requiresAssistantAfterToolResult`, `requiresThinkingAsText` and `requiresReasoningContentOnAssistantMessages` derived like the provider), and Responses `reasoning`, `message` (id and phase from the recorded signature), `function_call` and `function_call_output` items. Anthropic `cache_control` and string-versus-block content are encoding. On Chat Completions a turn whose recorded thinking signature is a valid reasoning-detail list (OpenRouter), or whose tool calls carry a legacy encrypted detail, replays it as `reasoning_details` instead of a raw reasoning field, as `convertMessages` does; and with the resolved `cacheControlFormat: "anthropic"` (explicit, or detected for provider `openrouter` with an `anthropic/` model id) the instruction message, the last tool and the last conversation message with text carry the derived `cache_control` marker (`{type: "ephemeral"}`, plus `ttl: "1h"` under long retention), a string content becoming one annotated text part. Both are derived from the resolved compatibility and the recorded transcript and compared by value, so a moved, reshaped, added or dropped marker, text changed inside an annotated part, or altered or dropped reasoning details fail. An expectation is never learned from the request under audit.

Tool definitions. Each configured tool's name, description and parameter schema (property names, descriptions, enum values, nesting) are derived from the tool registry before the run and compared by value on every audited API, in the provider's own shape (`input_schema` with `type`/`properties`/`required` for Anthropic, `parameters` otherwise). The `strict` flag is protocol encoding the registry does not expose: when a definition declares `strict: true` its schema must equal the strict-mode derivation of the registry schema (a port of Pi's `makeStrictJsonSchema`, with Anthropic's unsupported-keyword rules), and a schema with no strict derivation fails. A Chat Completions tool object carries only `type` and `function` (plus the derived `cache_control` on the last tool), and its `function` only `name`, `description`, `parameters` and, exactly when the resolved `supportsStrictMode` is not false, a boolean `strict`.

OpenAI-family expectations come from the installed consumers and permit no auth or compatibility adaptation that adds text (the Anthropic-only flags never apply to another API):

- `openai-completions`: one leading message holding exactly the treatment, and none when the treatment is empty. Its role is derived from the selected model, never accepted from the payload: `developer` when `model.reasoning` and the resolved `supportsDeveloperRole` (the model's `compat` over the provider/base-URL defaults of `detectCompat`) hold, otherwise `system`. The assignment is the only user message; function tools are named exactly as configured; the rest of the conversation is the transcript-derived list.
- `openai-responses`: one leading item holding exactly the treatment (none when empty) whose role is derived like the Chat Completions one (`developer` when `model.reasoning` and `compat.supportsDeveloperRole !== false`, otherwise `system`), then the transcript-derived input. With `compat.supportsMidConvoEffort` and a resolved thinking level (and not a ChatGPT sign-in credential) `configuration_update` items are expected: one before each earlier assistant turn from the same provider, API and model whose recorded `providerThinkingLevel` is set, then one trailing item carrying `thinkingLevelMap[level] ?? level`. These items are protocol encoding of the same kind as the Anthropic effort markers (owner-classified): positions, content and levels derive from the selected configuration, the resolved level and the recorded history, and a dropped, added or altered item fails. This does not permit arbitrary configuration updates.
- `openai-codex-responses`: the treatment is top-level `instructions`, or Pi's fixed `You are a helpful assistant.` when the treatment is empty (owner-approved, recorded as the `codex-default-instructions` adaptation: exactly that text, only for an empty treatment, and no other default text on any API is implied); the input carries no system item.

For all three, any `additional_tools`, `tool_search_*`, custom/grammar tool, mid-conversation system or developer update, extra user message, unknown item type or unknown top-level field fails closed, because the whole message list must equal the transcript-derived one. Tool-result images and placeholders (owner-approved) are derived from the recorded result content, its error state and the model's image capability (`model.input` includes `image`), through the installed consumer rules, never accepted from the request. A model without image input gets `(tool image omitted: model does not support images)` in place of each run of images, on every API. With image input: `anthropic-messages` sends image blocks inside the `tool_result`, adds a `(see attached image)` text block when the result holds no text, and for an error result puts `(image attached after the tool results)` in the result and sends the caption `Images from the error result of tool call <id> (<tool name>):` plus the images after all results of the turn in the same user message; `openai-completions` sends a `tool` message (`(see attached image)` when there is no text, `(no tool output)` when the result is empty) and one user bridge message `Attached image(s) from tool result:` with the `image_url` blocks after the whole group of results (preceded by `I have processed the tool results.` when `requiresAssistantAfterToolResult`); `openai-responses` and `openai-codex-responses` send `input_text` and `input_image` parts inline, or the string `(no tool output)` for an empty result. An empty Anthropic result is the empty string. A changed caption, bridge or placeholder text, changed image bytes or MIME type, an added or dropped image or a wrong capability fails. Still failing closed: a user message with an image (the assignment is literal text), a tool-result block that is neither text nor image, an assistant turn from another provider, API or model, assistant message ids over 64 characters and grammar-constrained tools. The complete pre-request payload is written to `request-N.json` for every audited request, including a failing one.

Protocol encoding is recorded apart from the treatment and is not compared with it, but it is derived and compared by value too. Every top-level field other than the context (`messages`, `system`, `input`, `instructions`, `tools` and the derived `fallbacks`) is built before comparison by `deriveTopLevel` from the selected model, its resolved compatibility, the resolved thinking level and the configured runtime inputs, under the installed `buildParams`/`buildRequestBody` rules: `model`, `stream`, `store`, `stream_options`, the Anthropic `betas` (computed, or a configured `anthropic-beta` header on the model or its auth), `thinking` (disabled, adaptive, or `enabled` with `budget_tokens` from the settings `thinkingBudgets` over Pi's defaults and the cap) and `output_config.effort`, the Chat Completions effort, thinking, `enable_thinking`, `reasoning` and `chat_template_kwargs`/`chat_template_args` fields per `thinkingFormat` (template values only from the model's configured templates), the thinking-budget field, `tool_stream`, `priority` and routing, the Responses `reasoning` and `include`, the Codex `text`, `include`, `tool_choice` and `parallel_tool_calls`, the prompt-cache key (the session id) and retention fields (`PI_CACHE_RETENTION`), and the model's sampling parameters for the level. The agent passes no temperature, tool choice, metadata, service tier, response format or text format, so none is expected. A changed, added, missing or nested-altered value fails. The output cap (`max_tokens`, `max_completion_tokens`, `max_output_tokens`) is clamped by Pi's context-token estimate, which the adapter cannot reproduce, so it is checked against the range derived from the model's `maxTokens` (known limit), and each budget derived from it is exact. `expectation.json` records these runtime inputs and `audit-N.json` `protocol.encoding` the derived fields. An `anthropic-beta` header or `PI_CACHE_RETENTION` value that only a `before_provider_headers` extension or a provider auth environment supplies is not seen and fails closed. Any other tool field or system block field fails. The recorded transcript holds exactly one user message and it must equal the assignment, and `tool_addition`, `tool_removal` and `tool_reference` blocks fail as mid-conversation tool changes. This audit is reproducibility and context control, not an operating-system sandbox: explicit extensions are trusted code.

Evidence under `<evidence-dir>/adapter/`: `manifest-record.json` (runtime, input hashes, tools), `expectation.json` (the expected adaptations and the provider-to-configured tool map, apart from the treatment), `request-N.json` and `audit-N.json` per request, `events.jsonl` (tool activity and assistant stops) and `terminal.json`. The verdict is written at Pi's `agent_settled` event, the final notice that no automatic retry, compaction or queued continuation will follow; `agent_end` can precede those. A provider request after a failed or aborted turn (Pi's agent-level retry, enabled by default) is refused before it is sent and fails the run with the original error retained, and `session_before_compact` is cancelled and recorded as a violation, so a sample is never retried or summarised. A process that ends before `agent_settled` leaves no terminal evidence, which `interpret-evidence` treats as failure. The installed runtime catches and ignores an exception thrown by a `before_provider_request` handler and then sends the request, so the audit handler never throws or returns on failure: any audit or evidence-write exception ends the process (exit code 5) before the request is sent, even when the failure evidence itself cannot be written. No credential is recorded. `interpret-evidence` takes `terminal.json`'s recorded request count as the authority and reports success only for a well-formed `terminal.json` with `success: true`, no violations, at least one request, and, for every recorded request N, a parseable `request-N.json` and an `audit-N.json` that is `ok` with no violations; a missing or malformed file, a harness error, a missing or failed audit, a request count that is absent or not an integer, or an audit file beyond the count is a failure. This is execution success, not answer quality.

Checks run inside the installed Pi with `scripts/pi/test.sh` ([#Pi fork adapter](#pi-fork-adapter) describes the runtime binding); the end-to-end cases launch a real subject through the helper against local fake Anthropic and OpenAI-family endpoints, so the installed provider builds the audited request. Each of the four APIs has a passing baseline and known-bad controls for changed tool-result text, injected assistant content, changed tool-call arguments, ids and names, changed tool descriptions and schemas, and, for every result shape (empty, image-only, mixed, error with image, text-only model), changed image bytes, MIME type, caption, bridge, placeholder and omission text and an added or dropped image, each retaining its complete pre-request payload, plus fallback list, Codex instruction, configuration-update and audit/evidence failure controls. Top-level encoding has a passing installed-provider control per API (adaptive and budget Anthropic thinking with a configured `thinkingBudgets` value, Chat Completions effort, Responses and Codex reasoning) followed by changed effort, budget, cap, beta, thinking field, output format, template text, include, verbosity, parallel-call, cache-key, tool-choice, metadata and nested-field mutations, each blocked before the request is sent; the three runtime inputs the adapter reads itself (a configured `anthropic-beta` model header, `PI_CACHE_RETENTION=long` and the model's `samplingParams` with `samplingParamsByThinkingLevel`) each have an installed-provider control that shows the value only that input produces and a blocked tamper; the built-in `~anthropic/claude-sonnet-latest` compatibility runs a two-request tool exchange with streamed `reasoning_details` and is blocked for stripped, reshaped, moved or added `cache_control`, changed annotated text, an added tool-object key, a changed OpenRouter effort and altered or dropped reasoning details. A pure literal matrix covers each per-API encoding rule, and the tool-selection case observes the work root before cleanup, with a configured `bash` positive control whose side effect it detects. The fixtures are the fake endpoints, a served-model override and an explicit `snap` test tool; no credential, external request or live model is involved.

### Fork launch

`--context fork` forks the caller's own persistent Pi session through [#Pi fork adapter](#pi-fork-adapter) and launches the child with `--session <fork file>`. It fails before allocation unless the resolved kind is `pi`, the caller is a `pi` agent whose Herdr `agent_session` is a readable file path, and the adapter's `fork-capability` check passes on the installed runtime. Unsupported combinations never fall back to a fresh session. The fork is created after the target checkout exists, so with `--worktree` the forked header `cwd` is that checkout.

The effective persona decides authority, as for any launch. An explicit persona is the overlay and replaces any inherited role; the CLI passes its composed text to the adapter and records it as the child's `:role-snapshot`. Without one, an unnamed root inherits no role (the child is persona-less, `HERDR_ORCH_ANONYMOUS=1`), and a named delegated caller inherits the `:role-snapshot` on its own ledger entry (found through `HERDR_ORCH_TASK`) and reapplies that text instead of rereading the roster. Below root the inherited persona must be in the caller's `HERDR_ORCH_SPAWNS` allow-list; an inherited persona outside it, a persona-less caller, or a named caller with no recorded snapshot is refused before allocation. An admitted below-root fork is still a leaf with source `depth`.

The ledger entry carries `:context "fork"` and `:fork {:source-session :source-session-id :source-sha256 :source-leaf :boundary-entry :batch-entry :boundary-rule :session-file :session-id :marker-entry :target-cwd :role-source :runtime}`; the start envelope reports it, so the boundary entry is the one this launch selected. `--print-prompt` reports `:fork {:source-session :boundary-rule :role-source}` and `:effective-persona` without a boundary entry, because the boundary depends on the invocation. The fork bootstrap puts a task boundary before the current delegated assignment: earlier requests and tool actions are context, not work to resume unless the current assignment explicitly asks for it. Relevant inherited context and compatible constraints remain available; the selected role and current delegation policy still apply. Only the current launch's TASK and RESULT route publication, not earlier task, result or identity values. These instructions define the emitted contract, not a guarantee of model compliance. A failed launch discards only the fork file it created (the adapter's `fork-discard`) and closes only its owned pane. `continue` carries `:fork` forward and never forks again. `HERDR_ORCH_PI_BIN` overrides the `pi` executable that runs the adapter.

### Measurement launch

`--context measurement --measurement-config PATH` runs one isolated Pi subject headless through [#Pi measurement adapter](#pi-measurement-adapter). Before preflight and any allocation it refuses a positional persona, `--trait`, `--prompt-extra`, `--retro`, `--no-retro` and `--spawns`, and requires `--measurement-config`; every other context refuses `--measurement-config`. A delegated caller cannot launch one (an absent role, [#Spawn gating](#spawn-gating)). The configuration is then read and frozen, kind resolves from the caller's harness and must be `pi`, and model, effort and `--timeout` resolve as for a persona-less launch. `--print-prompt` reports the exact compiled treatment as `:preview`, the literal `:assignment`, `:measurement` (config path, input hashes, tools, extensions, hard limit, expected outputs), the model and effort arguments and `:monitor`, with no allocation. Checkout selection, reservation and `--worktree` are unchanged; measurement is not read-only. An `expectedOutputs` target that already exists is refused before allocation for a present checkout, and after creation for a new managed one.

Detachment is verified on Linux only: the platform must be Linux with `setsid` on `PATH` and a readable `/proc`; any other platform, Darwin included, is refused before any allocation or subject launch. Launch writes the entry, freezes the inputs with the adapter helper's `launch-spec` (`treatment.txt`, `assignment.txt`, `manifest.json`, `inputs.json`) and writes `run.json` (the subject argv, work root, hard limit and expected outputs; no environment, so no credential) under `<assignment-root>/.tmp/herdr-orch/measurements/<task>/`. It then starts the supervisor (`herdr-orch.supervisor`, the same bb runtime and classpath) through `setsid` with stdin from `/dev/null`, stdout and stderr in `supervisor.out`/`supervisor.err`, and an environment without any `HERDR_*` or `ORCH_*` value except `ORCH_ASSIGNMENT_ROOT`. `start` acknowledges only after `/proc` shows the supervisor leading its own session and process group, outside the invoker's session, and the ledger records `:supervisor {:pid :start :pgid :sid}`, where `:start` is the kernel start time, so a reused PID never matches. The supervisor launches no subject until it reads that record (and gives up 30 s after its own start), so a launcher that dies before acknowledging leaves no subject. The entry also records the launcher's own identity as `:launcher {:pid :start :pgid :sid}` at reservation, and the launcher writes `launching` and the acknowledgement only over the status it wrote last: a round retired or closed while the launcher was delayed keeps that state, the launcher fails with `retired or closed during launch`, and no supervisor or subject starts after it. If the supervisor never leads its own session, the launch failure names `supervisor.err`.

The supervisor owns the run. It starts the subject with the frozen argv in the work root, stdin from `/dev/null` and stdout/stderr in `subject.stdout`/`subject.stderr`, and the environment `subject-env` builds from its own (no routing, the `HERDR_ORCH_SUBJECT` marker, provider credentials kept). Its session is the ownership unit: the subject and every descendant that stays in it. `hardTimeoutMs` bounds that tree: on expiry, and after a normal exit too, every other session member gets TERM, then KILL after 2 s, for at most 10 s. `--timeout` stays the non-destructive wait budget. Execution succeeds only with exit 0, successful terminal adapter evidence and an `ok` audit for every recorded request (`interpret-evidence`), every expected output present as a new regular file, and no session member left. A crash, a non-zero exit, malformed or failed evidence, an audit failure, a missing output or hard-limit expiry is a failure; a sample is never retried. `execution.json` records the outcome, reasons, exit, supervisor and subject identities, cleanup and outputs. The supervisor then publishes once through `publish-execution!`: `COMPLETE` or `FAILED`, a one-line summary (success is execution evidence, not an answer-quality score), the present expected outputs as artefacts and the evidence directory and reasons as findings. Publication takes the same child lock, stream seal, capacity, artefact and worktree-checkpoint rules as `publish`, validating the body before the checkpoint can commit, but is bound to the recorded supervisor identity rather than to an injected child environment or a pane; it never resolves Herdr identity and applies no discharge check, so open sibling rounds never block it. It sends no toast and no parent push ([#Parent push](#parent-push)), whatever the waiting policy: `collect` or `collect --any` reads the result. An interactive `publish` naming a measurement round is refused. If publication fails, `publication-error.json` records why and all evidence stays.

No pane is created by default. An explicit `--tab` or `--split` opens a read-only monitor after acknowledgement, with existing placement semantics but never the configured placement default, recorded as `:monitor {:pane-id :tab-id :shell-pid :placement}` apart from `:pane-id` (which stays `nil`). It runs `herdr-orch.supervisor monitor <evidence-dir>`, which prints the supervisor log, the subject's JSON events as tool activity and errors, its stderr, the adapter events and the execution state, and exits when the run stops. It holds no handle on the run: closing it or typing into it changes no input, stops nothing and publishes nothing. A monitor failure is recorded as `:monitor-error` and never fails the launch.

Execution state (`status`, waiters and lifecycle guards) comes from process identity, never from a pane or an agent: `running` while the supervisor or any member of its session is alive, `finished` once stopped with `execution.json`, `supervisor-lost` once stopped without it, and `launching`/`not-started` before the identity is recorded: `launching` while the recorded launcher or a self-recorded supervisor lives, however long checkout creation takes, and `not-started` once both have stopped, because no acknowledgement can then follow. Before classifying a pre-acknowledgement snapshot as stopped after launcher death, the reader refreshes the ledger entry and honours any recorded supervisor acknowledgement, even when `supervisor.json` is not written yet. A launcher observed live stays live for that observation; a refresh error propagates rather than proving death. An entry without `:launcher` (written before it existed) is `launching` until 30 s after `:created-at`. `status` reports `:execution-state` and the monitor's own `:live?` separately. `collect --wait` and `run` poll the result stream while the execution lives and return `pending` with reason `timeout` or, once the execution is proved stopped with nothing published, `execution-stopped`; `collect --any --wait` counts a live execution as a live candidate.

Lifecycle. `continue` and `poke` refuse a measurement round. `close` needs ownership, a captured terminal result and a stopped execution; it closes the monitor only while its pane still holds the recorded shell with nothing else in the foreground, and otherwise reports it `gone`, `replaced` or `retained` and leaves it. `close --abandon` refuses; `close --settled` includes captured measurement rounds. `prune` and `orphans --prune` retire an unpublished round only when its execution is proved stopped (supervisor and every session member gone), never merely on a dead supervisor or a live launcher, and record a `:prune-reason` that names the evidence: `publication-failed` when `publication-error.json` exists, `not-started` when no supervisor was acknowledged, otherwise `supervisor-lost`; no evidence file is removed. Both prune paths recheck execution liveness on the current entry inside their final ledger update and refuse an acknowledgement that arrived after the initial stop observation. `orphans` and `orphans --close` admit a captured measurement only once its owner has ended ([#Orphans](#orphans)). `compact` keeps `:context`, `:execution`, `:measurement` and `:supervisor`. `harvest` reads no `PROCESS` items from a measurement. `worktree remove` refuses a checkout whose measurement is unsealed or whose execution is still live. [../../references/workflow-recipes.md](../../references/workflow-recipes.md) specifies root-owned repeated samples, optional monitors and evidence retention before managed-checkout teardown.

## Spawn gating

`run` and `start` resolve the child's spawn allow-list -- the personas it may itself spawn -- with precedence `--spawns` (value-bearing; whitespace- and/or comma-separated, deduplicated) > persona frontmatter `spawns:` > the built-in default, which is **deny** (the empty list). The literal flag value `none` forces the empty policy without consulting the roster. An absent key and a present-but-blank frontmatter value both mean leaf, not an error. An unresolvable persona name in either the flag or the frontmatter fails fast at spawn, naming the declaring persona, the offending name, and the source.

The resolved policy is recorded on the ledger entry as `:spawns` and `:spawns-source` (`flag`, `frontmatter`, `default`, or `depth`), reported by `--print-prompt` alongside the composed prompt, injected into the child as the space-joined `HERDR_ORCH_SPAWNS`, and composed into the prompt's delegation guidance: a non-empty policy renders the may-spawn sentence, an empty one the leaf sentence.

Depth is bounded to one nesting level absolutely, with no depth counter: a CLI whose own `HERDR_ORCH_PERSONA` is set is below root. Below root, a target persona absent from the caller's own `HERDR_ORCH_SPAWNS` is refused before preflight, ledger allocation, and any pane mutation -- a refused spawn writes no ledger entry and creates nothing billable. A spawn that passes this gate and then fails at `agent start` is a different case: it has a ledger entry and a pane, and takes the start-failure cleanup of [#Start and prompt outcomes](#start-and-prompt-outcomes). Blank and unset `HERDR_ORCH_SPAWNS` both deny. The empty-string/unset distinction is never load-bearing. An explicit below-root `--spawns` with any value other than `none` fails fast, and a permitted below-root spawn always injects an empty grandchild `HERDR_ORCH_SPAWNS` with source `depth`, regardless of the grandchild persona's frontmatter. A root CLI (no `HERDR_ORCH_PERSONA`) is unrestricted in what it may spawn. Below root, a persona-less launch is refused before the allow-list check ([#Context modes](#context-modes)).

## Labels and geometry

Labels are `<persona>-<index>[-<model-basename>]`. A below-root child is `<parent-persona>-<n>/<persona>-<index>[-<model-basename>]`, prefixed from the spawning agent's injected `HERDR_ORCH_PERSONA`. Workspace names are excluded. Labels are display metadata only: capability and depth are enforced by [#Spawn gating](#spawn-gating), never by label parsing. Direction is `right` only when the caller's own matching layout pane rect has `width >= 80 && width >= 2 * height`, otherwise `down`. Tab area is irrelevant.

## Placement

Placement resolves as explicit `--tab`/`--split` flag > configured `:defaults :placement` > code fallback `"split"`. A configured `:tab-split` resolves to tab at root and split below root, using `HERDR_ORCH_PERSONA` as the depth discriminator. The shipped `subagents/config.edn` sets `:tab-split`, so out of the box a root-level child gets its own tab while a grandchild splits its parent's pane ([../../README.org#Child placement](../../README.org#child-placement) records why). The code fallback stays `"split"` and is deliberately *not* kept in step with the shipped value: it fires only for a config that declares no `:placement` at all, which the shipped file always does. A resolved split creates the child with `pane split --pane $HERDR_PANE_ID --direction ... --cwd ... --no-focus --env ...` in the caller's pane, choosing `--direction` as above. A resolved tab (from `--tab` or config) creates the child with `tab create --workspace $HERDR_WORKSPACE_ID --cwd ... --label ... --no-focus --env ...` in a new tab of the caller's Herdr workspace. The child pane is `.result.root_pane`, distinct from `.result.tab` (whose `tab_id` is recorded but never separately focused). Both *delegation* placement calls pass `--no-focus` unconditionally: delegation never moves the UI, at any depth, and no spawn flag or configuration re-opens it. That statement is scoped to delegation. The raw passthrough `oh pane split [--pane PANE] [--focus]` (and the Pi `herdr_layout pane_split` tool over it) may name another source pane, infers an omitted direction from *that* pane's rect, and may request focus with `--focus`; its default is still the caller's pane, unfocused. Tab placement skips the `caller-rect!`/direction computation entirely -- it needs neither. Every other step (env injection, `pane rename` onto the child pane, `agent start`/`prompt` -- whose failure outcomes are in [#Start and prompt outcomes](#start-and-prompt-outcomes) -- wait/collect, and `close`, which also closes a tab whose last pane it takes) is identical between the two placements.

Placement is resolved per spawn: it is never persisted per-child, never inherited via environment, and no child environment variable carries it. A child's own spawns resolve from config and depth alone. The ledger entry records `:placement` (`"split"` or `"tab"`) and `:tab-id` (the created tab's id, `nil` for a split placement).
