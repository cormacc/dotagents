#+TITLE: General-purpose agent skills

These top-level skills are symlinked into =~/.agents/skills/= by the editable Home Manager route, or installed by an Agent Skills-compatible loader. They are harness-agnostic unless their own compatibility field says otherwise. Pi-only skills that require pi extensions live under [[file:../pi/skills/][../pi/skills/]].

The =org-tasks=, =org-plan=, and =org-jira= skills are also the generic-skill slice shipped by the =@cormacc/agent-org-memory= pi package alongside the =tasks=, =jira=, and =emacsclient= extensions. See [[file:../README.md][../README.md]] for exact package boundaries and install routes.

This inventory is maintained by hand: every top-level =skills/*/SKILL.md= frontmatter name should appear exactly once below, and every listed file should exist. =gh skill list --dir skills/ --json skillName,sourceURL,version= enumerates the same set mechanically, and gives a non-empty =sourceURL= to each =gh skill=-managed entry -- which is the vendored set except =gitlab-cli-skills=, whose own sync script installs it. The =check-metadata.ts= script that once enforced this was retired on 2026-08-11: it also kept a duplicate of =oh='s persona-frontmatter contract, which drifted in both directions -- missing the live =timeout:= key while allow-listing a =requires:= key no persona uses -- so the check sat red and was ignored. Frontmatter is validated where it is used, at spawn, and =oh= will grow a check when a real failure calls for one.

Document format follows the audience, not the directory. A skill's =SKILL.md= and anything an agent loads on demand -- the =references/= bodies -- are Markdown, because the Agent Skills spec requires it for the former and internal consistency argues for it in the latter. Repository documentation written for humans is org: this file, each skill's =README.org=, the design records, and everything =org-tasks= manages. Getting this backwards costs a lossy conversion in both directions; it happened once, converting an agent-facing reference to org and back.

** Vendored
Maintained upstream and re-synced rather than edited here. Do *not* apply local repository conventions to these bodies -- no prose reflowing, style normalisation, or wording edits, because every local change is lost on the next sync and inflates the diff against upstream. Fix a problem upstream, or record it as a local task naming a non-vendored destination. Deliberate divergence is allowed, but it is a reclassification: move the skill to "Adopted or adapted" and say what diverged.

The mechanism is =gh skill=, run against the committed tree from the repository root:

#+begin_src sh
gh skill install <owner/repo> <skill-or-path> --dir skills/ --force  # (re)vendor
gh skill list   --dir skills/ --json skillName,sourceURL,version     # inventory
gh skill update --dir skills/ --dry-run --all                       # read-only drift check
#+end_src

=gh skill install= injects =metadata.github-repo=, =github-path=, =github-ref= and =github-tree-sha= into the body's frontmatter, and =update= compares that tree SHA against the remote. Provenance therefore lives in the file rather than in a lockfile -- do not commit a =skills-lock.json=, and never hand-write or hand-edit a =metadata.github-*= value. "Byte-identical to upstream" means identical apart from that block and the frontmatter re-serialisation the tool performs; the prose is upstream's. To compare a managed body against upstream, build a =raw.githubusercontent.com= URL from its own =github-repo=, =github-path= and =github-ref= instead of guessing the repository layout; a =github.com/blob/= URL answers 301 whether or not the path exists, so it cannot confirm one.

Drift is tracked by content hash rather than by upstream commit: a source revision churns on every unrelated commit to the source repo while saying nothing about whether the skill itself moved, and =github-tree-sha= also catches a body swapped behind an unchanged tag. The managed set is deliberately left unpinned, because =gh skill update= skips a pinned skill and would suppress that signal; review =update --dry-run --all= and apply deliberately. Pass =--all=: without it, an interactive terminal stops at =? Repository for <skill> (owner/repo):= for the first skill carrying no metadata, which is most of this tree. The warnings it prints for those skills are noise, not errors.

=gitlab-cli-skills= is the one exception, and it is a permanent one because upstream ships a flat collection: a =gitlab-cli-skills/= router directory beside 47 standalone =glab-*/= directories, all at the repository root, each with its own =SKILL.md=. =npx skills add= therefore installs 48 sibling skills, and every one of their descriptions enters discovery -- 14,572 characters of trigger text at the last sync. This repository nests them under the router instead, so a harness discovers one description and the router loads a command group on demand. Re-sync with =scripts/sync-gitlab-cli-skills.bb=, which re-nests upstream deterministically, re-applies the local router description, and records the upstream commit in =gitlab-cli-skills/.vendor.edn=. Child-to-child links (=../glab-x/SKILL.md=) hold in both layouts because siblings stay adjacent; only the router's own links are rewritten. Retire the exception if the CLI gains a nested-collection install mode.

=herdr= used to be an exception because upstream shipped its =SKILL.md= at the repository root, where an installer resolves the skill to the whole repository and drags in the entire Rust project. Upstream has since repackaged it under =skills/herdr/=, which retires the exception on its own terms. Install it by skill name (=gh skill install ogulcancelik/herdr herdr --dir skills/=); the exact-path form (=... herdr SKILL.md=) is rejected.
