** TODO [#B] Skill vendoring improvements :project_convention:
:PROPERTIES:
:CUSTOM_ID: 98cf369c-83aa-4961-bf8b-2fa3aca8b2f3
:CREATED: [2026-07-31 Fri 13:17]
:END:
:LOGBOOK:
- Created [2026-07-31 Fri 13:17]

Vendored third-party skills (dirge, find-skills, skill-creator, herdr) currently sit hand-copied inside the published `skills/` tree with no recorded provenance. Two constraints shape the fix:

1. Vendored skills must stay manageable by `npx skills` (add/update). That rules out the herdr-style in-file vendor header: any local edit changes the file, so `skills-lock.json` `computedHash` never matches upstream and an update overwrites the header regardless. Provenance therefore has to live outside the skill bodies, in `skills-lock.json`.
2. Vendored skills must NOT be republished by `npx skills add cormacc/dotagents`, while all agent config stays maintainable within this single repo.

`herdr` is a permanent exception to (1): its `SKILL.md` sits at its repo root, so `npx skills add ogulcancelik/herdr` installs the entire Rust project (Cargo.toml, flake.nix, src/, docs/). It stays hand-vendored with its existing header until upstream packages it under a `skills/` subdirectory.

Verified findings behind this task:
- `skills-lock.json` (v1) records `source`, `sourceType`, `skillPath`, `computedHash` per skill. `computedHash` is a content hash of the installed skill, confirmed by an update that rewrote only the hashes. This is the correct drift signal and the intended design: it answers "has this skill changed?", which is the only question that matters for a vendored copy. Do NOT track upstream repo commits — a SHA churns on every unrelated commit to the source repo while saying nothing about whether the skill itself moved. The provisional README "Revision" column is therefore wrong and should be dropped rather than backfilled.
- `npx skills add cormacc/dotagents --list` reports 16 skills, including all 4 vendored ones: they are currently republished to consumers, who get stale copies rather than upstream.
- `npx skills add` installs into `<project>/.agents/skills/` or `~/.agents/skills/`. Since `agents.nix` symlinks `~/.agents/skills` at this repo's `skills/`, a global install writes straight into the published tree — the likely origin of the current state.
- Attribution gap: herdr ships a LICENSE upstream that did not come across with its SKILL.md.

** TODO herdr-orch: support unmanaged harness kinds herdr cannot start or detect :skill:herdr_orch:
:PROPERTIES:
:CUSTOM_ID: 22f68a11-eeef-43e9-81d3-79341842ca84
:CREATED: [2026-08-04 Tue 19:44]
:END:
:LOGBOOK:
- Created [2026-08-04 Tue 19:44]
:END:
A harness absent from herdr's `agent start --kind` enum (e.g. dirge) cannot participate in delegation at all today, even though most of the protocol does not actually depend on agent registration. Adding the kind upstream is the clean fix; this task is the local workaround.

What already works without registration (verified):
- `task publish` takes identity purely from the injected HERDR_ORCH_* env vars and makes no herdr agent call (cli.clj:443).
- `task collect <full-task-uuid>` captures and validates the result file; maybe-close! (cli.clj:258) swallows the failed agent lookup and simply skips the pane close.
- `pane split --env KEY=VALUE` can inject the protocol variables (cli.clj:755 -> herdr.clj:89). Note `oh spawn` cannot -- it hardcodes :env {} (cli.clj:827).

What is blocked:
- Spawning: spawn! calls herdr/start! with the kind (cli.clj:339), and `agent start` additionally verifies the expected agent was *detected*, so PATH-shadowing a supported kind fails rather than mis-registering.
- Orchestrating: parent-identity (cli.clj:122) runs `agent get` on $HERDR_PANE_ID, so an unsupported harness cannot drive `task run`/`start`, `collect --any`, or `prune` either. Verified empirically: from a bare pane, `oh task run scout --task x --print-prompt` fails with agent_not_found.

Desired outcome: let a :harnesses entry declare itself launch-by-command (a command template plus e.g. :managed false). spawn! then uses `pane split` + `pane run` instead of `agent start` and flags the ledger entry as unmanaged.

Load-bearing safety requirement: for an unmanaged entry, `prune` and `collect --any` must treat absence from `agent list` as *unknown*, never as proof of death. Today absence is part of prune's staleness proof, so an unmanaged child that is alive and working satisfies the whole proof (uncaptured, non-terminal, no RESULT yet, absent from the listing) and can be pruned mid-flight. Shipping the launch path without this would build that hazard into the tool.

Accepted degradation for unmanaged kinds: no lifecycle states, no :child-session, no auto-close, no agent prompt/wait/read, excluded from fan-in, and no ability to spawn grandchildren. The result file remains the completion signal, which is the part that matters.
