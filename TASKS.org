A persona is mandatory today: =oh task run --task 'write a readme'= fails with "persona not found in project, home, or packaged roster" and lists the seven packaged names. There is no =--persona-file=, no inline persona argument, and no runtime trait-only construction -- =roster= (cli.clj) resolves =<name>.md= through project > home > packaged and fails when nothing matches. So the two natural throwaway delegations ("spawn a subagent to write a readme", "spawn a subagent to check the scripts folder contents") cannot be expressed without first authoring a definition file.

Desired outcome: a spawn with no persona, and/or a light persona composed at runtime from traits, without adding a definition to the roster. Both shapes want the same thing -- an assignment-only child that still gets the delegation, identity, and publication guidance the launcher injects.

- Does a runtime trait-composed persona need a name for the ledger label and the child name (=child-label= composes =<persona>-<index>-<model>=), and if so what is it?
- Does =--print-prompt= still make sense as the inspection route.

Second shape, added [2026-08-19] from the prose-style evaluation: a *measurement* session, which is a stricter case than the persona-less child above and pulls in the opposite direction on one point. That evaluation ran 45 sessions across three rounds as raw =pi --print= invocations, entirely outside the ledger, because =oh= could not express them. Two reasons, both verified:

- No environment-override surface. =oh task run= and =oh task start= accept only =--model=, =--timeout=, =--tab=/=--split=, =--spawns=, =--retro=/=--no-retro=, =--prompt-extra=, =--print-prompt=, and =--worktree=. Grepping contract.md for those terms returns nothing, against a positive control of three =Model resolution= matches.

Whatever lands must let a caller opt out of the wrap entirely, not merely skip the persona.

The hard part is the completion signal: the contract requires the child to publish a v1 envelope through the injected launcher, and a bare model rewriting prose cannot. A measurement mode needs a different terminal condition, such as process exit plus the expected output artefact existing. Batching matters too, because 15 sessions per round do not each want a pane.

Cost of the gap, measured: the isolation audit was rebuilt by hand in each round (transcript capture, tool-call extraction, a positive-controlled contamination matrix). As a spawn property it would be derived once.

Two verified =pi= facts any implementation must respect, both of which cost a round when they were assumed rather than checked:

** TODO [#A] Skill vendoring improvements :project_convention:
:PROPERTIES:
:CUSTOM_ID: 98cf369c-83aa-4961-bf8b-2fa3aca8b2f3
:CREATED: [2026-07-31 Fri 13:17]

Vendored third-party skills (dirge, find-skills, skill-creator, herdr) currently sit hand-copied inside the published `skills/` tree with no recorded provenance. Two constraints shape the fix:

1. Vendored skills must stay manageable by `npx skills` (add/update). That rules out the herdr-style in-file vendor header: any local edit changes the file, so `skills-lock.json` `computedHash` never matches upstream and an update overwrites the header regardless. Provenance therefore has to live outside the skill bodies, in `skills-lock.json`.
2. Vendored skills must NOT be republished by `npx skills add cormacc/dotagents`, while all agent config stays maintainable within this single repo.

`herdr` is a permanent exception to (1): its `SKILL.md` sits at its repo root, so `npx skills add ogulcancelik/herdr` installs the entire Rust project (Cargo.toml, flake.nix, src/, docs/). It stays hand-vendored with its existing header until upstream packages it under a `skills/` subdirectory.

Verified findings behind this task:
- `skills-lock.json` (v1) records `source`, `sourceType`, `skillPath`, `computedHash` per skill. `computedHash` is a content hash of the installed skill, confirmed by an update that rewrote only the hashes. This is the correct drift signal and the intended design: it answers "has this skill changed?", which is the only question that matters for a vendored copy. Do NOT track upstream repo commits — a SHA churns on every unrelated commit to the source repo while saying nothing about whether the skill itself moved.
