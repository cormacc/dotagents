Extract reusable org-file primitives into their own CLI-oriented org tooling so non-task consumers (jira, emacsclient, future doc tooling) can depend on org parsing without pulling in the tasks UI.

Motivation:
- The previous in-pi-tool `org_read_section` seed was removed; future generic org tooling should expose a CLI contract rather than a persistent agent-facing pi tool registration.
- `nvim-orgmode/tree-sitter-org` is an actively maintained tree-sitter grammar (MIT, weekly-touched, backs nvim-orgmode) whose `(section)` / `(headline)` / `(body)` node shapes map cleanly onto the slicing and parsing tasks we hand-roll today in `pi/extensions/tasks/parser.ts` and `section.ts`.
- Pi today has no JS-side tree-sitter runtime; introducing one for a single ~50-line primitive was rejected as disproportionate. Doing it once, as part of an extension extraction that amortises across multiple consumers, is the right time.

Acceptance criteria:
- New extension at `pi/extensions/org/` with its own `package.json`, `index.ts`, `README.md`.
- `web-tree-sitter` (or native bindings, decided during the work) wired up with `tree-sitter-org.wasm` bundled or fetched at install time; async grammar init handled lazily so cold-start cost only hits the first call.
- A generic section-reading CLI command is implemented using a tree-sitter query against `(document (section (headline (item) @name)) @section)`, with a migration path for any current `ot section` callers.
- Decision documented in the new extension's README on whether to migrate `parser.ts`'s heading / property-drawer regexes to tree-sitter queries in the same change, or leave that as a follow-up.
- Closure-time `evaluateSummaryRefresh` path in the tasks extension continues to work synchronously — either by keeping a thin regex-based `hasSummaryHeading` check in `summary.ts`, or by ensuring the tree-sitter init is eager enough that the sync read remains viable. Recorded as a Decision.
- Unit tests for the migrated primitive cover the same five acceptance-criteria cases as the original (section present, absent, last, no headings, literal `* ` inside src block).
- README cross-references the `org-tasks` resume read order and the future `tasks_resume_brief` consumer.

No longer blocked by an in-place pi tool seed; coordinate with existing `ot section` behaviour before extracting a generic CLI.

Findings from a quick review of pi/extensions/bb-tasks/index.ts.

Bugs
- Exit-code ignored: runBbCommand collects bash tool content but sendBbBashMessage always passes error:false on the non-throw path. pi's bash tool returns failures as content, not exceptions, so failed tasks render as successes. Surface and propagate the bash tool's failure flag.
- Task parser regex requires whitespace + description; tasks without docstrings are dropped. Relax to ^(\S+)(?:\s+(.*))?$ and treat missing description as empty.
- `bb tasks` header detection only filters the literal "The following tasks are available" line. Stricter approach: discard lines that don't match the task-line shape.

Staleness
- refreshTasks runs only at session_start. Editing bb.edn mid-session leaves autocomplete stale. Easiest fix: call refreshTasks() from getArgumentCompletions (return current snapshot, refresh in background). Optional: fs.watch on bb.edn.

UX
- /bb with no args lists tasks via ctx.ui.notify, which is cramped for many tasks. Reuse the custom renderer (or a sibling list renderer) instead.
- Add `/bb info <task>` (or describe) to surface the task body via `bb tasks --help <name>` / `bb describe-task` without leaving pi.

Code cleanups
- Asymmetric exec paths (pi.exec for discovery vs createBashToolDefinition for execution) is intentional but worth a comment.
- MAX_NOTIFY_OUTPUT_LENGTH is now applied to the renderer's details output, not notify popups — rename or split.

`ot status <id> DONE` for a task whose `:CUSTOM_ID:` lives inside a
change-record's `* Plan` (i.e. the subtask was migrated out of
TASKS.org into a `#+IMPORT:`-linked plan file) reports
`TODO → DONE` in stdout but does not actually rewrite the heading
keyword in the record file. `ot list` then continues to show the
subtask as `TODO`.

Repro (encountered 2026-05-22 during the *Refactor flake* task):

1. Create a top-level task, run `ot record create <id>` to scaffold
   a change-record at `design/log/…org`.
2. Hand-author `** TODO …` headings under `* Plan` with their own
   `:CUSTOM_ID:` UUIDs.
3. Run `ot status <subtask-uuid> STARTED` — prints success.
4. Run `ot status <subtask-uuid> DONE` — prints success.
5. Grep the record file: heading is still `** TODO`.
6. `ot list --levels 3` shows the subtask as `TODO`.

Workaround used: hand-edit the heading + add `CLOSED:` + `:LOGBOOK:`
entries directly in the record file.

Expected: `ot status` should locate the subtask in whichever file
holds the matching `:CUSTOM_ID:` (record file *or* TASKS.org) and

in place. Same node, same writer.

pi writes runtime state (lastChangelogVersion, defaultProvider, defaultModel) into pi/settings.json alongside durable config (packages, theme, thinking settings), producing dirty-tree noise every session.

install-git-filter.sh already exists and solves this cleanly via a `clean` filter that strips the three volatile keys at stage time (smudge = cat). The remaining friction is that it requires a manual per-clone invocation, easy to forget on a fresh checkout — the clone used in this session evidently never had it run.

Action:
- Add a Home Manager activation hook in agents.nix that invokes install-git-filter.sh from the dotagents submodule when present and the filter isn't already configured (`git config --get filter.pi-settings.clean`).
- Make the script idempotent re. already-installed state (it currently re-runs cleanly, but the activation hook should short-circuit when configured to avoid unnecessary work).
- Document in agents/README.org and the dotagents AGENTS.md so manual invocation is also discoverable for non-Nix clones.
- Optionally widen the strip list as pi adds more runtime keys (reactive; not part of initial scope).

Explicitly not in scope:
- pi/settings.template.json vendored + gitignore live file. Requires manual template updates after every package install or setting change; high drift risk.

Follow-up: 12543944-2045-444a-8135-b7cfb47a6d3e — upstream request to pi maintainers for a runtime/config split, which would remove the need for this workaround entirely.
