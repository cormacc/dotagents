Findings from a quick review of pi/extensions/bb-tasks/index.ts.

Bugs
- Exit-code ignored: runBbCommand collects bash tool content but sendBbBashMessage always passes error:false on the non-throw path. pi's bash tool returns failures as content, not exceptions, so failed tasks render as successes. Surface and propagate the bash tool's failure flag.
- Task parser regex requires whitespace + description; tasks without docstrings are dropped. Relax to ^(\S+)(?:\s+(.*))?$ and treat missing description as empty.
- `bb tasks` header detection only filters the literal "The following tasks are available" line. Stricter approach: discard lines that don't match the task-line shape.

Staleness
- refreshTasks runs only at session_start. Editing bb.edn mid-session leaves autocomplete stale. Easiest fix: call refreshTasks() from getArgumentCompletions (return current snapshot, refresh in background). Optional: fs.watch on bb.edn.

UX
- /bb with no args lists tasks via ctx.ui.notify, which is cramped for many tasks. Reuse the custom renderer (or a sibling list renderer) instead.
- Add `/bb info <task>` (or describe) to surface the task body via `bb tasks --help <name>` / `bb describe-task` without leaving pi.

Code cleanups
- Asymmetric exec paths (pi.exec for discovery vs createBashToolDefinition for execution) is intentional but worth a comment.
- MAX_NOTIFY_OUTPUT_LENGTH is now applied to the renderer's details output, not notify popups — rename or split.

** TODO pi/settings.json: auto-install git clean filter on activation :project-convention:
:PROPERTIES:
:CUSTOM_ID: a064abbd-0192-4ca2-8394-50d371c57651
:CREATED: [2026-05-29 Fri 00:20]

:LOGBOOK:

pi writes runtime state (lastChangelogVersion, defaultProvider, defaultModel) into pi/settings.json alongside durable config (packages, theme, thinking settings), producing dirty-tree noise every session.

install-git-filter.sh already exists and solves this cleanly via a `clean` filter that strips the three volatile keys at stage time (smudge = cat). The remaining friction is that it requires a manual per-clone invocation, easy to forget on a fresh checkout — the clone used in this session evidently never had it run.

Action:
- Add a Home Manager activation hook in agents.nix that invokes install-git-filter.sh from the dotagents submodule when present and the filter isn't already configured (`git config --get filter.pi-settings.clean`).
- Make the script idempotent re. already-installed state (it currently re-runs cleanly, but the activation hook should short-circuit when configured to avoid unnecessary work).
- Document in agents/README.org and the dotagents AGENTS.md so manual invocation is also discoverable for non-Nix clones.
- Optionally widen the strip list as pi adds more runtime keys (reactive; not part of initial scope).

Explicitly not in scope:
- pi/settings.template.json vendored + gitignore live file. Requires manual template updates after every package install or setting change; high drift risk.

Follow-up: 12543944-2045-444a-8135-b7cfb47a6d3e — upstream request to pi maintainers for a runtime/config split, which would remove the need for this workaround entirely.
