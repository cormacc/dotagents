#+IMPORT: [[plan:2026-11-04-parallel-file-guard.org]]
The portable rule "Read a path only after the call that writes it has finished and succeeded. Never run the two calls in parallel." (home/AGENTS.md, File operations) does not stop the agent from batching a write and its verifying read into one parallel tool call. The check then reads the old file and its result is wrong. Restating the rule has not changed the behaviour, so add a structural guard: a harness check that warns, or serialises, when one parallel tool batch both writes a path (Edit, Write) and reads it (Read, grep or bash naming the same path), or writes the same path twice (Edit, Write, or a bash ~sed -i~ or redirect naming it).

Origin:
- cwd: /home/cormacc/nmd/products/connect/portal
- git: git@git.nmd.ie:products/connect/portal @ fail-fast
- timestamp: [2026-10-14 Wed 11:10]
- sender: agent

Evidence:
- 2026-10-14: four batches paired an Edit with a grep or sed of the same file; each check read the pre-edit content, and one led the agent to report a remaining match that the edit had already removed.
- RETROLOG.org 2026-10-01 records the same failure ("Parallel read and write"), after which the rule was rewritten as an ordering rule.
- 2026-10-22 (dotagents, herdr-orch change-record closure): one batch ran an Edit and a bash ~sed -i~ line deletion on the same record. The Edit wrote content from its own earlier read, so the deletion was lost without an error; a diff against a snapshot showed it.
