=oh task close= refuses indefinitely when a child process has exited while its last observed lifecycle state was =working=. Observed 2026-08-11 on two captured, validated children: =oh agent list= returned no live agents at all, while =task close= reported =status=retained=, =reason=unsettled=, =agent-status=working= on repeated attempts spanning several minutes. The panes had to be closed with raw =oh pane close=, which bypasses the ledger guard entirely.

The guard requires a live observation in =idle= or =done=. A child that vanishes mid-=working= can never produce one, so the entry is unclosable through the supported path. The documented released-name fallback (a live pane whose recorded =shell_pid= still matches and whose foreground is not busy) did not engage, plausibly because the pane's foreground was still the agent's own TUI process.

Acceptance criteria:
- [X] =close= resolves a captured entry whose agent is absent from =agent list=, rather than reporting =unsettled= forever; the outcome names why it acted (no live occupant) so it is distinguishable from closing a settled agent -- found already satisfied before any change (state A below), and =--abandon= now names its own outcome =pane-left-to-operator=.
- [X] The existing guards are untouched for the cases they exist for: a live =working= child is still refused, and an entry owned by another session is still refused -- both asserted, and both re-checked by deliberately removing =assert-closable!= (5 failures).
- [X] A stale =working= status alone never authorises closing a pane that still has a live occupant -- =--abandon= closes no pane at all, so the bar is not merely upheld but unreachable.
- [X] Reproduce the observed state before fixing, and trigger the new path deliberately rather than only observing it pass -- three candidate states driven before any edit, and the shipped guard sabotaged two ways afterwards.
Must not: weaken the ownership guard; make =pane close= the documented route for a spawned child.

Measurement [2026-08-13 Thu]: all three candidate states driven against the fake harness. (A) A child genuinely absent from =agent list= *already closes today* -- =released-name-close= finds no occupant, the foreground is idle, the =shell_pid= witness matches, and it takes the pane. So the first acceptance criterion is already satisfied and is not the defect. (B) An occupant present at the pane but reporting a stale =working= reproduces the reported triple exactly (=retained=/=unsettled=/=agent-status=working=), because the occupant branch returns before the foreground and =shell_pid= evidence ever runs. (C) A named, genuinely working child retains correctly.

The report is internally inconsistent, and this blocks a fix rather than merely annoying: =:agent-status= is populated *only* where an occupant was observed, so "=agent list= returned no live agents at all" and "=agent-status=working=" cannot both describe the same moment. Either the listing was non-empty during the close attempts, or the two observations are minutes apart. The body's own guess -- that the fallback did not engage because the pane's foreground was still the agent's TUI -- is wrong: that branch returns a result with no =:agent-status= at all.

Resolved by option (a). `close --abandon` retires the ledger round for a captured entry whose pane cannot be confirmed free, running every `assert-closable!` guard and skipping only the liveness observation; it issues no `pane close`, reports `abandoned`/`pane-left-to-operator`, and records `:pane-abandoned true`. No existing guard moved: a live occupant still holds its pane, `collect --close` never abandons, and `close --settled --abandon` is refused rather than ignored. The pane was never the thing that had to die -- the entry outliving it in `close --settled` and `orphans` was.

Originally blocked on a design decision, not on effort. Making a listed-but-stale occupant closable on foreground evidence was implemented and reverted: it contradicts =close-shell-pid-fallback-still-requires-a-settled-occupant=, whose stated rationale is that prompt text must never land mid-turn just because a name disappeared, and it violates this task's own third criterion, since a listed occupant *is* a live occupant. Options: (a) leave the pane guard alone and add a way to resolve the *entry* without taking the pane, so a stuck round stops blocking =close --settled= and =orphans= while the operator disposes of the pane; (b) let idle-foreground evidence override a reported status, which needs the existing contract renegotiated deliberately; (c) bound it by time as well as foreground. (a) is the only one that touches no existing guard.

** TODO [#B] Skill vendoring improvements :project_convention:
:PROPERTIES:
:CUSTOM_ID: 98cf369c-83aa-4961-bf8b-2fa3aca8b2f3
:CREATED: [2026-07-31 Fri 13:17]
:END:
:LOGBOOK:
- Created [2026-07-31 Fri 13:17]
:END:
Vendored third-party skills (dirge, find-skills, skill-creator, herdr) currently sit hand-copied inside the published `skills/` tree with no recorded provenance. Two constraints shape the fix:

1. Vendored skills must stay manageable by `npx skills` (add/update). That rules out the herdr-style in-file vendor header: any local edit changes the file, so `skills-lock.json` `computedHash` never matches upstream and an update overwrites the header regardless. Provenance therefore has to live outside the skill bodies, in `skills-lock.json`.
2. Vendored skills must NOT be republished by `npx skills add cormacc/dotagents`, while all agent config stays maintainable within this single repo.

`herdr` is a permanent exception to (1): its `SKILL.md` sits at its repo root, so `npx skills add ogulcancelik/herdr` installs the entire Rust project (Cargo.toml, flake.nix, src/, docs/). It stays hand-vendored with its existing header until upstream packages it under a `skills/` subdirectory.

Verified findings behind this task:
- `skills-lock.json` (v1) records `source`, `sourceType`, `skillPath`, `computedHash` per skill. `computedHash` is a content hash of the installed skill, confirmed by an update that rewrote only the hashes. This is the correct drift signal and the intended design: it answers "has this skill changed?", which is the only question that matters for a vendored copy. Do NOT track upstream repo commits — a SHA churns on every unrelated commit to the source repo while saying nothing about whether the skill itself moved. The provisional README "Revision" column is therefore wrong and should be dropped rather than backfilled.
- `npx skills add cormacc/dotagents --list` reports 16 skills, including all 4 vendored ones: they are currently republished to consumers, who get stale copies rather than upstream.
- `npx skills add` installs into `<project>/.agents/skills/` or `~/.agents/skills/`. Since `agents.nix` symlinks `~/.agents/skills` at this repo's `skills/`, a global install writes straight into the published tree — the likely origin of the current state.
- Attribution gap: herdr ships a LICENSE upstream that did not come across with its SKILL.md.
