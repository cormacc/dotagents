** TODO code-review: verify negative tests are non-vacuous :skill_code-review:
:PROPERTIES:
:CUSTOM_ID: fd8e0daf-8272-4442-b7d8-8b3d62948b1e
:CREATED: [2026-07-30 Thu 10:31]
:END:
:LOGBOOK:
- Created [2026-07-30 Thu 10:31]
:END:
Negative and anti-criterion assertions can pass without exercising the guard they claim to prove—for example because setup state already excludes the case, test ordering captures it first, or a logged `--help` probe satisfies a broad matcher. Add a general review/testing rule: when a must-not assertion is materially susceptible to a vacuous pass, temporarily break or remove the guarded condition and confirm the focused test fails, then restore it. Keep this targeted to load-bearing negative guarantees rather than requiring mutation checks for every ordinary assertion.

Origin:
- cwd: /home/cormacc/dotfiles/agents
- git: git@github.com:cormacc/dotagents.git @ main
- timestamp: [2026-07-30 Thu 10:25]
- sender: agent

Evidence:
During `collect --any` work, mutation checks proved the `:status "failed"` candidate exclusion and exposed a foreign-session assertion that passed only because an owning capture had already set `:captured-at`. A separate pane-close absence assertion initially matched the unconditional `pane close --help` preflight probe. The pattern is general testing validity, not Herdr-specific behavior.

Additional facet (2026-07-30, `prune` implementation, task 032dbe16): overlapping lifecycle guards can also produce a vacuous pass without any test-ordering or matcher trick — a specific guard's precondition can be implied by a more general one that always fires first (e.g. an already-captured entry is also, incidentally, non-terminal), so a test asserting on the specific guard's message alone can pass for the wrong reason. Extend the rule: when two guards overlap this way, isolate the specific guard under test by first neutralizing the general precondition, not by asserting on message text alone.

Additional facet (2026-07-30, `collect --any` settle-close implementation, task e8ea2227): a fixture standing in for an external system can produce the same vacuous pass by *recording* a flag without *honouring* it — a test asserting a call carried a given flag (e.g. `--until`) can pass even though the fixture's behavior is identical with or without it, so a regression that drops the flag still passes. Extend the rule again: when a test's claim depends on a flag's effect, make the fixture actually implement that effect, not just log the argv.
